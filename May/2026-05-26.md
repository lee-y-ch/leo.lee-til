#### 주제 1: 데이터를 기록하는 방식의 변화
- 초기에는 천공 카드 같은 물리적인 매체에 데이터를 기록했다.
- 천공 카드는 한 줄에 80개의 문자를 담는 구조였고, 이 흔적은 지금도 일부 CLI 환경에서 한 줄을 80컬럼 기준으로 보여주는 문화에 영향을 주었다.
- 데이터베이스가 없다면 애플리케이션은 파일 시스템에 정보를 기록해야 한다.
- 파일 시스템 방식은 기능별로 파일을 만들고, 데이터를 종이에 적듯 저장하는 방식에 가깝다.
- 하지만 파일이 많아지고 데이터가 커지면 중복, 검색 어려움, 권한 관리 부족, 동시 수정 문제, 데이터 오류, OS 간 호환성 문제 등이 발생한다.

#### 주제 2: 데이터베이스의 등장
- 데이터베이스는 구조화된 데이터의 모음이다.
- 관계형 데이터베이스는 데이터를 테이블 단위로 관리하고, 테이블 사이의 관계를 표현하는 데이터베이스이다.
- 데이터베이스는 파일 시스템의 여러 한계를 해결하기 위해 등장했다.
- 데이터 중복 문제는 중앙 집중 관리와 관계 표현을 통해 줄일 수 있다.
- 검색 문제는 인덱스 같은 자료구조를 사용해 효율적으로 해결할 수 있다.
- 보안 문제는 사용자별, 데이터베이스별 권한 제어를 통해 개선할 수 있다.
- 동시 수정 문제는 트랜잭션과 락을 통해 충돌을 제어한다.
- 잘못된 데이터 입력 문제는 무결성 제약 조건을 통해 데이터베이스 수준에서 규칙을 강제한다.
- OS 호환성 문제는 데이터베이스 관리 시스템이 공통된 방식으로 데이터를 다루도록 제공하면서 해결한다.
- RDBMS(Relational Database Management System)는 관계형 데이터를 저장하고 관리하는 시스템이다.

#### 주제 3: 테이블 설계
- 테이블 설계는 크게 엔티티 정의, 속성 정의, 관계 정의로 진행할 수 있다.
- 엔티티는 데이터베이스에 넣고자 하는 대상이다.
- 예를 들어 학생, 강의, 회원, 게시글 등이 엔티티가 될 수 있다.
- 속성은 엔티티가 가진 정보이다.
- 예를 들어 학생의 이름, 학번, 생년월일 등이 속성에 해당한다.
- 관계는 테이블끼리의 연결이다.
- 예를 들어 학생과 강의 사이에는 수강 관계가 있을 수 있다.
- 관계형 데이터베이스에서는 테이블 간 관계를 잘 설계해야 데이터 중복을 줄이고 일관성을 유지할 수 있다.

#### 주제 4: SQL
- SQL(Structured Query Language)은 관계형 데이터베이스와 대화하기 위한 언어이다.
- DDL(Data Definition Language)은 데이터 구조를 정의하는 명령어이다.
- 예를 들어 `CREATE`, `ALTER`, `DROP` 등이 DDL에 해당한다.
- DML(Data Manipulation Language)은 데이터를 조회하거나 조작하는 명령어이다.
- 예를 들어 `SELECT`, `INSERT`, `UPDATE`, `DELETE` 등이 DML에 해당한다.
- DCL(Data Control Language)은 데이터 접근 권한을 제어하는 명령어이다.
- 예를 들어 `GRANT`, `REVOKE` 등이 DCL에 해당한다.

#### 주제 5: ERD
- ERD(Entity Relationship Diagram)는 개체와 관계를 한눈에 알아볼 수 있도록 표현한 도표이다.
- ERD를 통해 테이블이 어떤 데이터를 가지는지, 테이블끼리 어떤 관계를 맺는지 시각적으로 확인할 수 있다.
- 개념적 모델링은 현실에 존재하는 데이터와 관계를 구상하는 단계이다.
- 논리적 모델링은 개념적 모델을 바탕으로 업무 중심의 데이터 모델을 만드는 단계이다.
- 물리적 모델링은 논리적 모델을 실제 데이터베이스에 구현할 수 있도록 테이블, 컬럼, 키, 제약 조건 등으로 구체화하는 단계이다.

#### 주제 6: 까마귀 발 표기법
- 까마귀 발 표기법은 ERD에서 테이블 간 관계의 수와 선택성을 표현하는 방식이다.
- One and Only는 정확히 하나와 반드시 연결되는 관계이다.
- `||`로 표현하며, 필수 1:1 관계라고 볼 수 있다.
- 1:1 관계는 A와 B가 서로 최대 하나와만 연결되는 관계이다.
- 다만 반드시 연결되어야 하는지는 선택성에 따라 달라진다.
- 1:N 관계는 A 하나가 B 여러 개와 연결될 수 있고, B 하나는 A 하나와 연결되는 관계이다.
- 예를 들어 회원 1명은 게시글 여러 개를 작성할 수 있고, 게시글 1개는 회원 1명에게 속한다.
- M:N 관계는 A 여러 개가 B 여러 개와 연결될 수 있는 관계이다.
- 예를 들어 학생은 여러 수업을 들을 수 있고, 수업 하나에는 여러 학생이 참여할 수 있다.
- 실제 관계형 데이터베이스에서는 M:N 관계를 보통 중간 테이블로 풀어서 표현한다.

#### 주제 7: 식별 관계와 비식별 관계
- 식별 관계는 자식 테이블이 부모 테이블 없이는 존재할 수 없는 관계이다.
- 이 경우 부모의 기본키가 자식의 기본키 일부로 포함될 수 있다.
- 비식별 관계는 자식 테이블이 부모와 연결되어 있지만, 스스로 식별 가능한 기본키를 가지는 관계이다.
- 비식별 관계에서는 부모의 키가 자식 테이블의 외래키로만 존재하고, 자식의 기본키는 별도로 관리된다.
- 두 관계를 구분하면 데이터의 생명주기와 의존성을 더 명확하게 설계할 수 있다.

#### 주제 8: 인덱스
- 인덱스는 데이터베이스에서 원하는 데이터를 빠르게 찾기 위해 사용하는 자료구조이다.
- 책의 목차처럼 특정 컬럼 값을 기준으로 데이터의 위치를 빠르게 찾을 수 있게 도와준다.
- 인덱스를 사용하면 조회 성능을 높일 수 있지만, 데이터 삽입, 수정, 삭제 시 인덱스도 함께 갱신해야 하므로 쓰기 비용이 증가한다.
- 인덱스의 대표적인 구조에는 Hash Index, B-Tree, B+Tree, Full Text Index 등이 있다.

#### 주제 9: Hash Index
- Hash Index는 입력 값을 해시 함수에 넣어 고정된 길이의 해시 값으로 바꾸고, 그 값을 기준으로 데이터 위치에 접근하는 방식이다.
- 같은 입력 값은 같은 해시 값을 만들기 때문에, 정확히 일치하는 값을 찾을 때 매우 빠르다.
- 중간에 트리 노드를 탐색하지 않고 해시 버킷 주소로 바로 접근할 수 있다는 장점이 있다.
- 정렬된 값을 관리하지 않기 때문에 인덱스 크기 측면에서도 효율적일 수 있다.
- 하지만 해시 값은 정렬되어 있지 않고 무작위에 가깝기 때문에 범위 검색이 어렵다.
- `LIKE '%검색어%'` 같은 부분 일치 검색이나 정렬, 그룹화에도 적합하지 않다.
- 서로 다른 키가 같은 해시 값을 가지는 해시 충돌이 발생할 수 있고, 충돌이 많아지면 성능이 떨어질 수 있다.
- Hash Index는 주로 Key-Value 기반 데이터베이스나 In-Memory DB에서 많이 사용된다.
- MySQL InnoDB에서도 자주 접근되는 값을 내부적으로 해시 형태로 최적화하는 Adaptive Hash Index를 사용할 수 있다.

#### 주제 10: Tree, B-Tree, B+Tree
- Tree는 부모-자식 관계를 가진 계층적 자료구조이다.
- 시작 노드를 루트 노드, 끝 노드를 리프 노드라고 한다.
- 정렬 가능한 값을 기준으로 왼쪽은 작은 값, 오른쪽은 큰 값처럼 비교 규칙을 사용해 데이터를 찾는다.
- 일반적인 트리는 데이터가 한쪽으로 치우치면 탐색 성능이 나빠질 수 있다.
- B-Tree는 Balanced Tree의 한 종류로, 트리의 높이를 균형 있게 유지한다.
- B-Tree는 노드마다 여러 개의 키와 자식 포인터를 가질 수 있고, 모든 리프 노드가 비슷한 깊이를 유지한다.
- 균형이 유지되기 때문에 어떤 데이터든 비교적 일정한 비용으로 탐색할 수 있다.
- 다만 균형을 맞추기 위한 노드 분할과 병합 비용이 발생한다.
- B+Tree는 MySQL InnoDB에서 기본적으로 사용하는 인덱스 구조이다.
- B+Tree는 내부 노드에는 탐색을 위한 키를 저장하고, 실제 데이터나 데이터 주소는 리프 노드에 모아둔다.
- 리프 노드끼리는 연결 리스트처럼 이어져 있어 범위 검색과 순차 접근에 유리하다.

#### 주제 11: B-Tree와 B+Tree의 차이
- B-Tree와 B+Tree의 핵심 차이는 내부 노드에 실제 데이터 주소까지 함께 저장하느냐이다.
- B-Tree는 노드에 키와 값 또는 주소를 함께 저장할 수 있다.
- B+Tree는 내부 노드에는 키만 두고, 실제 값 또는 주소는 리프 노드에만 둔다.
- 데이터베이스는 디스크에서 데이터를 읽을 때 보통 페이지 단위로 읽는다.
- MySQL InnoDB의 기본 페이지 크기는 보통 16KB이다.
- B+Tree는 내부 노드에 키만 저장하므로 한 페이지에 더 많은 키를 담을 수 있다.
- 한 노드가 가질 수 있는 자식 노드의 최대 개수를 Fan-out이라고 한다.
- B+Tree는 Fan-out이 커지기 쉬워 트리 높이가 낮아지고, 그만큼 디스크 접근 횟수를 줄일 수 있다.
- 또한 B+Tree는 리프 노드가 서로 연결되어 있어 범위 검색 시 한 번 리프까지 내려간 뒤 옆 리프 노드로 순차 이동할 수 있다.
- 이 구조 덕분에 `WHERE id BETWEEN 10 AND 100` 같은 범위 검색에서 B+Tree가 특히 유리하다.

#### 주제 12: Full Text Index
- Full Text Index는 긴 텍스트를 검색하기 위해 사용하는 인덱스이다.
- 일반적인 B+Tree 인덱스는 정렬 가능한 값의 비교 검색에 적합하지만, 문장 안에 특정 단어가 포함되어 있는지 찾는 데는 한계가 있다.
- Full Text Index는 문장을 특정 단위로 쪼개고, 쪼갠 단어를 키로 사용한다.
- Inverted Index는 단어를 기준으로 그 단어가 어느 문서에 등장하는지 관리하는 구조이다.
- 예를 들어 여러 게시글을 단어 단위로 분해한 뒤, `클라우드`라는 단어가 포함된 게시글 목록을 따로 관리할 수 있다.
- MySQL에서는 `FULLTEXT INDEX`를 사용해 전문 검색 인덱스를 만들 수 있다.

#### 주제 13: Full Text Parser
- Parser는 문장을 검색 가능한 단위로 쪼개는 엔진이다.
- Stopword 기반 파서는 공백이나 문장 부호를 기준으로 단어를 나누고, 검색에 큰 의미가 없는 단어를 제외한다.
- 영어권 언어에서는 비교적 잘 동작하지만, 한국어처럼 조사와 어미가 붙는 언어에서는 정확도가 떨어질 수 있다.
- N-gram 파서는 지정한 글자 수만큼 문장을 잘라 인덱싱한다.
- 예를 들어 Bi-gram은 두 글자 단위로 문장을 나눈다.
- N-gram은 한국어처럼 형태 변화가 있는 언어에서도 검색이 잘 되는 편이지만, 인덱스 크기가 커지고 의미 없는 검색 결과가 나올 수 있다.
- MeCab은 한국어 형태소 분석기로, 문장을 형태소 단위로 분석해 검색 품질을 높일 수 있다.
- MeCab은 한국어 검색에서 노이즈를 줄이고 인덱스를 가볍게 만들 수 있지만, 동의어 처리나 문맥 분석, 대규모 검색 기능까지 완벽히 해결하지는 못한다.

#### 주제 14: 전문 검색 엔진
- 한국어 검색 품질과 성능을 높이려면 데이터베이스의 Full Text Index만으로는 한계가 있을 수 있다.
- MySQL의 Full Text Index는 간이 전문 검색 기능으로 볼 수 있으며, INSERT나 UPDATE가 발생할 때마다 문장을 쪼개고 Inverted Index를 갱신해야 하므로 비용이 크다.
- 사용자가 기대하는 검색 기능은 오타 보정, 동의어 처리, 랭킹, 문맥 분석 등으로 점점 높아지고 있다.
- 이런 경우 Elasticsearch 같은 별도 검색 엔진을 두고, 데이터베이스의 데이터를 검색 엔진으로 동기화하여 검색을 맡기는 구조를 사용할 수 있다.
- 더 고도화된 검색에서는 그래프 데이터베이스나 벡터 데이터베이스를 함께 활용할 수도 있다.
- 다만 전문 검색 엔진은 운영 비용과 복잡도가 높아지므로 서비스 요구사항에 맞춰 선택해야 한다.

#### 주제 15: 트랜잭션
- 트랜잭션은 데이터베이스의 무결성과 일관성을 보장하기 위해 여러 작업을 하나의 논리적인 작업 단위로 묶은 것이다.
- 트랜잭션은 일의 최소 단위로 볼 수 있다.
- 여러 연산이 모두 성공해야만 최종 반영되고, 하나라도 실패하면 원래 상태로 되돌려야 한다.
- 이를 All or Nothing이라고 표현한다.
- 트랜잭션 상태에는 Active, Partially Committed, Failed, Aborted, Committed 등이 있다.
- Active는 트랜잭션이 실행 중인 상태이다.
- Partially Committed는 마지막 연산까지 수행했지만 아직 완전히 반영되기 전 상태이다.
- Failed는 트랜잭션 수행 중 오류가 발생한 상태이다.
- Aborted는 실패한 트랜잭션을 롤백해 원래 상태로 되돌린 상태이다.
- Committed는 트랜잭션이 성공적으로 완료되어 결과가 영구 반영된 상태이다.

#### 주제 16: 트랜잭션을 사용하는 이유
- 트랜잭션을 사용하는 이유는 데이터베이스의 무결성과 일관성을 보장하기 위해서이다.
- 무결성은 데이터에 결함이 없고, 정확하고 유효하며 신뢰할 수 있는 상태를 의미한다.
- 일관성은 작업 전후에 데이터 상태가 모순 없이 규칙을 준수하는 것을 의미한다.
- 예를 들어 계좌 이체에서 한 계좌의 잔액은 줄었는데 다른 계좌의 잔액은 늘지 않았다면 일관성이 깨진 것이다.
- 트랜잭션은 이런 중간 실패 상태가 데이터베이스에 남지 않도록 여러 작업을 하나로 묶어 처리한다.

#### 주제 17: ACID
- ACID는 트랜잭션이 안전하게 수행된다는 것을 보장하는 네 가지 성질이다.
- Atomicity(원자성)는 트랜잭션이 완벽하게 수행되거나 전혀 수행되지 않아야 한다는 성질이다.
- Consistency(일관성)는 트랜잭션 전후의 데이터가 항상 정해진 규칙과 제약 조건을 만족해야 한다는 성질이다.
- Isolation(격리성)은 동시에 여러 트랜잭션이 실행되어도 서로 독립적으로 실행되는 것처럼 보여야 한다는 성질이다.
- Durability(지속성)는 트랜잭션이 성공적으로 완료되면 그 결과가 영구적으로 반영되어야 한다는 성질이다.
- Isolation은 격리 정도에 따라 여러 레벨로 나뉘며, 격리 수준이 높을수록 데이터 정합성은 강해지지만 성능 비용이 커질 수 있다.
- 격리 레벨은 데이터베이스 성능 최적화와 동시성 제어에서 중요한 트레이드오프이다.
