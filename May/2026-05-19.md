## 소제목: Spring MVC와 HTTPS의 동작 원리 이해

### 새로 배운 내용

#### 주제 1: 서블릿(Servlet)
- 서블릿은 자바를 사용해 웹 페이지나 데이터를 동적으로 생성하기 위한 서버 측 프로그램이다.
- JSP나 Spring처럼 동적 콘텐츠를 전달하는 기술은 결국 클라이언트의 HTTP 요청을 해석하고, 그에 맞는 HTTP 응답을 만들어 반환해야 한다.
- 웹 애플리케이션이 복잡해지면서 요청과 응답을 직접 처리하는 코드가 반복되었고, 개발자가 비즈니스 로직보다 HTTP 처리 코드에 더 많은 신경을 써야 하는 문제가 생겼다.
- 이를 해결하기 위해 HTTP 요청과 응답의 기본 흐름을 서블릿 메서드 형태로 제공하게 되었다.
- Spring 환경에서는 서블릿을 담고 관리하는 서블릿 컨테이너가 존재한다.
- 각각의 서블릿 핸들러에서 `GET`, `POST` 같은 요청 처리 공통 로직이 반복될 수 있기 때문에, Spring MVC는 Dispatcher Servlet을 통해 공통 흐름을 한 곳에서 처리한다.

#### 주제 2: Dispatcher Servlet
- Dispatcher Servlet은 Spring MVC에서 프론트 컨트롤러 역할을 한다.
- 클라이언트의 요청을 가장 먼저 받아 요청을 해석하고, 적절한 핸들러에게 요청을 전달한 뒤, 처리 결과를 응답으로 반환한다.
- Dispatcher Servlet이 모든 일을 직접 처리하면 역할이 너무 많아지기 때문에 Spring MVC는 여러 구성 요소로 책임을 나눈다.
- `Handler Mapping`은 요청 URL에 맞는 컨트롤러 또는 핸들러를 찾는다.
- `Handler Adapter`는 찾은 핸들러를 실제로 실행할 수 있도록 연결한다.
- `View Resolver`는 컨트롤러가 반환한 결과를 실제 응답 형태로 변환하는 데 도움을 준다.
- 결과물은 보통 HTML 또는 JSON 형태로 반환되며, View Resolver나 메시지 컨버터가 이를 HTTP Response로 포장한다.
- Dispatcher Servlet은 서블릿 컨테이너에 존재하고, Handler Mapping, Handler Adapter, View Resolver 같은 의존 객체들은 Spring 컨테이너가 DI를 통해 주입한다.

#### 주제 3: Spring MVC(Model-View-Controller)
- Spring MVC는 웹 애플리케이션을 구현하기 위한 Spring의 웹 프레임워크이다.
- MVC 패턴은 애플리케이션의 책임을 `Model`, `View`, `Controller`로 분리해 코드의 복잡도를 낮추고 유지보수성을 높이기 위한 구조이다.
- `Controller`는 사용자의 요청을 URL 단위로 받고, 필요한 모델과 뷰를 연결한다.
- `Model`은 실제 비즈니스 로직과 데이터를 담당한다.
- `View`는 사용자가 보는 화면이나 응답 결과를 담당한다.
- 최근 웹 애플리케이션에서는 View가 전통적인 HTML 화면뿐 아니라 JSON 응답인 경우도 많다.
- CSR(Client Side Rendering)이 기본적으로 많이 사용되고, SSR(Server Side Rendering)은 SEO나 초기 렌더링 속도 같은 기술적 요구가 있을 때 선택된다.
- Spring Web MVC는 Spring에서 웹 요청을 처리하기 위해 MVC 패턴을 사용하는 방식이며, 그 중심에 Dispatcher Servlet이 있다.
- Dispatcher Servlet을 직접 코딩할 일은 많지 않지만, 디버깅이나 성능 개선을 할 때 내부 요청 처리 흐름을 이해하고 있으면 도움이 된다.

#### 주제 4: HTTPS
- HTTPS는 HTTP에 보안 요소를 추가한 프로토콜이다.
- 현대 웹은 단순 검색뿐 아니라 로그인, 결제, 개인정보 처리, 자산 관리처럼 민감한 작업을 수행하기 때문에 보안이 중요하다.
- HTTPS는 크게 암호화와 인증을 통해 안전한 통신을 제공한다.

#### 주제 5: HTTPS의 암호화
- 대칭키 암호화는 같은 키로 암호화와 복호화를 수행하기 때문에 속도가 빠르다.
- 하지만 통신 전에 클라이언트와 서버가 같은 대칭키를 안전하게 공유해야 하는 문제가 있다.
- HTTPS의 핵심 과정 중 하나는 클라이언트와 서버가 사용할 대칭키를 안전하게 주고받는 것이다.
- 이를 위해 비대칭키 암호화를 사용한다.
- 클라이언트는 대칭키를 생성한 뒤 서버의 공개키로 암호화해서 서버에게 전달한다.
- 서버는 자신의 개인키로 이를 복호화하여 대칭키를 얻는다.
- 이후 클라이언트와 서버는 공유된 대칭키를 사용해 빠르고 안전하게 데이터를 암호화하여 통신한다.

#### 주제 6: HTTPS의 인증
- HTTPS에서는 클라이언트가 통신하려는 서버가 진짜 서버인지 확인해야 한다.
- 이를 위해 서버는 인증서를 사용한다.
- 인증서에는 서버의 공개키, 인증 기관(CA) 정보, 인증 기관의 전자 서명 등이 포함된다.
- 인증 기관의 전자 서명은 인증 기관의 개인키로 만들어진다.
- 클라이언트가 서버에 접속하면 서버는 자신의 인증서를 클라이언트에게 전달한다.
- 클라이언트는 브라우저나 운영체제에 저장된 신뢰할 수 있는 CA 목록과 CA 공개키를 사용해 인증서를 검증한다.
- 인증서 검증에 성공하면 클라이언트는 서버의 공개키를 신뢰할 수 있고, 이후 대칭키를 안전하게 교환할 수 있다.
