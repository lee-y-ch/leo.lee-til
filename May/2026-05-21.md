### 새로 배운 내용

#### 주제 1: Stateful과 Stateless
- Stateful은 서버가 클라이언트의 상태를 계속 기억하는 방식이다.
- 사용자의 이전 요청이나 진행 상황을 서버가 알고 있기 때문에 맞춤형 서비스나 복잡한 흐름 제어에 유리하다.
- 게임, 채팅, 실시간 협업 서비스처럼 사용자 상태를 계속 추적해야 하는 서비스에서 활용된다.
- 하지만 서버가 상태를 계속 기억해야 하므로 사용자가 많아질수록 서버 부담이 커진다.
- 또한 여러 서버로 분산된 환경에서는 특정 사용자의 상태를 어느 서버가 가지고 있는지 관리해야 하므로 확장이 어려워질 수 있다.
- Stateless는 서버가 클라이언트의 이전 상태를 기억하지 않는 방식이다.
- 각 요청은 독립적으로 처리되며, 서버는 요청을 처리하는 데 필요한 정보를 요청 자체에서 받아야 한다.
- 서버 부담이 적고 확장하기 쉬우며, 여러 서버가 같은 요청을 처리할 수 있어 대규모 트래픽 처리에 유리하다.
- 대신 복잡한 요청에서는 매번 필요한 정보를 함께 보내야 하고, 사용자별 맞춤 서비스나 순서가 중요한 흐름을 관리하기 어렵다.

#### 주제 2: HTTP가 Stateless인 이유
- HTTP는 기본적으로 Stateless한 프로토콜이다.
- 서버가 모든 사용자의 상태를 계속 기억하면 사용자 수가 늘어날수록 서버 자원 부담이 커진다.
- 웹은 개인 맞춤 요청뿐 아니라 다양하고 많은 사용자의 요청을 빠르게 처리해야 하므로, 요청을 독립적으로 처리하는 Stateless 방식이 확장성에 유리하다.
- Stateless 구조 덕분에 서버는 특정 사용자와 계속 묶여 있지 않아도 되고, 여러 서버로 요청을 분산하기 쉬워진다.

#### 주제 3: Connection-oriented와 Connectionless
- Connection-oriented는 연결을 맺은 뒤 연결을 끊기 전까지 계속 유지하는 방식이다.
- 한 번 연결을 유지한 상태에서 데이터를 계속 주고받을 수 있으므로 전달량이 많거나 실시간성이 중요한 서비스에 유리하다.
- 실시간 화상 채팅, 온라인 게임, 채팅 서비스처럼 지속적인 연결이 필요한 경우에 사용된다.
- 하지만 연결을 계속 유지하려면 서버 자원이 계속 사용된다.
- 동시에 많은 연결을 유지하기 어렵고, 한 서버가 감당할 수 있는 사용자 수가 줄어들 수 있다.
- Connectionless는 요청과 응답을 한 번 주고받으면 연결을 끊는 방식이다.
- HTTP는 기본적으로 Connectionless 특성을 가진다.
- 연결을 오래 유지하지 않으므로 서버 자원을 효율적으로 사용할 수 있지만, 실시간으로 계속 데이터를 주고받아야 하는 경우에는 별도의 기술이 필요하다.

#### 주제 4: 인증과 인가
- 인증(Authentication)은 사용자가 진짜 본인이 맞는지 검증하는 과정이다.
- 인가(Authorization)는 인증된 사용자가 특정 행위나 리소스 접근을 해도 되는지 검증하는 과정이다.
- HTTP는 Stateless하고 Connectionless하기 때문에 서버가 이전 요청에서 사용자를 인증했다는 사실을 기본적으로 기억하지 못한다.
- 따라서 원칙적으로는 요청마다 인증과 인가가 필요하다.
- 하지만 매 요청마다 아이디와 비밀번호를 처음부터 다시 검증하는 것은 비효율적이다.
- 그래서 로그인 이후 요청에서는 브라우저가 쿠키, 세션 ID, 토큰 같은 인증 정보를 함께 보내고, 서버는 이를 기반으로 사용자를 식별하고 권한을 확인한다.

#### 주제 5: 쿠키
- 쿠키는 브라우저에 저장되는 작은 데이터이다.
- HTTP가 상태를 저장하지 않더라도, 사용자 개인화나 간단한 상태 저장을 위해 쿠키를 사용할 수 있다.
- 쿠키는 서버에 저장할 필요는 없지만 사용자별로 유지하고 싶은 정보를 클라이언트에 저장할 때 유용하다.
- 예를 들어 방문 기록, 장바구니 정보, 언어 설정 같은 데이터를 쿠키에 저장할 수 있다.
- 서버 자원은 클라이언트 자원보다 비싸기 때문에, 보안성이 크게 중요하지 않은 개인화 정보는 쿠키에 저장하는 것이 효율적일 수 있다.
- 다만 쿠키는 브라우저에 저장되며 사용자가 확인할 수 있으므로 민감한 정보를 그대로 저장하면 안 된다.

#### 주제 6: 세션
- 세션은 서버가 사용자의 인증 상태를 저장하는 방식이다.
- 쿠키는 클라이언트에 저장되기 때문에 보안성이 낮고, 인증 정보를 그대로 담기에는 위험하다.
- 세션 방식에서는 서버가 세션 저장소에 인증 정보와 세션 ID를 저장한다.
- 서버는 로그인에 성공한 사용자에게 세션 ID를 전달하고, 클라이언트는 이후 요청마다 이 세션 ID를 쿠키에 담아 보낸다.
- 서버는 요청으로 전달된 세션 ID를 세션 저장소에서 조회해 사용자가 인증된 상태인지 확인한다.
- 세션 저장소로는 RDB, MySQL, Redis 등을 사용할 수 있으며, 실무에서는 빠른 조회와 만료 처리가 쉬운 Redis를 많이 사용한다.
- 세션은 인증 정보를 서버에서 관리하기 때문에 쿠키만 사용하는 방식보다 보안적으로 더 안전하게 설계할 수 있다.

#### 주제 7: 프레임워크와 라이브러리
- 프레임워크는 개발을 위한 기본 구조, 규칙, 기능을 제공한다.
- 프레임워크를 사용하면 개발 과정이 단순해지고, 기본 기능을 활용해 개발 속도를 높일 수 있다.
- 여러 명이 함께 개발할 때도 같은 구조와 규칙을 따르게 되어 일관성을 유지하기 쉽다.
- 라이브러리는 특정 기능을 미리 만들어 놓은 코드 묶음이다.
- 지도, 그래프, 수학 계산, DB 연결처럼 특정 기능이 필요할 때 가져다 사용할 수 있다.
- 프레임워크와 라이브러리의 차이는 자율성이다.
- 프레임워크는 애플리케이션의 전체 구조와 흐름을 어느 정도 정해주지만, 라이브러리는 개발자가 필요한 기능만 선택해서 호출한다.
- 즉, 프레임워크는 기본 골조를 제공하고, 라이브러리는 전문적인 기능을 제공한다.

#### 주제 8: API
- API(Application Programming Interface)는 서로 다른 시스템, 애플리케이션, 객체가 소통하기 위한 약속이자 접점이다.
- API는 두 대상 사이에서 어떤 요청을 보낼 수 있고, 어떤 응답을 받을 수 있는지 알려주는 설명서 역할을 한다.
- API를 통해 이미 만들어진 다른 애플리케이션과 상호 작용할 수 있다.
- 서로 다른 시스템은 API를 기준으로 데이터를 교환하고 기능을 공유한다.
- 웹 서비스에서는 클라이언트와 서버가 API를 통해 요청과 응답을 주고받는다.

#### 주제 9: 페이징
- 페이징은 많은 데이터를 한 번에 처리하지 않고 적당한 크기의 페이지 단위로 나누어 처리하는 방식이다.
- 게시판에서 여러 개의 글을 나누어 보여줄 때 대표적으로 사용된다.
- 사용자는 한 번에 모든 데이터를 보지 않고 필요한 범위의 데이터만 조회할 수 있다.
- 서버는 필요한 만큼의 데이터만 조회하므로 자원 사용량을 줄일 수 있고, 클라이언트도 한 번에 많은 데이터를 받지 않아 부하가 줄어든다.
- 페이징을 사용하면 사용자가 원하는 페이지로 이동하거나 데이터를 단계적으로 탐색하기 쉬워진다.

#### 주제 10: LIMIT과 OFFSET
- 데이터베이스에서 페이징을 구현할 때 `LIMIT`과 `OFFSET`을 사용할 수 있다.
- `LIMIT`은 몇 개의 데이터를 가져올지 정하는 값이다.
- `OFFSET`은 앞에서 몇 개의 데이터를 건너뛸지 정하는 값이다.
- 예를 들어 `LIMIT 20 OFFSET 40`은 앞의 40개를 건너뛰고 20개의 데이터를 가져오라는 의미이다.
- API에서는 `offset`과 `limit`을 Query String으로 받아 서버가 DB 조회 조건으로 사용할 수 있다.
- 이때 클라이언트가 전달한 값은 숫자인지 검증해야 하며, SQL Injection을 막기 위해 문자열 보간 대신 파라미터 바인딩을 사용하는 것이 안전하다.

#### 주제 11: Offset-based Pagination
- Offset-based Pagination은 클라이언트가 요청한 페이지 번호를 서버가 offset 값으로 변환해 데이터를 조회하는 방식이다.
- 예를 들어 `page=2&size=20`이면 서버는 `(page - 1) * size` 공식을 사용해 offset을 계산할 수 있다.
- 클라이언트 관점에서는 Page-based 방식이고, 데이터베이스 관점에서는 Offset-based 방식으로 볼 수 있다.
- 구현이 쉽고 특정 페이지로 바로 이동할 수 있다는 장점이 있다.
- 하지만 뒤 페이지로 갈수록 DB가 앞의 데이터를 많이 읽고 버려야 하므로 성능이 떨어진다.
- 예를 들어 `LIMIT 20 OFFSET 400`이면 DB는 앞의 400개를 건너뛰기 위해 많은 데이터를 확인한 뒤 20개만 반환한다.
- 또한 페이징 도중 데이터가 추가되거나 삭제되면 같은 데이터를 다시 보거나 일부 데이터가 누락되는 Data Drift 문제가 발생할 수 있다.

#### 주제 12: Keyset-based와 Cursor-based Pagination
- Keyset-based Pagination은 마지막으로 읽은 데이터의 식별자를 기준으로 다음 데이터를 조회하는 방식이다.
- 예를 들어 최신순 게시글 목록에서 마지막으로 본 게시글의 `id`를 기준으로 `WHERE id < last_seen_id ORDER BY id DESC LIMIT 20`과 같이 조회할 수 있다.
- DB는 인덱스를 이용해 기준 위치로 이동한 뒤 필요한 개수만 읽으면 되므로 깊은 페이지에서도 성능이 비교적 일정하다.
- 다만 특정 페이지 번호로 바로 이동하기 어렵고, 주로 다음/이전 탐색에 적합하다.
- 정렬 기준이 되는 컬럼이 중복될 수 있다면 `created_at DESC, id DESC`처럼 Tie-breaker를 함께 사용해 결정적 정렬을 보장해야 한다.
- Keyset-based는 DB 관점의 SQL 최적화 기법이다.
- Cursor-based는 API 관점의 인터페이스 패턴이다.
- 클라이언트는 마지막으로 본 위치를 나타내는 Cursor를 서버에 전달하고, 서버는 그 Cursor를 바탕으로 Keyset 조건을 만들어 다음 데이터를 조회한다.
- 이때 웹 API의 Cursor-based Pagination은 DB의 Stateful Cursor와는 다른 개념이다.

#### 주제 13: Token-based Pagination
- Token-based Pagination은 Cursor 정보를 그대로 노출하지 않고 토큰 형태로 감싸 클라이언트에게 전달하는 방식이다.
- 서버는 마지막 데이터의 정렬 기준 값이나 식별자를 Base64 등으로 인코딩해 `nextToken`으로 내려줄 수 있다.
- 클라이언트는 DB 정렬 기준이나 내부 페이징 로직을 알 필요 없이, 받은 토큰을 다음 요청에 그대로 포함하면 된다.
- 백엔드의 DB 스키마나 정렬 조건이 바뀌어도 API 토큰 형식만 유지하면 클라이언트 변경을 줄일 수 있다.

#### 주제 14: 무한 스크롤
- 무한 스크롤은 사용자가 페이지 끝에 도달할 때마다 새로운 콘텐츠를 자동으로 불러와 이어서 보여주는 UI/UX 패턴이다.
- 처음부터 모든 콘텐츠를 불러오지 않고 필요한 데이터만 그때그때 가져오기 때문에 초기 로딩 속도를 개선할 수 있다.
- 사용자가 스크롤을 내릴 때 끝에 도달했는지 감지하고, 도달하면 서버에 다음 데이터 요청을 보낸다.
- 일반적으로 스크롤 이벤트 리스너나 Intersection Observer를 사용해 구현할 수 있다.
- 사용자가 빠르게 스크롤해도 콘텐츠가 자연스럽게 로딩되도록 중복 요청 방지, 로딩 상태 표시, 다음 데이터 존재 여부 처리가 중요하다.
- 무한 스크롤은 Cursor-based 또는 Token-based Pagination과 잘 어울린다.
