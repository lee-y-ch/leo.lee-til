# TIL

## 날짜: 2026-05-20
## 소제목: OOP, SOLID, JVM의 핵심 개념 이해

### 새로 배운 내용

#### 주제 1: OOP란 무엇인가
- OOP(Object-Oriented Programming)는 현실 세계의 객체 개념을 바탕으로 데이터와 기능을 하나의 단위로 묶어 프로그램을 설계하는 패러다임이다.
- 객체는 단순히 데이터를 담는 상자가 아니라, 자신의 역할과 책임을 가진 주체이다.
- OOP스럽게 개발한다는 것은 무조건 객체를 많이 만들거나 상속을 사용하는 것이 아니라, 각 객체가 어떤 일을 책임져야 하는지 기준을 세워 설계하는 것이다.
- OOP는 항상 정답처럼 강제되는 방식은 아니며, 복잡도가 커지는 만큼 유지보수성과 확장성이 필요한 상황에서 특히 중요해진다.

#### 주제 2: OOP를 사용하지 않으면 생기는 문제
- OOP를 사용하지 않는 코드는 보통 절차지향적으로 작성된다.
- 절차지향 코드는 프로그램이 처리되는 순서에 따라 흐름을 작성하기 때문에, 작은 규모에서는 이해하기 쉽다.
- 하지만 서비스 규모가 커지면 기능이 추가될 때마다 기존 흐름을 계속 수정해야 하고, 코드 간 결합도가 높아져 유지보수가 어려워질 수 있다.
- 결국 중요한 것은 처리 순서가 아니라, 누가 어떤 일을 책임질 것인지 나누는 것이다.

#### 주제 3: OOP의 핵심 관점
- OOP는 "누가 이 일을 책임질 것인가?"라는 기준으로 코드를 나누는 프로그래밍 기법이다.
- 프로그램을 단순한 처리 순서가 아니라 역할과 책임을 가진 객체들의 협력으로 바라본다.
- 예를 들어 커피 객체를 상속받은 아이스 아메리카노를 단순히 온도만 다른 데이터로 생각하면 객체를 제대로 이해한 것이 아니다.
- 객체는 값의 묶음이 아니라, 자신의 역할을 수행하고 책임을 지는 단위로 이해해야 한다.
- Spring Boot에서도 OOP의 책임 분리는 잘 드러난다.
- `Controller`는 요청 흐름을 책임진다.
- `Service`는 비즈니스 로직을 책임진다.
- `Repository`는 데이터 접근을 책임진다.
- OOP는 대규모 서비스를 안정적으로 유지보수하기 위한 중요한 설계 방식이며, Spring과 Spring Boot는 이러한 객체지향 설계를 잘 지킬 수 있도록 도와준다.

#### 주제 4: SOLID란 무엇인가
- SOLID는 유지보수성과 확장성을 높이기 위해 만들어진 객체지향 설계의 다섯 가지 핵심 원칙이다.
- `S`는 SRP(Single Responsibility Principle, 단일 책임 원칙)를 의미한다.
- `O`는 OCP(Open Closed Principle, 개방 폐쇄 원칙)를 의미한다.
- `L`은 LSP(Liskov Substitution Principle, 리스코프 치환 원칙)를 의미한다.
- `I`는 ISP(Interface Segregation Principle, 인터페이스 분리 원칙)를 의미한다.
- `D`는 DIP(Dependency Inversion Principle, 의존관계 역전 원칙)를 의미한다.
- 오늘은 이 중 SRP, OCP, DIP를 중심으로 학습했다.

#### 주제 5: SRP(Single Responsibility Principle)
- SRP는 하나의 클래스가 하나의 책임만 가져야 한다는 원칙이다.
- 더 정확히는 클래스가 변경되는 이유가 한 가지여야 한다는 의미이다.
- 어떤 클래스를 만들었을 때 "이 클래스는 몇 가지 이유로 수정될 수 있는가?"라고 질문해볼 수 있다.
- 좋은 설계에서는 하나의 클래스가 한 가지 이유로만 수정되어야 한다.
- 책임이 섞이면 기능 하나를 수정했을 때 예상하지 못한 다른 기능까지 영향을 받을 수 있다.

#### 주제 6: OCP(Open Closed Principle)
- OCP는 소프트웨어의 기능 확장에는 열려 있고, 기존 코드 변경에는 닫혀 있어야 한다는 원칙이다.
- 새로운 기능을 추가하거나 확장할 수 있어야 하지만, 이미 잘 동작하고 있는 기존 코드는 가능한 한 수정하지 않아야 한다.
- 즉, 새 기능을 넣을 때 기존 코드를 직접 건드리는 방식보다 확장 지점을 만들어 추가하는 방식이 더 안정적이다.
- `Open`은 새로운 기능 추가와 확장에 열려 있다는 뜻이다.
- `Closed`는 기능 추가로 인해 기존 코드가 수정되는 것에는 닫혀 있어야 한다는 뜻이다.

#### 주제 7: DIP(Dependency Inversion Principle)
- DIP는 상위 모듈이 하위 모듈의 구체적인 구현에 직접 의존하지 않고, 양쪽 모두 추상화에 의존해야 한다는 원칙이다.
- 상위 모듈은 정책이나 핵심 흐름을 결정하는 코드이고, 하위 모듈은 세부 구현을 담당하는 코드이다.
- 예를 들어 파일 저장 기능을 만들 때, 상위 로직이 `LocalFileStorage` 같은 구체 클래스에 직접 의존하면 저장 방식이 바뀔 때 기존 코드 수정이 필요하다.
- 대신 `FileStorage`처럼 "파일을 저장한다"라는 역할을 인터페이스로 정의하고, 로컬 저장소와 클라우드 저장소를 각각 구현체로 만들 수 있다.
- 이렇게 하면 파일 저장 방식이 바뀌어도 상위 로직은 인터페이스만 바라보면 되므로 OCP와 DIP를 함께 지킬 수 있다.

#### 주제 8: JVM(Java Virtual Machine)
- JVM은 Java Virtual Machine의 약자로, 자바 바이트코드를 각 운영체제에 맞게 실행해주는 가상 머신이다.
- 기계어는 운영체제와 CPU 구조에 종속되기 때문에, 같은 소스 코드를 모든 환경에서 그대로 실행하기 어렵다.
- 자바는 이 문제를 해결하기 위해 소스 코드를 바로 기계어로 바꾸지 않고, 중간 형태인 바이트코드로 컴파일한다.
- 실행 흐름은 `Java 코드 -> javac 컴파일러 -> class 파일(바이트코드) -> JVM -> OS에 맞는 기계어 실행` 순서로 볼 수 있다.
- JVM 덕분에 자바는 한 번 작성한 코드를 다양한 환경에서 실행할 수 있다.

#### 주제 9: Class Loader
- Class Loader는 `.class` 파일의 바이트코드를 JVM 메모리 영역으로 로드하는 역할을 한다.
- 클래스 파일을 메서드 영역에 올리는 과정을 클래스 로딩 과정이라고 한다.
- 클래스 로딩 과정은 크게 `Loading`, `Linking`, `Initialization`으로 나눌 수 있다.
- `Loading`은 클래스 파일을 JVM 메모리에 로드하는 단계이다.
- `Linking`은 클래스 파일을 실제로 사용할 수 있도록 검증하고 준비하는 단계이다.
- Linking 내부에는 `Verifying`, `Preparing`, `Resolving` 과정이 있다.
- `Verifying`은 읽어들인 클래스가 JVM 명세에 맞는지 확인한다.
- `Preparing`은 클래스가 필요로 하는 메모리를 할당한다.
- `Resolving`은 클래스 상수 풀의 심볼릭 레퍼런스를 다이렉트 레퍼런스로 변경한다.
- `Initialization`은 static 필드 같은 클래스 변수를 실제 설정된 값으로 초기화하는 단계이다.

#### 주제 10: 바이트코드와 Constant Pool
- 자바 소스 코드는 `javac` 컴파일러를 거쳐 `.class` 파일이 된다.
- `.class` 파일은 JVM이 해석할 수 있는 바이트코드로 구성되어 있다.
- Constant Pool은 바이트코드 내부에 있는 테이블 형태의 저장 공간이다.
- 클래스 이름, 메서드 이름, 필드 정보, 문자열, 메서드 시그니처 같은 메타데이터가 Constant Pool에 저장된다.
- 바이트코드에서 보이는 `#숫자` 형태의 값은 Constant Pool의 인덱스를 가리킨다.
- 실행 중 필요한 이름과 참조 정보를 문자열 그대로 반복해서 저장하는 대신, 인덱스를 통해 관리한다.

#### 주제 11: 기본 생성자와 바이트코드
- 자바에서 생성자를 직접 작성하지 않으면 `javac` 컴파일러가 기본 생성자를 자동으로 생성한다.
- 기본 생성자의 바이트코드에서는 현재 객체인 `this`를 스택에 올리고, 부모 클래스인 `Object`의 생성자를 호출한 뒤 종료한다.
- 예를 들어 `aload_0`은 현재 객체를 스택에 올리는 명령어이다.
- `invokespecial`은 상위 클래스 생성자처럼 특별한 메서드를 호출할 때 사용된다.
- `return`은 메서드 실행을 종료한다.

#### 주제 12: Execution Engine
- Execution Engine은 Class Loader를 통해 Runtime Data Area에 배치된 바이트코드를 읽고 실행하는 역할을 한다.
- JVM은 바이트코드를 한 줄씩 해석해 실행할 수 있는데, 이 역할을 인터프리터가 수행한다.
- 자바는 소스 코드를 `javac`로 바이트코드로 컴파일하고, 실행 시점에는 JVM이 바이트코드를 해석하거나 기계어로 바꾸어 실행한다.
- 그래서 자바는 컴파일 방식과 인터프리터 방식을 함께 사용하는 하이브리드 언어라고 볼 수 있다.
- JIT(Just-In-Time) 컴파일러는 자주 실행되는 바이트코드를 감지해 기계어로 컴파일하고 캐싱하여 성능을 높인다.
- 인터프리터가 매번 같은 명령어를 해석하는 비용을 줄이기 위해, 자주 쓰이는 코드 경로를 최적화하는 역할을 한다.

#### 주제 13: Runtime Data Area
- Runtime Data Area는 JVM이 자바 애플리케이션을 실행할 때 운영체제로부터 할당받아 사용하는 메모리 영역이다.
- 프로그램 실행 중 발생하는 클래스 정보, 객체 인스턴스, 메서드 호출 상태, 지역 변수 등의 데이터를 관리한다.
- 주요 영역으로 Method Area, Heap Area, JVM Stack, PC Register, Native Method Stack이 있다.
- Method Area는 JVM이 실행될 때 생성되는 공간으로, 클래스가 메모리에 올라올 때 초기화되는 정보들이 저장된다.
- Method Area에는 필드 정보, 메서드 정보, 타입 정보 등이 저장되며, JVM이 동작하는 동안 유지된다.
- Heap Area는 객체 인스턴스가 저장되는 영역이다.
- JVM Stack은 메서드 호출마다 생성되는 스택 프레임을 관리하며, 지역 변수와 메서드 실행 상태를 저장한다.
- PC Register는 각 스레드가 현재 실행 중인 JVM 명령어 주소를 저장하는 공간이다.
- Native Method Stack은 자바 코드가 아닌 C, C++, 어셈블리 등으로 작성된 네이티브 메서드를 실행할 때 사용하는 스택 메모리이다.

#### 주제 14: JVM이 하는 일 정리
- JVM은 바이트코드를 해석하고 실행한다.
- JVM은 프로그램 실행에 필요한 메모리를 관리한다.
- Class Loader는 바이트코드를 가져와 Method Area에 올린다.
- Execution Engine의 인터프리터는 바이트코드를 하나씩 읽고 해석한다.
- JIT 컴파일러는 자주 사용되는 명령어를 최적화하고 캐싱하여 실행 성능을 높인다.
