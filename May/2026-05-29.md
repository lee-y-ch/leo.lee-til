## 소제목: 데이터베이스 동시성 제어와 OAuth 이해

### 새로 배운 내용

#### 주제 1: 데이터베이스 동시성 제어
- 트랜잭션은 더 이상 나눌 수 없는 논리적인 일의 단위이다.
- 여러 트랜잭션이 동시에 실행되면 같은 데이터에 접근하거나 수정하는 상황이 발생할 수 있다.
- 데이터베이스 동시성 제어는 여러 트랜잭션이 동시에 실행될 때 데이터의 일관성과 무결성을 지키기 위한 방법이다.
- 동시성을 높이면 처리량은 좋아지지만 일관성 문제가 생길 수 있다.
- 일관성을 강하게 보장하면 안정성은 높아지지만 동시에 처리할 수 있는 작업 수가 줄어들 수 있다.
- 따라서 DB나 데이터의 특성에 맞춰 일관성이 중요한지, 동시성이 중요한지 판단해야 한다.

#### 주제 2: Serial Schedule과 Non-Serial Schedule
- Serial Schedule은 트랜잭션이 서로 겹치지 않고 한 번에 하나씩 순차적으로 실행되는 스케줄이다.
- Serial Schedule은 트랜잭션을 순서대로 처리하기 때문에 일관성을 보장하기 쉽다.
- 하지만 한 번에 하나의 트랜잭션만 처리하므로 동시성이 낮다.
- Non-Serial Schedule은 여러 트랜잭션의 작업이 서로 섞여 실행되는 스케줄이다.
- Non-Serial Schedule은 동시성이 높아 처리량을 늘릴 수 있다.
- 하지만 작업 순서에 따라 일관성 문제가 발생할 수 있으므로 적절한 동시성 제어가 필요하다.
- 데이터베이스는 가능하면 Non-Serial하게 실행하면서도 결과는 Serial하게 실행한 것과 같도록 만드는 방향을 추구한다.

#### 주제 3: Conflict
- Conflict는 여러 트랜잭션이 동시에 실행될 때 충돌이 발생할 수 있는 연산 관계를 의미한다.
- Conflict가 발생하려면 세 가지 조건을 모두 만족해야 한다.
- 첫째, 서로 다른 트랜잭션에 속한 연산이어야 한다.
- 둘째, 같은 데이터에 접근해야 한다.
- 셋째, 최소 하나의 연산이 Write여야 한다.
- 예를 들어 두 트랜잭션이 같은 계좌 잔액을 수정한다면 Conflict가 발생할 수 있다.
- 반대로 한 트랜잭션은 잔액을 수정하고 다른 트랜잭션은 별명을 수정한다면 서로 다른 데이터에 접근하므로 Conflict로 보지 않을 수 있다.
- Conflict를 적절히 제어하면 Non-Serial Schedule에서도 Serial Schedule과 같은 결과를 만들 수 있다.

#### 주제 4: 직렬화 가능성
- 직렬화 가능성은 여러 트랜잭션이 섞여 실행되더라도 결과가 어떤 Serial Schedule과 동일한지를 판단하는 기준이다.
- 트랜잭션을 무조건 하나씩 실행하면 안전하지만 성능이 낮아진다.
- 반대로 무작정 동시에 실행하면 데이터 일관성이 깨질 수 있다.
- 직렬화 가능성은 동시성과 일관성 사이에서 안전한 실행 순서를 판단하기 위한 개념이다.
- Conflict가 있는 연산의 순서를 잘 제어하면 동시에 실행하면서도 결과적으로는 순차 실행과 같은 효과를 낼 수 있다.

#### 주제 5: 락킹
- 락킹은 특정 데이터에 대한 접근을 제어해 동시성 문제를 막는 방법이다.
- 트랜잭션이 데이터를 읽거나 쓰는 동안 다른 트랜잭션의 접근을 제한할 수 있다.
- 락은 행 단위, 컬럼에 가까운 논리 단위, 페이지 단위, 테이블 단위 등 다양한 범위로 적용될 수 있다.
- 일반적인 RDBMS에서는 행 단위 락을 많이 사용한다.
- 테이블 전체 락은 `ALTER TABLE` 같은 DDL 작업이나 조건 없이 대량 변경을 수행하는 작업에서 발생할 수 있다.
- 락 범위가 넓을수록 안전성은 높아질 수 있지만 동시성은 낮아진다.

#### 주제 6: 비관적 락
- 비관적 락(Pessimistic Lock)은 충돌이 일어날 가능성이 높다고 가정하는 방식이다.
- 데이터를 사용하기 전에 먼저 락을 걸어 다른 트랜잭션의 접근이나 수정을 제어한다.
- 일반적으로 RDBMS에서 많이 사용된다.
- 예를 들어 계좌 잔액처럼 동시에 수정되면 안 되는 중요한 데이터에 비관적 락을 적용할 수 있다.
- 비관적 락의 장점은 높은 무결성과 신뢰성을 제공한다는 점이다.
- 충돌을 사전에 막기 때문에 데이터 손상 가능성을 줄일 수 있다.
- 단점은 락을 기다리는 시간이 생기고, 성능 저하나 병목이 발생할 수 있다는 점이다.
- 여러 트랜잭션이 서로의 락을 기다리면 데드락이 발생할 수 있다.

#### 주제 7: 낙관적 락
- 낙관적 락(Optimistic Lock)은 충돌이 자주 발생하지 않을 것이라고 가정하는 방식이다.
- 데이터를 읽을 때는 락을 걸지 않고 작업을 진행한다.
- 업데이트 직전에 데이터의 버전이 처음 읽었을 때와 같은지 확인한다.
- 버전이 같으면 다른 트랜잭션이 중간에 수정하지 않았다고 판단하고 업데이트한다.
- 버전이 달라졌다면 충돌이 발생한 것으로 보고 롤백하거나 재시도한다.
- 낙관적 락은 읽기 성능과 동시성이 높다는 장점이 있다.
- 분산 시스템처럼 락을 오래 유지하기 어려운 환경에서도 유용하다.
- 단점은 충돌이 발생했을 때 예외 처리와 재시도 로직이 필요하다는 점이다.
- 충돌이 자주 발생하는 데이터에서는 재시도 비용이 커져 오히려 성능이 떨어질 수 있다.

#### 주제 8: 낙관적 락의 버전 체크
- 낙관적 락에서 버전을 읽고 쓰는 과정도 동시성 문제가 생길 수 있어 보인다.
- 일반적으로는 버전 컬럼 자체에 별도의 비관적 락을 직접 거는 방식이 아니라, DB의 원자적 업데이트를 이용한다.
- 예를 들어 다음과 같은 방식으로 업데이트한다.

```sql
UPDATE account
SET balance = balance - 1000,
    version = version + 1
WHERE id = 1
  AND version = 3;
```

- 이 쿼리는 `id = 1`이고 `version = 3`인 경우에만 업데이트된다.
- DB는 이 UPDATE를 하나의 원자적 연산으로 처리한다.
- 동시에 다른 트랜잭션이 먼저 같은 row의 version을 바꾸면, 나중에 실행된 UPDATE는 영향 받은 행 수가 0이 된다.
- 애플리케이션은 영향 받은 행 수가 0인지 확인해 충돌을 감지하고, 예외 처리나 재시도를 수행한다.
- 즉, 낙관적 락은 버전 체크와 업데이트를 분리해서 처리하는 것이 아니라 하나의 UPDATE 조건으로 묶어 처리하는 것이 핵심이다.

#### 주제 9: 비관적 락과 낙관적 락 선택 기준
- 비관적 락은 충돌이 자주 발생하고 데이터 무결성이 매우 중요한 경우에 적합하다.
- 예를 들어 재고 차감, 계좌 이체, 좌석 예매처럼 동시에 수정되면 문제가 큰 데이터에 사용할 수 있다.
- 낙관적 락은 충돌이 드물고 읽기 요청이 많은 경우에 적합하다.
- 예를 들어 사용자 프로필 수정, 게시글 수정처럼 충돌 가능성이 낮은 데이터에 사용할 수 있다.
- 비관적 락은 충돌을 사전에 막는 방식이고, 낙관적 락은 충돌을 사후에 감지하는 방식이다.
- 어떤 락이 무조건 좋은 것이 아니라 데이터 특성, 트래픽 패턴, 충돌 빈도, 사용자 경험을 기준으로 선택해야 한다.

#### 주제 10: OAuth가 등장한 배경
- OAuth는 사용자의 비밀번호를 제3자 서비스에 직접 넘기지 않고도, 특정 권한을 위임할 수 있게 하는 표준 프로토콜이다.
- 예를 들어 어떤 서비스가 사용자의 구글 프로필 정보나 깃허브 저장소 정보에 접근해야 할 때, 사용자의 구글 또는 깃허브 비밀번호를 직접 받아서는 안 된다.
- OAuth는 사용자가 신뢰하는 Authorization Server에서 인증을 수행하고, Client에게 필요한 범위의 접근 권한만 위임하도록 만든다.
- 핵심은 사용자 인증과 권한 위임을 분리하는 것이다.
- OAuth 자체는 주로 인가와 권한 위임을 위한 프로토콜이며, 로그인 인증 용도로 사용할 때는 OpenID Connect 같은 확장이 함께 사용될 수 있다.

#### 주제 11: OAuth의 주요 역할
- Resource Owner는 자원의 소유자이다.
- 보통 서비스를 사용하는 사용자 본인을 의미한다.
- Client는 Resource Owner의 권한을 위임받아 Resource Server에 접근하려는 애플리케이션이다.
- Authorization Server는 사용자를 인증하고 Client에게 권한을 부여하는 서버이다.
- Resource Server는 실제 보호된 자원을 가지고 있는 서버이다.
- Access Token은 Client가 Resource Server에 접근할 때 사용하는 토큰이다.
- Client는 사용자의 비밀번호를 직접 보관하지 않고, Authorization Server가 발급한 토큰을 사용해 필요한 자원에 접근한다.

#### 주제 12: OAuth Authorization Code 흐름
- Authorization Code 흐름은 OAuth에서 많이 사용되는 인가 흐름이다.
- 먼저 Client는 사용자를 Authorization Server의 로그인 및 동의 화면으로 리다이렉트한다.
- Resource Owner는 Authorization Server에서 로그인하고, Client가 요청한 권한 범위에 동의한다.
- Authorization Server는 Authorization Code를 발급하고, 사용자의 브라우저를 Client의 Redirect URI로 다시 보낸다.
- 이때 Authorization Code가 브라우저를 통해 Client에게 전달된다.
- Client는 받은 Authorization Code를 Authorization Server에 전달하고, Access Token을 발급받는다.
- 이후 Client는 Access Token을 사용해 Resource Server의 보호된 자원에 접근한다.

#### 주제 13: Authorization Code가 브라우저에 전달되는 이유
- Authorization Code가 브라우저를 통해 Client에게 전달되는 이유는 OAuth 흐름에서 Resource Owner가 Authorization Server와 브라우저 기반으로 상호작용하기 때문이다.
- 사용자는 Authorization Server에서 로그인과 권한 동의를 수행한다.
- HTTP는 Stateless하므로 Client는 Authorization Server에서 사용자가 어떤 과정을 거쳤는지 직접 알 수 없다.
- 따라서 Authorization Server는 사용자의 브라우저를 Client의 Redirect URI로 돌려보내면서 Authorization Code를 함께 전달한다.
- Client는 이 Authorization Code를 증거로 사용해 Authorization Server에 토큰 발급을 요청한다.
- Authorization Code 자체는 최종 접근 권한이 아니라 Access Token을 받기 위한 임시 코드이다.

#### 주제 14: OAuth가 해결하는 문제
- OAuth가 해결하려는 핵심 문제는 사용자의 비밀번호를 Client에게 직접 넘기지 않고도 권한을 위임하는 것이다.
- 사용자는 Authorization Server에서만 인증하고, Client는 사용자의 실제 비밀번호를 알 필요가 없다.
- Client는 필요한 범위의 권한만 Access Token으로 위임받는다.
- 이 구조를 통해 인증 주체와 권한을 사용하는 애플리케이션을 분리할 수 있다.
- 또한 권한 범위를 제한하거나 토큰을 만료시키는 방식으로 더 안전하게 외부 서비스 접근을 제어할 수 있다.
