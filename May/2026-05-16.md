### 새로 배운 내용
#### 주제 1: 추상 클래스(Abstract Class)와 상속 설계
- abstract 클래스는 직접 인스턴스를 생성할 수 없어, 구체적인 타입 없이 객체를 만드는 실수를 컴파일 타임에 방지할 수 있다
- abstract 메서드는 자식 클래스에서 반드시 구현하도록 강제한다
- 중간 계층 추상 클래스(Standard, Special)도 abstract 메서드를 구현할 수 있으며, 이 경우 하위 클래스들이 공통 로직을 상속받아 중복을 줄일 수 있다
- Interface와의 차이: abstract 클래스는 인스턴스 필드와 생성자를 가질 수 있지만, Interface는 인스턴스 필드와 생성자를 가질 수 없다 (Java 8부터 default 메서드는 가능)

#### 주제 2: 접근 제어자와 final의 활용
- protected: 자식 클래스에서는 접근 가능하지만 외부에서는 접근 불가. 내부 로직(calculateFee)을 감추고 public 메서드(getFinalFee)를 통해서만 접근하도록 설계할 때 사용
- final 메서드: 자식 클래스가 override할 수 없도록 고정. private(외부 접근 불가)이나 static(객체 필드 접근 불가)으로는 같은 효과를 낼 수 없어 final을 선택함

#### 주제 3: super()와 super.method() 활용
- 자식 클래스 생성자에서 super()로 부모 생성자를 먼저 호출하면, 부모 필드의 초기화 책임이 부모 클래스에 남아 초기화 로직이 우회되지 않는다
- 메서드 override 시 super.printLabel()을 호출하면 부모의 출력 로직을 재사용하면서 자식의 고유 정보를 덧붙일 수 있다

#### 주제 4: 부동소수점 문제와 형변환
- double 타입은 10진수를 2진수로 표현하는 과정에서 근사값이 저장되어 `2.1 * 500 = 1050.0000000000002` 같은 오차가 발생할 수 있다
- 요금처럼 정수 단위가 필요한 값은 long 타입을 사용해 오차를 방지한다
- `(long)` 캐스트는 소수점을 버림(truncate)하므로, 더 정밀한 처리가 필요하면 `Math.round()`를 사용해야 한다

- Standard 클래스의 존재 이유 불명확: 초기에 Standard 클래스에 필드가 없어 "굳이 왜 있어야 하냐"는 의문이 생겼다. 실제 우체국의 무게 제한 규칙을 반영해 maxWeight 필드와 isOverWeight() 메서드를 추가함으로써 존재 의의를 확보했다
- printLabel() override 위치 결정: isOverWeight()가 Standard에 정의되어 있으므로 관련 출력 로직도 Standard에 두는 것이 자연스럽다고 판단했다. 덕분에 Document와 NormalBox는 별도 override 없이 경고 출력을 상속받을 수 있다
