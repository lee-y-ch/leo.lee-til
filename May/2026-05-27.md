# TIL

## 날짜: 2026-05-28
## 소제목: HTTP 인증 헤더, JWT, 토큰 재발급, 레이어드 아키텍처 이해

### 새로 배운 내용

#### 주제 1: HTTP 자격 증명 헤더
- HTTP 자격 증명 헤더는 클라이언트와 서버 간 인증 과정에서 사용자의 자격을 확인하기 위해 사용되는 헤더이다.
- HTTP는 Stateless한 특성을 가지므로, 서버는 기본적으로 이전 요청의 인증 상태를 기억하지 않는다.
- 따라서 인증이 필요한 API나 자원에 접근할 때는 요청마다 인증 정보를 함께 보내야 한다.
- 이때 인증 정보는 주로 HTTP Header를 통해 전달된다.

#### 주제 2: WWW-Authenticate와 Authorization
- `WWW-Authenticate`는 서버가 클라이언트에게 인증이 필요하다고 알려줄 때 사용하는 Response Header이다.
- 클라이언트가 보호된 자원에 인증 없이 접근하면 서버는 보통 `401 Unauthorized` 응답과 함께 `WWW-Authenticate` 헤더를 내려준다.
- 이 헤더에는 서버가 요구하는 인증 방식과 인증 영역 정보가 포함될 수 있다.
- `Authorization`은 클라이언트가 서버에 요청을 보낼 때 인증 정보를 담는 Request Header이다.
- 클라이언트는 `Authorization` 헤더에 Basic, Digest, Bearer Token 같은 인증 정보를 담아 서버에 전달한다.

#### 주제 3: Basic Authentication
- Basic Authentication은 가장 단순한 HTTP 인증 방식이다.
- 아이디와 비밀번호를 `아이디:비밀번호` 형태로 합친 뒤 Base64로 인코딩하여 `Authorization` 헤더에 담아 보낸다.
- 예시는 다음과 같다.

```http
Authorization: Basic Aszxqerasdf=
```

- Base64는 암호화가 아니라 인코딩이므로 누구나 디코딩할 수 있다.
- 따라서 Basic Authentication은 반드시 HTTPS/TLS처럼 암호화된 통신 위에서만 사용해야 한다.
- 서버는 요청마다 전달된 아이디와 비밀번호를 확인해야 하므로 DB 조회와 검증 비용이 발생한다.
- 구현이 간단하기 때문에 토이 프로젝트나 내부 API 호출처럼 제한된 환경에서 사용할 수 있다.

#### 주제 4: Digest Authentication
- Digest Authentication은 Basic Authentication의 보안 취약점을 보완하기 위해 나온 방식이다.
- 비밀번호를 그대로 보내지 않고, 서버가 제공한 값과 비밀번호를 조합해 해시 값을 만든 뒤 전송한다.
- `Nonce`는 서버가 클라이언트에게 한 번 사용하라고 주는 일회성 난수이다.
- `Realm`은 서버가 관리하는 보안 영역의 이름이다.
- Digest Authentication의 흐름은 다음과 같다.
- 클라이언트가 보호된 리소스를 요청한다.
- 서버는 `401 Unauthorized` 응답과 함께 `Nonce`, `Realm` 등을 전달한다.
- 클라이언트는 비밀번호, Nonce, Realm 등을 조합해 해시 값을 만들고, 이를 `Authorization` 헤더에 담아 보낸다.
- 서버는 같은 방식으로 해시 값을 계산해 클라이언트가 보낸 값과 비교한다.
- Basic보다 비밀번호 노출 위험은 줄어들지만, 요청마다 Nonce 발급, 검증, 해시 계산이 필요하므로 서버 부담은 여전히 존재한다.

#### 주제 5: Bearer Token
- Bearer Token 방식은 토큰을 소지한 요청을 인증된 요청으로 보는 방식이다.
- 예시는 다음과 같다.

```http
Authorization: Bearer mF_9.B5f-4.1JqM
```

- Basic과 Digest는 요청마다 사용자 자격 정보를 직접 검증해야 하는 부담이 있다.
- Bearer Token 방식에서는 최초 로그인 시에만 아이디와 비밀번호를 확인하고, 이후에는 서버가 발급한 토큰을 이용해 인증과 인가를 처리한다.
- 토큰은 무기명 티켓처럼 동작한다.
- 토큰을 가진 클라이언트는 인증된 사용자처럼 요청할 수 있기 때문에, 토큰 관리가 매우 중요하다.
- Bearer Token 방식은 브라우저뿐 아니라 모바일 앱, 다른 도메인의 클라이언트, 외부 API 호출에서도 범용적으로 사용할 수 있다.

#### 주제 6: Bearer Token의 장점과 단점
- Bearer Token의 장점은 사용자의 실제 비밀번호를 매 요청마다 보내지 않아도 된다는 점이다.
- 최초 로그인 이후에는 토큰만 전송하므로 비밀번호 노출 위험이 줄어든다.
- Cookie 기반 세션 방식보다 다양한 클라이언트 환경에서 사용하기 쉽다.
- `Authorization` 헤더에 직접 넣어 보내는 방식은 쿠키 자동 전송으로 발생할 수 있는 CSRF 위험을 줄이는 데 도움이 된다.
- 단점은 토큰이 탈취되면 토큰을 가진 사람이 사용자인 것처럼 요청할 수 있다는 점이다.
- 따라서 HTTPS 사용은 기본이고, 토큰 유효기간을 짧게 설정하는 것이 일반적이다.
- 토큰 저장 위치도 중요하다.
- LocalStorage나 SessionStorage는 JavaScript로 접근할 수 있어 XSS 공격에 취약할 수 있다.
- Cookie는 자동으로 요청에 포함되기 때문에 CSRF 공격에 주의해야 한다.
- 결국 토큰 저장 방식은 XSS, CSRF, 사용자 경험, 구현 복잡도를 함께 고려해 선택해야 한다.

#### 주제 7: Opaque Token과 JWT
- Opaque Token은 토큰 값 자체에는 의미가 없는 무작위 문자열 토큰이다.
- 서버는 Opaque Token과 사용자 정보를 저장소에 보관하고, 요청이 올 때마다 토큰을 조회해 사용자를 확인한다.
- 이 방식은 토큰을 서버에서 쉽게 무효화할 수 있다는 장점이 있다.
- 하지만 사용자가 많아지면 토큰 저장소 조회 비용이 커질 수 있다.
- JWT는 토큰 자체에 사용자 정보와 만료 시간 같은 정보를 담고, 서명을 통해 위변조 여부를 확인할 수 있는 토큰 형식이다.
- Bearer Token은 토큰을 전달하는 인증 방식이고, JWT는 그 Bearer Token으로 사용할 수 있는 토큰 형식 중 하나이다.

#### 주제 8: JWT란 무엇인가
- JWT(JSON Web Token)는 당사자 간 정보를 JSON 객체 형태로 안전하고 가볍게 전달하기 위한 개방형 표준이다.
- JWT는 보통 `Header.Payload.Signature` 형태의 세 부분으로 구성된다.
- Header와 Payload는 Base64URL로 인코딩되어 있을 뿐 암호화된 것이 아니다.
- 따라서 누구나 디코딩해 내용을 확인할 수 있으므로 비밀번호, 주민번호 같은 민감한 정보는 절대 넣으면 안 된다.
- JWT의 안전성은 Payload를 숨기는 데서 나오는 것이 아니라, Signature를 통해 내용이 위변조되지 않았음을 검증하는 데서 나온다.

```text
eyJhbGciOiJIUzI1NiIsIn... . eyJzdWIiOiIxMjM0NTY3O... . SflKxwRJSMeKKF2QT4fwpMe...
      Header              .          Payload             .          Signature
```

#### 주제 9: JWT Header, Payload, Signature
- Header에는 토큰 타입과 서명 알고리즘 정보가 들어간다.

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

- Payload에는 토큰에 담고 싶은 클레임 정보가 들어간다.

```json
{
  "userId": 10,
  "email": "void@startupcode.kr",
  "username": "void",
  "role": "admin",
  "iat": 1609239023,
  "exp": 1609242623
}
```

- `iat`는 Issued At의 약자로 토큰 발행 시간을 의미한다.
- `exp`는 Expiration Time의 약자로 토큰 만료 시간을 의미한다.
- Signature는 인코딩된 Header와 Payload를 서버의 비밀키와 함께 알고리즘에 넣어 만든 값이다.
- 정확히는 `base64url(header) + "." + base64url(payload)`를 비밀키로 서명한 결과가 Signature가 된다.
- Header나 Payload의 값이 한 글자라도 바뀌면 서버가 다시 계산한 Signature와 토큰의 Signature가 달라지므로 위변조를 탐지할 수 있다.

#### 주제 10: JWT를 사용하는 이유
- JWT를 사용하면 서버가 세션 저장소를 조회하지 않고도 토큰 자체만 검증해 인증과 인가에 필요한 정보를 확인할 수 있다.
- 서버는 JWT를 Base64URL 디코딩해 Payload를 읽고, Signature를 검증해 위변조 여부를 확인한다.
- DB나 Redis 같은 저장소 조회 없이 CPU 연산으로 검증할 수 있어 Stateless 구조와 잘 어울린다.
- 서버를 여러 대로 확장해도 같은 비밀키 또는 공개키 검증 체계를 공유하면 어느 서버에서든 JWT를 검증할 수 있다.
- 이 때문에 JWT는 확장성이 좋은 인증 방식으로 많이 사용된다.

#### 주제 11: JWT의 단점
- JWT는 한 번 발급되면 만료 전까지 서버가 직접 통제하기 어렵다.
- 클라이언트가 토큰을 가지고 있기 때문에, 토큰이 탈취되면 만료 전까지 악용될 수 있다.
- 이를 완화하기 위해 Access Token의 수명을 짧게 두고, Refresh Token으로 재발급하는 구조를 사용한다.
- JWT는 내부 정보가 많아질수록 길이가 길어진다.
- 매 API 요청마다 큰 토큰을 보내면 네트워크 대역폭이 낭비될 수 있다.
- 따라서 JWT Payload에는 꼭 필요한 정보만 담아야 한다.

#### 주제 12: Access Token과 Refresh Token
- Access Token은 실제 API 리소스에 접근하기 위한 토큰이다.
- Refresh Token은 Access Token을 새로 발급받기 위한 토큰이다.
- Access Token은 매 요청마다 전송되기 때문에 노출 위험이 크고, 보통 15분에서 30분처럼 짧은 수명을 가진다.
- Refresh Token은 Access Token이 만료되었을 때만 사용되며, 보통 2주에서 1달처럼 더 긴 수명을 가진다.
- Access Token을 너무 길게 설정하면 사용자 편의성은 좋아지지만 탈취 시 위험이 커진다.
- Access Token을 너무 짧게 설정하면 보안성은 좋아지지만 사용자가 자주 다시 로그인해야 하는 불편이 생긴다.
- Refresh Token은 이 보안성과 편의성의 균형을 맞추기 위해 사용된다.

#### 주제 13: Refresh Token Rotation
- Refresh Token이 탈취되면 공격자는 장기간 Access Token을 재발급받을 수 있다.
- Refresh Token Rotation(RTR)은 Refresh Token을 한 번 사용하면 폐기하고 새로운 Refresh Token을 발급하는 방식이다.
- 사용자가 Access Token 만료 후 기존 Refresh Token `R1`로 재발급을 요청하면 서버는 `R1`의 유효성을 확인한다.
- 서버는 `R1`을 폐기하고 새로운 Access Token `A2`와 Refresh Token `R2`를 발급한다.
- 이후 서버는 `R2`를 저장소에 저장한다.
- 만약 공격자가 탈취한 `R1`을 먼저 사용했다면, 나중에 정상 사용자가 `R1`을 사용할 때 서버는 이미 사용된 토큰의 재사용을 감지할 수 있다.
- 이때 서버는 해당 사용자 또는 토큰 패밀리의 Refresh Token을 모두 무효화해 피해를 줄일 수 있다.
- RTR은 Refresh Token 탈취를 완전히 막지는 못하지만, 재사용 탐지를 통해 공격을 발견하고 확산을 줄이는 데 도움을 준다.

#### 주제 14: Cookie, Authorization Header, Session, Token의 관계
- Cookie와 Authorization Header는 인증 정보를 전달하는 수단이다.
- Session과 Token은 인증 상태를 관리하는 방식이다.
- `Cookie + Session` 방식에서는 클라이언트가 Cookie 안의 `sessionId`를 보내고, 서버는 세션 저장소를 조회한다.
- `Authorization + Bearer Token` 방식에서는 클라이언트가 `Authorization: Bearer ...` 형태로 토큰을 보내고, 서버는 토큰 자체 또는 토큰 저장소를 확인한다.
- `Cookie + Token` 방식에서는 Cookie 안에 JWT나 Access Token을 담고, 서버는 토큰의 서명, 만료 시간, 권한 정보를 확인한다.
- 전송 수단과 인증 상태 관리 방식은 서로 다른 개념이므로 구분해서 이해해야 한다.

#### 주제 15: 레이어드 아키텍처
- 레이어드 아키텍처는 애플리케이션의 책임을 계층별로 분리하는 구조이다.
- 책임을 분리하면 코드 중복을 줄이고, 변경이 필요한 부분을 더 쉽게 찾을 수 있다.
- 일반적인 Spring 애플리케이션에서는 Controller, Service, Repository 같은 계층으로 나누어 관심사를 분리한다.
- Controller는 HTTP 요청과 응답 흐름을 담당한다.
- Service는 비즈니스 로직을 담당한다.
- Repository는 데이터베이스 접근을 담당한다.
- 핵심은 각 계층이 자신의 책임에 집중하도록 만드는 것이다.

#### 주제 16: Entity와 DTO
- 관계형 데이터베이스는 테이블과 관계를 중심으로 데이터를 다룬다.
- Java 애플리케이션은 객체를 중심으로 코드를 작성한다.
- 이 차이를 객체지향 코드에서 다루기 위해 RDB 테이블 구조와 규칙을 객체화한 것이 Entity이다.
- Entity는 DB 테이블과 매핑되는 도메인 또는 영속성 객체이다.
- Entity는 테이블 정의, 컬럼 매핑, 키 정의 등을 담당한다.

```java
@Entity
public class User {
    @Id
    private Long id;

    private String email;
    private String password;
    private String name;
}
```

- JPA는 Entity를 보고 `insert`, `update`, `select` 같은 SQL 처리를 수행한다.
- DTO(Data Transfer Object)는 계층 간 데이터 전달을 위해 사용하는 객체이다.
- DTO는 API 요청이나 응답에 필요한 데이터만 담을 수 있다.

```java
public record UserResponse(
    Long id,
    String email,
    String name
) {}
```

- 예를 들어 응답 DTO에서 `password`를 제외하면 민감한 정보를 응답하지 않도록 제어할 수 있다.
- 정리하면 Entity는 DB와 매핑되는 객체이고, DTO는 요청/응답 또는 계층 간 전달을 위한 객체이다.

#### 주제 17: 요청과 응답 흐름
- 요청 흐름은 보통 `Controller -> DTO -> Service -> Entity -> Repository -> DB` 순서로 이어진다.
- 클라이언트가 JSON 요청을 보내면 Spring은 요청 JSON의 필드 이름과 DTO의 필드, 생성자, 세터 등을 보고 객체로 매핑한다.
- Service 계층은 DTO를 바탕으로 Entity를 생성하거나 조회하고, 비즈니스 로직을 수행한다.
- Repository는 Entity를 기준으로 DB와 통신한다.
- 응답 흐름은 보통 `DB -> Entity -> Service -> DTO -> Controller -> JSON 응답` 순서로 이어진다.
- Entity를 그대로 응답하지 않고 DTO로 변환하면 API 응답 구조를 유연하게 관리할 수 있다.

#### 주제 18: DTO 검증
- DTO에는 요청 값 검증을 위한 어노테이션을 붙일 수 있다.
- 예를 들어 `@Email`, `@NotBlank` 등을 사용하면 컨트롤러 로직에 들어가기 전에 요청 값의 유효성을 검사할 수 있다.

```java
public record UserCreateRequest(
    @Email
    String email,

    @NotBlank
    String password,

    @NotBlank
    String name
) {}
```

```java
@PostMapping("/users")
public ResponseEntity<Void> createUser(
    @Valid @RequestBody UserCreateRequest request
) {
    userService.create(request);
    return ResponseEntity.ok().build();
}
```

- 이메일 형식이 아니거나 비밀번호가 비어 있으면 Controller 내부 로직까지 가지 않고 에러 응답을 줄 수 있다.

#### 주제 19: Mapper, 직렬화, 미들웨어
- Entity와 DTO는 역할이 다르기 때문에 서로 변환하는 과정이 필요하다.
- 이 변환 로직을 별도의 Mapper 또는 Helper 클래스로 분리하면 계층의 책임을 더 깔끔하게 유지할 수 있다.
- Repository에서 DTO 변환까지 수행하면 Repository가 DB 접근과 데이터 변환이라는 두 책임을 가지게 된다.
- 따라서 Repository는 DB 접근에 집중하고, DTO 변환은 Service나 Mapper 계층에서 처리하는 것이 더 적절하다.
- 직렬화는 객체를 JSON 같은 전송 가능한 형태로 바꾸는 것이다.
- 역직렬화는 JSON 같은 데이터를 객체로 바꾸는 것이다.
- 미들웨어는 요청과 응답 사이에서 공통 기능을 처리하는 계층이다.
- 인증, 로깅, 에러 처리, 요청 전처리 같은 공통 관심사를 미들웨어에서 처리할 수 있다.
