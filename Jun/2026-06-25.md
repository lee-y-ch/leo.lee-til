#### 주제 1: Lambd란 무엇인가
- Lambda는 서버를 직접 관리하지 않고 코드만 실행할 수 있는 서버리스 컴퓨팅 서비스이다.
- 특정 이벤트가 발생했을 때 함수 코드가 실행되고, 실행이 끝난 뒤 일정 시간이 지나면 실행 환경이 정리된다.
- EC2처럼 서버를 계속 켜두는 방식이 아니라, 코드가 실행되는 시간 중심으로 동작한다.
- 실행 시간만큼 비용을 지불하고, 코드 단위로 확장할 수 있다는 장점이 있다.

#### 주제 2: 서버리스란 무엇인가
- 서버리스는 서버가 없다는 뜻이 아니다.
- 서버가 사라진 것이 아니라 서버 운영의 상당 부분을 AWS가 책임지는 방식이다.
- EC2를 사용하면 인스턴스 생성, 운영체제 관리, 서버 실행, 패치, 용량 조절을 직접 고려해야 한다.
- Lambda를 사용하면 함수 코드 작성, 이벤트 트리거 연결, IAM 권한 설정에 집중하고 나머지 실행 환경 운영은 AWS가 담당한다.

```text
EC2 방식
-> 인스턴스 생성
-> 운영체제 관리
-> 서버 실행
-> 패치
-> 용량 조절

Lambda 방식
-> 함수 코드 작성
-> 이벤트 트리거 연결
-> IAM 권한 설정
-> AWS가 실행 환경 관리
```

#### 주제 3: EC2와 Lambda 비교

##### EC2
- EC2는 서버를 켜 두는 방식이다.
- 사용자가 요청하면 이미 켜져 있는 서버가 응답한다.
- 사용자 요청이 없어도 서버는 계속 켜져 있고, 보통 시간 단위로 비용이 발생한다.
- 서버가 이미 켜져 있으므로 바로 응답할 수 있다.
- 서버 내부 상태, 디스크, 파일을 상대적으로 관리하기 쉽다.
- 필요한 라이브러리를 자유롭게 설치하고 사용할 수 있다.
- 단점은 요청이 없어도 비용이 발생한다는 점이다.

##### Lambda
- Lambda는 지정한 이벤트가 발생할 때만 실행된다.
- 일정 시간이 지나면 실행 환경이 사라질 수 있다.
- 실행 시간만큼 과금되므로 요청이 거의 없는 작업에는 비용 효율적일 수 있다.
- 코드 단위로 자동 확장되는 장점이 있다.
- 다만 실행 환경 준비 시간이 발생할 수 있고, 장기간 실행되거나 상태를 오래 유지해야 하는 작업에는 적합하지 않을 수 있다.

#### 주제 4: Lambda 이벤트
- Lambda는 누군가 버튼을 누르면 실행되는 코드처럼 이해할 수 있다.
- 다양한 이벤트 소스를 통해 실행될 수 있다.

| 이벤트 소스 | Lambda 사용 예시 |
| --- | --- |
| API Gateway | HTTP API 요청 처리 |
| S3 | 이미지 업로드 후 썸네일 생성 |
| EventBridge | 매일 오전 9시 정기 작업 |
| SQS | 비동기 메시지 처리 |
| DynamoDB Streams | 데이터 변경 감지 후 후속 처리 |
| CloudWatch Alarm | 장애 발생 시 자동 복구 작업 |
| Cognito | 회원가입 전후 사용자 처리 |
| ALB | HTTP 요청을 Lambda로 전달 |

#### 주제 5: Lambda 실행 순서
- Lambda는 이벤트가 발생하면 실행 환경을 준비하고, Init 단계를 거친 뒤 Handler를 호출한다.

[이미지 위치: Lambda 실행 순서 Mermaid 다이어그램]

##### 1. 이벤트 발생
- API Gateway 요청, S3 파일 업로드, EventBridge 스케줄 같은 이벤트가 발생한다.

##### 2. 실행 환경 준비
- Lambda는 코드를 실행하기 위한 격리된 실행 공간을 준비한다.
- 이를 Execution Environment라고 한다.
- 실행 환경에는 설정한 메모리와 CPU 자원, Runtime, 함수 코드, `/tmp` 임시 저장소, 환경변수가 포함된다.

##### 3. Init 단계
- 함수 코드와 Lambda Layer를 다운로드한다.
- Runtime을 초기화한다.
- 핸들러 밖에 작성한 코드들도 초기화된다.
- Java처럼 실행 환경이 무거운 런타임은 Init 단계가 길어질 수 있다.

##### 4. Invoke 단계
- 초기화가 끝나면 Lambda가 Handler를 호출한다.
- Handler는 이벤트를 받아 실제 비즈니스 로직을 처리하는 함수이다.

```java
public class GreetingHandler
        implements RequestHandler<Map<String, String>, Map<String, String>> {

    @Override
    public Map<String, String> handleRequest(
            Map<String, String> event,
            Context context
    ) {
        String name = event.getOrDefault("name", "Guest");

        return Map.of(
                "message", "Hello " + name
        );
    }
}
```

- 코드 실행이 끝나면 Lambda는 특정 대기 시간 동안 실행 환경을 유지할 수 있다.

#### 주제 6: Cold Start와 Warm Start
- Cold Start는 새 실행 환경을 만들고 Init 단계까지 수행한 뒤 요청을 처리하는 경우이다.
- 실행 환경이 준비되어 있지 않기 때문에 환경 준비 시간이 추가되어 응답 시간이 길어질 수 있다.
- Warm Start는 기존에 만들어진 실행 환경을 재사용하는 경우이다.
- Warm Start에서는 Init 단계를 건너뛰기 때문에 상대적으로 응답 시간이 짧다.
- 실행 환경을 계속 켜두면 응답은 빨라질 수 있지만, 컴퓨팅 자원을 오래 들고 있어 비용이 발생한다.

| 구분 | 설명 |
| --- | --- |
| Cold Start | 새 실행 환경 생성과 Init 단계 이후 요청 처리 |
| Warm Start | 기존 실행 환경을 재사용해 요청 처리 |

- Lambda도 설정이나 운영 방식으로 Warm Start에 가깝게 유지할 수 있다.
- 예를 들어 일정 시간마다 헬스체크 요청을 보내 실행 환경이 죽지 않도록 하는 Warmup 방식을 사용할 수 있다.

#### 주제 7: Lambda를 사용하기 좋은 경우

##### 파일 업로드 처리
- 파일은 S3에 저장하고, S3 업로드 완료 이벤트가 발생하면 Lambda를 실행할 수 있다.
- 프로필 사진 리사이징, 이미지 형식 변환, 업로드 파일 바이러스 검사 같은 작업에 사용할 수 있다.

##### 극초기 API
- 서비스 초기에는 사용자가 거의 없는데 EC2를 계속 켜둘 필요가 없을 수 있다.
- 이 경우 간단한 API를 Lambda로 시작할 수 있다.
- 다만 API는 응답 시간이 중요하기 때문에 Lambda와 항상 잘 맞는 것은 아니다.
- Warmup이나 Provisioned Concurrency를 사용하지 않으면 Cold Start 문제가 발생할 수 있다.

##### 예약 작업
- 매일 새벽 임시 데이터 삭제, 매주 월요일 리포트 생성 같은 배치 작업에 적합하다.

##### 비동기 작업 처리
- 주문 API는 사용자에게 바로 응답하고, 이메일, Slack 알림, 통계 갱신 같은 작업은 큐를 통해 Lambda가 비동기로 처리할 수 있다.

#### 주제 8: Lambda는 상태를 오래 저장하지 않는다
- Lambda는 기본적으로 짧은 작업에 적합하다.
- 이벤트 처리가 끝나고 일정 시간이 지나면 자원을 반납할 수 있다.
- 실행 환경이 재사용될 수는 있지만, 여기에 저장된 값이 언제 사라질지 보장할 수 없다.
- 전역 변수나 `/tmp` 폴더에 저장한 값도 영구 저장소로 생각하면 안 된다.
- 오래 저장해야 하는 상태가 필요하면 외부 저장소를 사용해야 한다.

#### 주제 9: Lambda 설정

##### 메모리
- Lambda 메모리는 128MB부터 10GB까지 설정할 수 있다.
- Lambda에서는 메모리를 늘리면 CPU 할당도 함께 늘어난다.
- 메모리를 낮게 설정하면 비용이 줄어들 것처럼 보이지만, 실행 시간이 길어져 결과적으로 비용이 더 나올 수도 있다.

##### 타임아웃
- 타임아웃은 Lambda 함수가 최대 얼마 동안 실행될 수 있는지 정하는 설정이다.
- 기본값은 3초이고, 최대값은 900초, 즉 15분이다.
- Lambda 함수는 15분 이상 실행될 수 없다.
- 작업에 따라 타임아웃을 잘 설정해야 한다.

```text
이미지 변환 작업 -> 30초
외부 API 호출 -> 10초
간단한 API -> 3~10초
```

- 타임아웃을 1분 이상으로 설정해야 한다면 Lambda를 사용하는 것이 적절한지 다시 고민해야 한다.

#### 주제 10: Lambda 실무 사용 원칙

##### 함수 하나에 하나의 책임만 둔다
- 하나의 Lambda에 너무 많은 책임을 넣으면 관리가 어려워진다.

```text
좋지 않은 예

회원가입 Lambda
-> 사용자 저장
-> 이메일 발송
-> 쿠폰 발급
-> 추천인 처리
-> 통계 저장
-> Slack 알림
```

- 독립적인 실패와 독립적인 처리가 필요한 경우 함수를 나누는 것이 좋다.

```text
회원가입 Lambda
-> 사용자 저장

회원가입 이벤트
-> 이메일 발송 Lambda
-> 쿠폰 발급 Lambda
-> 통계 저장 Lambda
-> Slack 알림 Lambda
```

- 무조건 함수를 잘게 쪼개는 것이 아니라, 독립적으로 실패하거나 독립적으로 처리되어야 하는지를 기준으로 나눈다.

##### Cold Start 문제 대응
- 실행 환경이 무거운 코드를 피하는 것이 도움이 된다.
- Java, Spring Boot처럼 무거운 런타임은 Cold Start가 커질 수 있다.
- 의존 라이브러리를 줄이거나 Node.js, Python처럼 비교적 가벼운 런타임을 선택할 수 있다.
- Provisioned Concurrency는 Lambda 실행 환경을 미리 준비해두는 기능이다.
- 항상 N개 이상의 실행 환경을 준비해두어 Cold Start를 줄일 수 있다.
- EventBridge를 이용해 일정 주기로 헬스체크 이벤트를 발생시켜 Warmup하는 방식도 있다.

##### 동시성 문제 대응
- Lambda는 계정 한도까지 자동 확장될 수 있다.
- 계정 동시성 한도는 기본적으로 1,000개 수준으로 설정될 수 있다.
- 동시에 많은 Lambda가 RDS 연결을 요청하면 DB 커넥션을 Lambda가 모두 차지할 수 있다.
- 이 경우 RDS 인스턴스 리소스가 고갈되고, WAS도 처리 불가능 상태가 될 수 있다.
- 중간에 큐를 두고, 현재 실행 중인 Lambda 수가 일정 개수 미만이면 실행하고 그 이상이면 큐에 적재하는 방식으로 제어할 수 있다.

##### 장기간 연결 요청 피하기
- Lambda는 최대 실행 시간이 15분으로 제한된다.
- 처음에는 1만 명의 탈퇴자 데이터를 15분 이내에 삭제할 수 있더라도, 서비스가 성장해 데이터가 많아지면 Lambda로 처리할 수 없게 될 수 있다.
- WebSocket처럼 장기간 연결이 필요한 작업이나, 파일 처리 용량이 매우 큰 작업은 Lambda와 맞지 않을 수 있다.

##### 모든 백엔드 기능을 Lambda로 만들지 않기
- Lambda는 편하지만 모든 API와 잘 맞는 것은 아니다.
- 복잡한 회원가입처럼 여러 서류와 검증 절차가 있고, 데이터베이스 연결을 지속적으로 사용해야 하는 작업은 Lambda만으로 구성하기 어려울 수 있다.
- 장점만 보고 선택하지 말고 단점을 극복할 수 있거나 단점을 무시할 수 있는 경우에 사용하는 것이 좋다.

#### 주제 11: Lambda 정리

| 개념 | 핵심 |
| --- | --- |
| Lambda | 이벤트가 발생할 때 코드를 실행하는 서버리스 컴퓨팅 서비스 |
| Serverless | 서버가 없는 것이 아니라 서버 운영을 AWS가 대신하는 방식 |
| Trigger | Lambda를 실행시키는 이벤트 소스 |
| Handler | 이벤트를 받아 실제 로직을 처리하는 함수 |
| Timeout | 함수가 실행될 수 있는 최대 시간 |
| Concurrency | 동시에 실행되는 Lambda 수 |
| Cold Start | 새 실행 환경 초기화로 첫 요청이 느려질 수 있는 현상 |
| `/tmp` | 임시 저장소이며 영구 저장소가 아님 |

#### 주제 12: API Gateway
- API Gateway는 클라이언트의 API 요청을 받아 백엔드로 전달하고, 인증, 권한, 요청 제한, CORS, 모니터링 같은 공통 기능을 API 앞단에서 관리하는 AWS 관리형 서비스이다.
- 인증, JWT, API Key 사용량, CORS 체크 등을 앞단에서 미리 수행할 수 있다.
- 이를 통해 백엔드의 처리 부담을 줄일 수 있다.
- Lambda 기반 서버리스 API를 사용하면 Spring과 별도로 인증, 인가가 필요하다.
- Lambda 함수 내부에 인증, 인가 로직을 모두 넣으면 함수가 무거워질 수 있으므로 API Gateway를 활용할 수 있다.

#### 주제 13: CloudTrail
- CloudTrail은 AWS 계정에서 발생하는 모든 API 호출과 콘솔 활동을 자동으로 기록하고 추적하는 서비스이다.
- 보안 감사, 컴플라이언스, 문제 해결을 위해 AWS 계정의 활동을 추적하고 분석할 때 사용한다.
- 누가, 언제, 어떤 AWS API를 호출했는지 확인하는 데 도움이 된다.

#### 주제 14: CloudWatch란 무엇인가
- CloudWatch는 AWS 리소스와 애플리케이션에서 발생하는 로그, 지표, 이벤트를 수집하고 모니터링하는 통합 관제 서비스이다.
- 운영 중 발생하는 문제를 사용자 제보 이후에 알게 되는 것이 아니라, CloudWatch를 통해 먼저 감지하는 것이 목적이다.

```text
- EC2 CPU가 갑자기 높아짐
- 디스크가 가득 참
- ALB의 5xx 오류가 증가함
- RDS 연결 수가 급증함
- 특정 API만 느려짐
- 배포 이후 오류가 늘어남
```

- CloudWatch의 목적은 단순히 그래프를 보는 것이 아니다.
- 장애를 더 빨리 발견하고 복구해 서비스 안정성을 높이는 것이 목적이다.

#### 주제 15: DevOps에서 모니터링이 중요한 이유
- DevOps는 배포 자동화만 의미하지 않는다.
- 운영 중인 서비스가 정상인지, 오류가 늘었는지, 어느 서버가 느린지, DB가 병목인지, 배포 후 문제가 생겼는지 확인할 수 있어야 한다.

[이미지 위치: DevOps와 모니터링]

| 확인 질문 | CloudWatch 사용 |
| --- | --- |
| 지금 서비스가 정상인가? | 대시보드와 메트릭 확인 |
| 오류가 늘었는가? | ALB 5xx, 애플리케이션 ERROR 로그 확인 |
| 어느 서버가 느린가? | CPU, 메모리, 응답 시간 확인 |
| DB가 병목인가? | RDS CPU, 연결 수, 지연 시간 확인 |
| 배포 후 문제가 생겼는가? | 배포 전후 오류율, 응답 시간 비교 |
| 운영자가 지금 대응해야 하는가? | Alarm 알림 |

- 모니터링은 운영의 선택 사항이 아니라 기본 장치이다.

#### 주제 16: CloudWatch 핵심 기능

| 기능 | 역할 | 예시 |
| --- | --- | --- |
| Metrics | 시간에 따른 숫자 지표 확인 | CPU, 요청 수, 오류 수 |
| Logs | 시스템과 애플리케이션 기록 저장 | Spring ERROR 로그, Nginx 로그 |
| Alarms | 조건 충족 시 알림 또는 자동 대응 | CPU 80% 초과 시 이메일 |
| Dashboards | 여러 지표를 한 화면에서 확인 | EC2, ALB, RDS 상태 한눈에 보기 |
| Logs Insights | 로그를 쿼리로 검색, 분석 | 5xx 오류가 많은 API 찾기 |

#### 주제 17: Metrics
- Metrics는 시간에 따라 변화하는 숫자 데이터이다.
- 예를 들어 EC2 CPU 사용률이 10:00에는 25%, 10:01에는 27%처럼 기록될 수 있다.
- CPU 사용률이 높아졌다면 서버 트래픽이 많아졌거나, 애플리케이션 코드가 비효율적일 수 있다.
- N+1 문제, Full Table Scan, 비효율적인 페이징 등이 원인일 수 있다.

| 서비스 | 확인할 메트릭 | 의미 |
| --- | --- | --- |
| EC2 | `CPUUtilization` | CPU 사용률 |
| EC2 | `StatusCheckFailed` | 인스턴스 또는 네트워크 상태 문제 |
| ALB | `RequestCount` | 요청 수 |
| ALB | `HTTPCode_Target_5XX_Count` | 백엔드 서버 5xx 오류 |
| ALB | `TargetResponseTime` | 백엔드 응답 시간 |
| ALB | `HealthyHostCount` | 정상 Target 수 |
| RDS | `DatabaseConnections` | DB 연결 수 |
| RDS | `FreeStorageSpace` | 남은 DB 스토리지 |
| ElastiCache | `Evictions` | 메모리 부족으로 제거된 캐시 수 |
| ElastiCache | `CacheHits`, `CacheMisses` | 캐시 효율 |

#### 주제 18: Logs
- Metrics는 문제가 발생했음을 알려준다.
- Logs는 문제가 왜 발생했는지 기록한다.
- 예를 들어 ALB 500 카운트가 증가했다면 CloudWatch Logs에서 구체적인 에러 메시지를 확인할 수 있다.

```text
ERROR Database connection timeout
ERROR Payment API timeout
ERROR NullPointerException
ERROR JWT validation failed
```

- CloudWatch Logs는 여러 EC2에서 발생하는 로그를 한 곳에 모아 중앙 집중화할 수 있다.
- 백엔드 서버가 10대라면 각 서버에 직접 접속하지 않고 한 곳에서 로그를 확인할 수 있다.

[이미지 위치: CloudWatch Logs 중앙 집중화]

#### 주제 19: Alarms
- Alarms는 특정 조건이 일정 시간 유지될 때 운영자에게 알림을 보내는 기능이다.

```text
EC2 CPU 평균이 5분 동안 80% 초과
-> 이메일 또는 Slack 알림

ALB Target 5xx가 급증
-> 운영자 알림

RDS 남은 스토리지가 부족
-> 장애 예방 알림
```

- Alarm은 단순히 이상한 일이 생겼다는 알림이 아니라, 지금 대응하지 않으면 장애로 이어질 수 있는 상황을 알려야 한다.
- 알람이 너무 자주 울리면 운영자가 무신경해질 수 있으므로 신중하게 설계해야 한다.

#### 주제 20: Observability란 무엇인가
- Observability는 시스템 내부를 직접 열어보지 않아도, 시스템이 밖으로 남기는 Metrics, Logs, Traces를 통해 무슨 일이 일어났고 왜 일어났는지 추론할 수 있는 능력이다.
- 서비스 규모가 작을 때는 문제가 생기면 SSH로 서버에 접속해 확인할 수 있다.
- 하지만 서버가 많아지고 서비스 계층이 늘어나면 어디가 문제인지 추측만으로 찾기 어렵다.

[이미지 위치: 여러 계층을 거치는 서비스 구조]

```text
- ALB가 느린가?
- Spring Boot가 느린가?
- DB 쿼리가 느린가?
- Redis가 응답하지 않는가?
- 외부 이미지 업로드 API가 느린가?
- 최근 배포 코드에 문제가 있는가?
```

- 옵저빌리티의 목적은 장애를 추측으로 해결하지 않고 데이터로 원인을 좁혀가는 것이다.

#### 주제 21: 모니터링과 옵저빌리티의 차이
- 모니터링은 이미 예상한 문제를 감지하고 확인하는 것이다.
- 예를 들어 EC2 CPU가 80%를 넘으면 알림을 주거나, ALB 500 오류가 늘면 알림을 주는 방식이다.
- 미리 기준을 정해두고 그 기준을 넘는지 확인한다.
- 옵저빌리티는 예상하지 못한 문제도 데이터로 원인을 추론할 수 있게 하는 것이다.

```text
사용자는 "로그인이 가끔 실패한다"고 말함

확인 결과:
- EC2 CPU 정상
- ALB 요청 수 정상
- DB CPU 정상
- 특정 OAuth 외부 API 호출만 간헐적으로 timeout
```

- 알람과 모니터링만으로는 부족할 수 있다.

#### 주제 22: 옵저빌리티의 세 가지 데이터

| 데이터 | 핵심 질문 | 대표 예시 |
| --- | --- | --- |
| Metrics | 지금 상태가 어떤가? | CPU, 오류율, 요청 수, 응답 시간 |
| Logs | 어떤 일이 발생했는가? | Exception, 에러 메시지, 요청 로그 |
| Traces | 어디에서 시간이 오래 걸렸는가? | API -> DB -> 외부 API 호출 시간 |

#### 주제 23: Traces와 Trace ID
- Trace는 요청이 어디를 거쳤는지 추적하는 것이다.
- 사용자는 "주문이 느리다"고 느낄 수 있다.
- Metrics만 보면 주문 응답 시간이 3.2초라는 사실만 알 수 있다.
- Logs만 보면 API가 200 OK로 끝났다는 사실만 알 수 있다.
- Trace를 보면 전체 요청 중 어디에서 시간이 오래 걸렸는지 확인할 수 있다.

```text
전체 요청: 3.2초
├─ Spring Boot 처리: 100ms
├─ RDS 쿼리: 20ms
└─ 외부 결제 API 호출: 3000ms
```

[이미지 위치: Trace 구조]

- 하나의 사용자 요청은 여러 시스템을 거친다.
- 이때 요청에 `traceId=abcd` 같은 Trace ID를 붙이면 여러 계층의 로그를 연결해서 볼 수 있다.

#### 주제 24: 옵저빌리티가 높다는 것
- CloudWatch가 있다고 해서 자동으로 옵저빌리티가 높은 것은 아니다.
- 아래 질문에 답할 수 있어야 옵저빌리티가 높다고 볼 수 있다.

```text
- 지금 서비스는 정상인가?
- 어떤 기능이 실패하고 있는가?
- 언제부터 문제가 시작됐는가?
- 어느 서버 또는 어느 API가 문제인가?
- 사용자는 얼마나 영향을 받고 있는가?
- DB, Redis, 외부 API 중 어디가 병목인가?
- 최근 배포와 관련이 있는가?
```

#### 주제 25: 실무에서 옵저빌리티를 높이는 방법

##### 로그를 구조화한다
- 로그를 JSON처럼 구조화하면 검색, 필터링, 분석이 쉬워진다.

```json
{
  "timestamp": "2026-06-25T10:12:20+09:00",
  "level": "ERROR",
  "service": "community-api",
  "traceId": "ab12cd34",
  "path": "/api/posts",
  "status": 500,
  "message": "Database connection timeout"
}
```

##### 핵심 API 응답 시간과 오류율을 수집한다
- 모든 API를 처음부터 완벽하게 수집할 필요는 없다.
- 회원가입, 결제, 작성처럼 중요한 기능부터 요청 수, 성공률, 4xx/5xx 비율, 평균 응답 시간, p95 응답 시간을 수집한다.

```text
- 요청 수
- 성공률
- 4xx / 5xx 비율
- 평균 응답 시간
- p95 응답 시간
```

#### 주제 26: CloudWatch와 Observability 정리
- CloudWatch는 도구일 뿐이다.
- 결국 중요한 것은 서비스를 안정적으로 제공하기 위해 옵저빌리티를 높이는 것이다.

| 개념 | 핵심 |
| --- | --- |
| CloudWatch | AWS 운영 상태를 확인하고 대응하는 서비스 |
| Metrics | CPU, 요청 수, 오류율 같은 숫자 지표 |
| Logs | 오류와 사건의 상세 기록 |
| Alarms | 기준 초과 시 알림과 자동 대응 |
| Dashboard | 여러 지표를 한 화면에서 확인 |
| Observability | 메트릭, 로그, 트레이스로 시스템 원인을 추론하는 능력 |
| CloudWatch Agent | EC2 내부 메모리, 디스크, 로그 수집 |
| CloudTrail | AWS 작업 이력과 감사 기록 |
