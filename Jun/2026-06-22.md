### 새로 배운 내용

#### 주제 1: VPC란 무엇인가
- VPC(Virtual Private Cloud)는 공용 클라우드 환경에서 사용자에게 독립된 가상 네트워크를 제공하는 서비스이다.
- AWS 안에 나만의 논리적으로 분리된 가상 네트워크를 만드는 개념이다.
- VPC 안에서 IP 대역, 서브넷, 라우팅, 보안 규칙을 설계할 수 있다.
- VPC를 사용하는 이유는 서버와 데이터베이스를 무작정 인터넷에 연결하지 않고, 서비스별 통신 경로와 접근 범위를 통제하기 위해서이다.
- VPC가 없다면 웹 서버, DB, 캐시 서버 같은 리소스들이 외부 인터넷에 그대로 노출될 위험이 있다.
- VPC를 사용하면 사용자가 접근할 수 있는 리소스와 내부 리소스 간 통신 경로를 분리할 수 있다.

#### 주제 2: VPC의 기본 역할
- VPC는 AWS 리소스를 배치하는 전체 가상 네트워크 공간이다.
- VPC를 만들 때 가장 먼저 지정하는 값 중 하나가 IPv4 CIDR 블록이다.
- 예를 들어 `10.0.0.0/16`을 VPC CIDR로 설정하면 약 65,000개 규모의 IP 주소 범위를 사용할 수 있다.
- 이 IP 대역을 서브넷 단위로 나누어 사용한다.
- VPC는 회사 전체 사내망처럼 생각할 수 있다.
- VPC 안에 EC2, RDS, ElastiCache 같은 AWS 리소스를 배치하고, 어떤 리소스를 외부에 공개할지와 어떤 리소스를 내부에 둘지 결정한다.

#### 주제 3: Subnet과 AZ
- Subnet은 VPC의 IP 주소 범위를 더 작은 네트워크 단위로 나눈 공간이다.
- 예를 들어 하나의 VPC `10.0.0.0/16`을 여러 서브넷으로 나눌 수 있다.

```text
VPC 전체: 10.0.0.0/16
Public Subnet A: 10.0.1.0/24
Public Subnet B: 10.0.2.0/24
Private Subnet A: 10.0.11.0/24
Private Subnet B: 10.0.12.0/24
```

- Subnet은 용도와 가용성에 맞춰 나눈다.
- AZ(Availability Zone)는 AWS 리전 안에 있는 물리적으로 분리된 데이터센터 단위이다.
- 운영 환경에서는 보통 두 개 이상의 AZ에 서브넷을 분산해 고가용성을 확보한다.
- 여러 AZ에 분산하면 특정 AZ 장애가 발생해도 다른 AZ에서 서비스를 이어갈 수 있다.
- 다만 고가용성 구성을 하면 비용도 함께 증가할 수 있다.

#### 주제 4: Public Subnet과 Private Subnet
- Public Subnet과 Private Subnet은 해당 서브넷의 라우팅 테이블에 Internet Gateway로 가는 경로가 있느냐로 구분한다.
- Public Subnet은 인터넷 게이트웨이로 가는 경로가 있어 인터넷과 직접 통신할 수 있다.
- Private Subnet은 인터넷 게이트웨이로 직접 가는 경로가 없어 인터넷에서 직접 접근할 수 없다.
- Public Subnet에는 보통 ALB, Bastion Host, NAT Gateway를 배치한다.
- Private Subnet에는 App Server, RDS, ElastiCache 같은 내부 리소스를 배치한다.
- 보안상 DB와 Cache 같은 내부 서비스는 Private Subnet에 두는 것이 일반적이다.

#### 주제 5: Route Table과 Internet Gateway
- Route Table은 목적지로 가는 트래픽을 어디로 보낼지 정하는 네트워크 경로표이다.
- VPC 내부 대역으로 가는 트래픽은 `local` 경로를 통해 VPC 내부에서 통신한다.
- 외부 인터넷으로 나가는 트래픽은 Internet Gateway로 보내는 경로를 추가해야 한다.

```text
0.0.0.0/0 -> Internet Gateway
```

- Internet Gateway는 VPC와 인터넷을 연결하는 출입구이다.
- Internet Gateway를 VPC에 연결하고, Public Subnet의 Route Table에 `0.0.0.0/0 -> igw-id` 경로를 추가하면 해당 서브넷은 인터넷으로 나갈 수 있다.
- EC2가 Public Subnet에 있어도 외부 접속이 되려면 Public IP, IGW 경로, Security Group 허용 규칙이 함께 필요하다.

#### 주제 6: NAT Gateway
- NAT Gateway는 Private Subnet의 서버가 외부 인터넷으로 나갈 수 있게 하되, 인터넷에서 먼저 들어오는 연결은 막는 장치이다.
- Private Subnet에 있는 Spring WAS도 외부 API 호출, Maven/Gradle 의존성 다운로드, 보안 패치 등을 위해 인터넷 통신이 필요할 수 있다.
- 이때 Private Subnet의 트래픽을 NAT Gateway로 보내고, NAT Gateway가 인터넷으로 릴레이한다.

```text
Private Subnet -> NAT Gateway -> Internet
```

- NAT Gateway는 유용하지만 비용이 비쌀 수 있다.
- 특히 컨테이너 이미지 다운로드, Git clone, S3 데이터 전송처럼 많은 트래픽이 NAT Gateway를 지나가면 비용이 커질 수 있다.

#### 주제 7: VPC 구성 시 주의할 점
- Public IP를 할당할 때는 비용과 보안 측면을 조심해야 한다.
- Public IP는 인스턴스 상태와 연결 방식에 따라 과금이 발생할 수 있다.
- RDS, ElastiCache 같은 내부 서비스에는 Public IP를 할당하지 않는 것이 좋다.
- RDS와 ElastiCache는 EC2처럼 OS에 SSH로 접속하는 서버가 아니므로 외부에 직접 공개할 이유가 거의 없다.
- SSH를 `0.0.0.0/0`으로 열어두는 것은 위험하다.
- VPC를 설계할 때는 WAS, DB, Web Server, Cache를 어디에 배치할지 미리 고민해야 한다.
- Public Subnet에는 외부와 직접 연결되어야 하는 리소스를 두고, Private Subnet에는 내부 서버와 데이터 저장소를 두는 식으로 역할을 나누는 것이 중요하다.

#### 주제 8: IAM이란 무엇인가
- IAM(Identity and Access Management)은 AWS 리소스에 대한 사용자 인증과 권한 관리를 제공하는 서비스이다.
- IAM은 누가 AWS 리소스에 접근할 수 있는지, 그리고 어떤 작업을 할 수 있는지를 결정한다.
- IAM은 크게 인증과 인가를 다룬다.
- 인증은 "당신은 누구인가?"를 확인하는 과정이다.
- 인가는 "당신은 무엇을 할 수 있는가?"를 확인하는 과정이다.
- 예를 들어 개발자가 EC2를 생성할 수 있는지, 운영 RDS를 삭제할 수 있는지, EC2 서버가 S3에 파일을 업로드할 수 있는지를 IAM으로 제어한다.

#### 주제 9: IAM을 사용하는 이유와 최소 권한 원칙
- AWS 계정의 Root User는 최고 관리자 권한을 가지므로 일상 작업에 사용하면 위험하다.
- 여러 개발자, 운영자, 재무 담당자가 함께 작업하는 환경에서는 각자 필요한 권한만 가져야 한다.
- 모두가 모든 권한을 가지면 실수나 계정 탈취 시 피해가 커진다.
- 최소 권한 원칙은 필요한 작업을 수행할 때 필요한 최소한의 권한만 부여하는 보안 원칙이다.
- 권한은 처음부터 넓게 열어두고 나중에 줄이는 것보다, 최소한으로 부여하고 필요할 때 검토 후 확장하는 것이 안전하다.

#### 주제 10: IAM 구성 요소
- Root User는 AWS 계정을 처음 만들 때 생성되는 최고 관리자이다.
- User는 AWS에 접근하는 개별 사용자이다.
- Group은 여러 사용자에게 공통 권한을 부여하는 묶음이다.
- Role은 특정 사용자나 AWS 서비스가 임시로 맡는 권한 묶음이다.
- Policy는 허용하거나 거부할 작업을 작성한 권한 규칙이다.
- MFA는 로그인 시 비밀번호 외에 추가 인증을 요구하는 보안 수단이다.
- 실무에서는 개발자, 운영자, 조회 전용 감사자, 결제 담당자처럼 역할에 따라 Group을 나누고 권한을 관리한다.

#### 주제 11: IAM Policy와 Role
- Policy는 AWS에서 어떤 작업을 허용할지, 거부할지 정하는 규칙이다.
- IAM Policy는 보통 Effect, Action, Resource, Condition으로 구성된다.
- Effect는 허용할지 거부할지를 나타낸다.
- Action은 어떤 AWS API 작업을 허용하거나 거부할지를 나타낸다.
- Resource는 어떤 AWS 리소스에 적용할지를 나타낸다.
- Condition은 어떤 조건에서만 허용하거나 거부할지를 나타낸다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-service-image/image/*"
    }
  ]
}
```

- Role은 IAM User나 AWS 서비스가 특정 권한을 임시로 빌려서 사용할 수 있게 하는 권한 묶음이다.
- EC2 서버가 S3에 파일을 업로드해야 한다면 EC2에 직접 키를 넣기보다 S3 업로드 권한이 있는 Role을 부여하는 것이 안전하다.
- 서버나 서비스 간 접근에서는 장기 Access Key보다 Role 사용을 우선 고려해야 한다.

#### 주제 12: 인프라 설계 흐름
- 인프라를 잘 구성하려면 먼저 제공하는 서비스와 기능 명세를 확인해야 한다.
- 어떤 서비스인지, 어떤 데이터가 중요한지, 어디에 부하가 걸리는지, 웹인지 앱인지 API인지 파악해야 한다.
- 그 다음 필요한 구성 요소를 검토한다.
- 데이터베이스, 세션 스토어, 웹 서버, WAS, 이미지 저장소, CDN, 로깅, 메트릭 수집이 필요한지 판단한다.
- 구성 요소를 확정한 뒤 공개 범위를 정한다.
- 외부에 공개해야 하는 것, 일부 공개해야 하는 것, 비공개해야 하는 것을 구분한다.
- DB, WAS, Cache는 보통 외부에 직접 공개하지 않는다.
- 목표 트래픽과 가용성 수준을 정한 뒤 VPC, 네트워킹, 데이터베이스, 인스턴스를 구성한다.

#### 주제 13: Security Group이란 무엇인가
- Security Group은 클라우드 환경에서 인스턴스에 대한 네트워크 트래픽을 제어하는 가상 방화벽이다.
- AWS 리소스에 들어오고 나가는 네트워크 트래픽을 허용 규칙으로 제어한다.
- 누가 어떤 포트로 이 리소스에 접근할 수 있는지를 정의한다.
- Security Group은 EC2 인스턴스 자체가 아니라 ENI(Elastic Network Interface)에 연결된다.
- ENI는 AWS에서 가상 NIC와 같은 역할을 한다.
- Security Group은 인바운드 트래픽과 아웃바운드 트래픽을 제어한다.

#### 주제 14: Security Group의 특징
- Security Group은 상태 저장형 방화벽이다.
- 한 번 허용된 요청의 응답은 반대 방향 규칙을 별도로 작성하지 않아도 자동으로 허용된다.
- Security Group은 Allow 규칙만 작성할 수 있다.
- 명시적으로 허용한 트래픽만 통과하고, 허용 규칙이 없으면 기본적으로 차단된다.
- 특정 IP나 국가 단위 트래픽을 명시적으로 차단하려면 Network ACL, WAF, Network Firewall, 애플리케이션 레벨 차단 등을 고려해야 한다.
- 하나의 리소스에 여러 Security Group을 붙일 수 있다.
- 다만 Security Group을 많이 붙인다고 항상 더 안전해지는 것은 아니다.
- Security Group은 Deny가 아니라 Allow 규칙을 누적하므로, 붙일수록 허용 범위가 넓어질 수 있다.

#### 주제 15: Security Group 참조
- Security Group 규칙의 Source 또는 Destination에는 CIDR뿐 아니라 다른 Security Group을 지정할 수 있다.
- IP 대역으로만 제어하면 오토스케일링으로 EC2가 늘어나거나 줄어들 때 IP가 바뀌어 관리가 어려워진다.
- Security Group 참조를 사용하면 어떤 역할의 서비스가 접근할 수 있는지 명확하게 표현할 수 있다.

| 보안 그룹 | 인바운드 허용 | Source |
| --- | --- | --- |
| sg-alb | HTTPS 443 | 0.0.0.0/0 |
| sg-app | TCP 8080 | sg-alb |
| sg-db | MySQL 3306 | sg-app |

- 위 구조에서는 인터넷 사용자는 ALB에만 접근하고, App Server는 ALB에서만 요청을 받으며, DB는 App Server에서만 접근할 수 있다.
- DB와 Redis를 인터넷에 직접 열지 않고 내부 서비스 통신은 Security Group 참조를 우선 검토하는 것이 좋다.

#### 주제 16: Route 53이란 무엇인가
- Route 53은 사람이 읽는 도메인 주소를 서버나 AWS 서비스의 주소로 연결하고, 상황에 따라 어느 서비스로 보낼지 결정하는 DNS 서비스이다.
- 브라우저는 `example.com` 같은 도메인만으로 서버에 직접 접속할 수 없고, IP 주소가 필요하다.
- DNS는 도메인 이름에 해당하는 IP 주소나 서비스 주소를 알려준다.
- Route 53은 AWS에서 제공하는 DNS 서비스로, AWS 리소스와 유기적으로 연결할 수 있다는 장점이 있다.
- 도메인을 가비아 같은 곳에서 구매했더라도 DNS 관리는 Route 53에서 할 수 있다.

#### 주제 17: Hosted Zone
- Hosted Zone은 특정 도메인과 서브도메인에 대한 DNS 레코드를 보관하고 관리하는 공간이다.
- Public Hosted Zone은 인터넷 전체에서 조회할 수 있다.
- 공개 웹사이트나 공개 API에 사용한다.
- 예를 들어 `www.example.com`, `api.example.com`이 Public Hosted Zone에 등록될 수 있다.
- Private Hosted Zone은 연결된 VPC 내부에서만 조회할 수 있다.
- 내부 DB, 사내 API, 서비스 디스커버리에 사용할 수 있다.
- 예를 들어 `db.internal.example.com`은 외부 DNS에서는 보이지 않고 VPC 내부에서만 조회되도록 만들 수 있다.

#### 주제 18: DNS Record
- DNS Record는 특정 도메인에 어떤 설정이 있는지 저장한 규칙이다.
- A Record는 도메인을 IPv4 주소에 연결한다.
- AAAA Record는 도메인을 IPv6 주소에 연결한다.
- CNAME은 한 도메인을 다른 도메인 이름에 연결한다.
- Alias는 Route 53에서 AWS 리소스를 도메인에 직접 연결하기 위한 AWS 전용 기능이다.
- MX는 메일 서버를 지정한다.
- TXT는 도메인 소유권 확인, SPF, DKIM, DMARC 같은 이메일 보안 정책에 사용된다.
- NS는 도메인의 DNS 담당 네임서버를 나타낸다.
- SOA는 DNS 영역의 대표 네임서버와 관리, 갱신 정보를 담는다.

#### 주제 19: Route 53 라우팅 정책
- Simple Routing은 하나의 도메인을 하나의 대상에 연결하는 기본 방식이다.
- Weighted Routing은 여러 대상에 대해 비율대로 요청을 분산하는 방식이다.
- 예를 들어 기존 v1 서버에 90%, 신규 v2 서버에 10%를 보내 카나리 배포나 무중단 배포에 활용할 수 있다.
- Failover Routing은 주 서버가 정상이면 주 서버로 보내고, 장애 시 대기 서버로 보내는 방식이다.
- Latency Routing은 사용자와 AWS 리전 사이의 지연 시간이 낮은 리전으로 연결한다.
- Geolocation Routing은 사용자 IP 기반으로 특정 지역에 맞는 리전으로 라우팅한다.
- 실무에서는 도메인을 ALB, CloudFront, S3 정적 웹사이트, API Gateway 등에 연결할 때 Route 53을 사용한다.

#### 주제 20: EC2와 가상화
- EC2는 AWS에서 가장 기본적인 컴퓨팅 자원이다.
- EC2 인스턴스는 하이퍼바이저가 물리 서버의 자원을 나누어 만든 가상 머신이다.
- 하이퍼바이저는 물리 서버 한 대의 CPU, 메모리, 디스크, 네트워크 자원을 여러 가상 컴퓨터가 나누어 사용하도록 만들고 서로 격리한다.
- 각 가상 머신은 자기만의 컴퓨터처럼 보이며, 다른 고객의 메모리, 프로세스, 디스크에 접근하지 못한다.
- 하이퍼바이저는 CPU 분배, 메모리 분리, 가상 디스크와 가상 네트워크 카드 제공, 격리를 담당한다.
- 컨테이너는 OS 커널을 공유하고 애플리케이션 레벨을 격리하지만, EC2 같은 가상 머신은 OS 레벨까지 격리한다.

#### 주제 21: EC2를 배우는 이유
- EC2는 백엔드 서버, 게임 서버, 크롤러, VPN 서버 등 다양한 용도로 사용할 수 있는 범용 컴퓨팅 자원이다.
- 운영체제를 격리해서 빌리는 것이기 때문에 애플리케이션, 네트워크, 운영체제, 보안, 스토리지, 모니터링을 직접 다루게 된다.
- ECS, EKS, RDS 같은 관리형 서비스도 결국 EC2 위에서 직접 구성할 수 있는 작업을 서비스화한 것으로 이해할 수 있다.
- EC2는 자유도가 높고 기본이 되는 서비스이므로 클라우드 인프라를 이해하는 출발점이 된다.

#### 주제 22: EC2 핵심 요소
- AMI(Amazon Machine Image)는 EC2 서버를 만드는 템플릿이다.
- AMI에는 운영체제와 초기 소프트웨어 구성이 들어 있다.
- 반복 배포나 Auto Scaling 환경에서는 JDK, Docker, 애플리케이션 실행 환경 등을 미리 구성한 Custom AMI를 사용할 수 있다.
- Instance Type은 CPU와 메모리 조합으로 결정되는 EC2 성능 단위이다.
- T 계열은 개발 서버나 작은 웹 서버에 적합하고, M 계열은 균형형, C 계열은 CPU 중심, R 계열은 메모리 중심, G/P 계열은 GPU 중심, I/D 계열은 고성능 로컬 스토리지 중심이다.
- 어떤 인스턴스 타입을 쓸지는 부하 테스트와 서비스의 트래픽 패턴, CPU/RAM 사용량을 보고 결정해야 한다.

#### 주제 23: EBS와 EC2 네트워크
- EBS(Elastic Block Store)는 EC2에 연결되는 영구 블록 스토리지이다.
- EC2는 컴퓨팅 자원이고, EBS는 가상의 하드디스크처럼 동작한다.
- EC2를 중지해도 EBS는 계속 존재할 수 있고, 다시 시작하면 기존 EBS를 연결해 사용할 수 있다.
- EBS는 분리해서 다른 EC2에 붙일 수도 있다.
- 스냅샷을 만들면 특정 시점의 백업을 생성할 수 있다.
- EC2는 반드시 VPC 안의 Subnet에 배치된다.
- 외부에서 EC2에 접속하려면 Public IP, Internet Gateway가 연결된 Public Subnet, Security Group 허용 규칙이 필요하다.

#### 주제 24: EC2 운영 시 주의점
- EC2에는 태그를 잘 붙여 관리하는 것이 좋다.
- `Name`, `Environment`, `Service`, `Owner`, `CostCenter`, `ManagedBy` 같은 태그를 사용하면 운영과 비용 추적이 쉬워진다.
- EC2에는 중요한 파일을 직접 저장하지 않는 것이 좋다.
- EC2는 삭제될 수 있으므로 파일은 S3 같은 별도 스토리지에 저장하는 편이 안전하다.
- 서버에 SSH로 직접 들어가 파일을 수정하는 방식은 서버가 한두 대일 때만 가능하다.
- 서버가 여러 대가 되면 배포 스크립트나 이미지 기반 배포, 자동화된 설정 관리가 필요하다.
- EC2는 장애가 발생할 수 있으므로 장애를 전제로 모니터링, 알림, 이중화, 복구 전략을 함께 설계해야 한다.
