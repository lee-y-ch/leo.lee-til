## 소제목: Portainer를 활용한 컨테이너 운영과 Docker Volume 이해

### 새로 배운 내용

#### 주제 1: Portainer란 무엇인가
- Portainer는 Docker와 Kubernetes 같은 컨테이너 환경을 쉽게 관리할 수 있도록 도와주는 웹 기반 GUI 관리 도구이다.
- Docker Engine 또는 Portainer Agent와 연결해 컨테이너, 이미지, 볼륨, 네트워크 등의 상태를 읽고 관리 명령을 실행한다.
- 화면에서 버튼을 누르면 Portainer가 이에 대응하는 Docker API 요청을 전달한다.
- Portainer는 Docker를 대체하지 않는다. Docker의 기능을 웹 화면에서 더 쉽게 사용할 수 있도록 돕는 운영 관리 도구이다.

[이미지 위치: Portainer 관리 화면]

#### 주제 2: Portainer가 필요한 이유
- Docker는 기본적으로 CLI 명령어를 사용해 관리한다.

```bash
docker ps
docker logs
docker restart
docker exec -it
docker network ls
docker images
docker volume ls
```

- CLI는 정확하고 자동화하기 편리하지만, 운영자가 많은 컨테이너와 여러 서버를 관리할 때는 전체 상태를 빠르게 파악하기 어렵다.

| 문제 | 상황 | 결과 |
| --- | --- | --- |
| 상태 파악이 어려움 | 컨테이너가 많아지면 `docker ps`, `docker logs`를 반복 실행 | 현재 서비스 상태를 한눈에 보기 어려움 |
| 명령어 실수 | 컨테이너 이름, 포트, 볼륨, 네트워크를 잘못 지정 | 잘못된 컨테이너를 삭제하거나 재시작할 수 있음 |
| 운영 접근성이 낮음 | CLI 경험이 적은 팀원도 운영 작업을 해야 함 | 운영 업무가 특정 인력에게 집중됨 |
| 여러 서버 관리가 불편함 | 여러 EC2에 각각 Docker가 설치됨 | 서버마다 SSH로 접속해 명령을 실행해야 함 |
| 설정이 눈에 보이지 않음 | 볼륨, 네트워크, 환경변수, 포트 설정이 분산됨 | 장애 원인 파악이 느려짐 |

- Portainer는 컨테이너 환경을 GUI로 보여주어 이런 운영상의 불편을 줄인다.

#### 주제 3: Portainer의 주요 기능

| 기능 | 설명 | 대응하는 Docker CLI |
| --- | --- | --- |
| 컨테이너 조회 | 실행, 중지, 종료 상태 확인 | `docker ps -a` |
| 시작, 중지, 재시작 | 버튼으로 컨테이너 제어 | `docker start`, `docker stop`, `docker restart` |
| 로그 확인 | 브라우저에서 컨테이너 로그 조회 | `docker logs -f` |
| 콘솔 접속 | 컨테이너 내부 셸 접속 | `docker exec -it` |
| 이미지 관리 | 이미지 조회, Pull, 삭제 | `docker images`, `docker pull`, `docker rmi` |
| 볼륨 관리 | 볼륨 생성, 연결, 조회 | `docker volume ...` |
| 네트워크 관리 | 컨테이너 네트워크 연결 상태 확인 | `docker network ...` |
| Stack 관리 | Docker Compose 기반 서비스 배포 | `docker compose up -d` |
| 자원 상태 확인 | CPU, 메모리, 네트워크, I/O 사용량 확인 | `docker stats`, `docker top` 등 |

#### 주제 4: Docker Desktop과 Portainer의 차이
- 두 도구 모두 Docker를 GUI로 관리할 수 있다.
- Docker Desktop은 주로 개인의 로컬 개발 환경에서 사용하고, Portainer는 서버와 운영 환경을 원격으로 관리할 때 사용한다.

| 구분 | Docker Desktop | Portainer |
| --- | --- | --- |
| 주 목적 | 개인 로컬 개발 환경 | 서버 및 운영 환경 관리 |
| 주 설치 위치 | 개발자 개인 PC | EC2, 온프레미스 서버, 클라우드 VM |
| 관리 범위 | 보통 개인 PC의 Docker | 여러 Docker 서버, Swarm, Kubernetes 환경 |
| 주요 사용자 | 개인 개발자 | 개발팀, 운영팀, DevOps 담당자 |
| 핵심 가치 | 개발 편의성 | 운영 가시성, 원격 관리, 표준화 |
| 대표 사용 상황 | 로컬에서 앱 실행 및 테스트 | EC2 컨테이너 상태 확인, 재시작, 로그 분석 |

#### 주제 5: Portainer의 운영 역할
- 서비스가 정상적으로 동작하는지 확인한다.
- 장애가 발생한 컨테이너의 로그를 확인한다.
- 필요한 컨테이너를 재시작한다.
- 새 이미지를 Pull하고 컨테이너를 다시 실행한다.
- 볼륨과 네트워크 연결 상태를 확인한다.

> Portainer는 컨테이너를 실행하는 엔진이 아니라 Docker 환경을 관리하는 운영 도구이다.

#### 주제 6: Portainer의 구조

[이미지 위치: Portainer Server, Agent, Docker Engine 구조]

| 구성 요소 | 역할 |
| --- | --- |
| Portainer Server | 웹 UI와 관리 기능을 제공하는 중심 서버 |
| Docker Engine | 실제 컨테이너, 이미지, 볼륨, 네트워크를 실행하고 관리하는 엔진 |
| Portainer Agent | 원격 Docker 서버의 정보를 Portainer Server에 제공하는 에이전트 |
| Edge Agent | 외부에서 직접 접근하기 어려운 원격 환경을 관리할 때 사용하는 방식 |

- 단일 서버 환경에서는 한 EC2에 Portainer 컨테이너를 실행하고 같은 서버의 Docker Engine을 관리할 수 있다.
- 여러 서버를 관리할 때는 각 서버의 Portainer Agent와 연결하는 구조를 사용할 수 있다.

#### 주제 7: Docker Socket
- Linux에서 Docker CLI가 Docker 데몬과 통신할 때 사용하는 Unix Socket 경로는 다음과 같다.

```bash
/var/run/docker.sock
```

- Docker Socket은 Docker API와 통신하는 경로이다.
- Portainer 컨테이너에 Docker Socket을 마운트하면 해당 Docker Engine을 제어할 수 있다.

```text
Portainer UI
-> Portainer Server
-> Docker Socket 또는 Portainer Agent
-> Docker Engine
-> 컨테이너, 이미지, 볼륨, 네트워크 제어
```

#### 주제 8: Docker Socket과 Portainer 보안
- Docker Socket은 매우 강한 권한을 제공한다.
- Socket에 접근할 수 있으면 컨테이너 생성, 중지, 삭제뿐 아니라 호스트 디렉터리 마운트와 민감한 환경변수 조회가 가능할 수 있다.
- 결과적으로 Docker Engine이 설치된 호스트에 큰 권한으로 접근할 수 있으므로 노출 범위를 엄격하게 제한해야 한다.

> Portainer 관리 화면과 Docker Socket을 외부 인터넷에 그대로 노출하면 안 된다.

- 가능한 경우 Portainer를 Private Subnet에 둔다.
- VPN이나 Bastion Host를 통해서만 접근한다.
- 직접 접근이 필요하다면 특정 IP 대역만 허용한다.
- Admin 계정을 공유하지 않는다.
- Portainer 관련 보안 설정과 접근 기록을 관리한다.

#### 주제 9: 실무에서 Portainer를 사용하는 경우

##### 1. 운영 가시성 확보
- 장애가 발생하면 어떤 컴포넌트와 컨테이너가 중지되었는지 빠르게 확인해야 한다.
- Portainer에서 컨테이너의 실행, 중지, 삭제 상태를 확인할 수 있다.
- 자동 재시작이 설정된 컨테이너의 재시작 횟수가 비정상적으로 높은지 살펴볼 수 있다.
- 실행 중인 컨테이너가 어떤 이미지 버전을 사용하는지 확인할 수 있다.
- CPU와 메모리 사용량을 확인할 수 있다.

```text
backend:1.0.0
backend:1.0.1
```

##### 2. 개발자와 DevOps의 협업
- 개발자는 코드를 작성하고 CI/CD 파이프라인과 테스트 결과를 확인한다.
- DevOps 담당자는 실제 배포가 안정적으로 이루어졌는지 운영 관점에서 확인한다.
- 개발자도 장애 원인을 찾기 위해 컨테이너 로그를 확인해야 한다.
- 컨테이너가 많아 CLI만으로 확인하기 어려울 때 Portainer가 공통 관리 화면을 제공한다.

##### 3. 소규모 운영 환경
- 중앙 집중형 로그와 메트릭 시스템은 강력하지만 설치와 운영이 무거울 수 있다.
- 소수의 EC2와 컨테이너를 운영하는 환경에서는 Portainer로 기본 상태, 자원 사용량, 개별 로그를 확인하는 방식이 실용적일 수 있다.
- 다만 Portainer는 전문적인 중앙 로그 수집이나 장기 모니터링 시스템을 완전히 대체하는 도구는 아니다.

#### 주제 10: Portainer 사용 시 주의 사항

##### 1. GUI에서 변경하면 실제 환경이 바뀐다
- 화면의 버튼을 누르는 행위가 실제 Docker 설정과 컨테이너 상태를 변경한다.
- 조작이 쉬운 만큼 삭제, 재시작, 네트워크 변경을 신중하게 수행해야 한다.

##### 2. RBAC로 권한을 분리한다
- RBAC는 Role-Based Access Control의 약자로, 역할에 따라 사용자의 권한을 관리하는 방식이다.
- 모든 사용자에게 관리자 권한을 주지 않고 업무에 필요한 권한만 부여한다.
- 실수할 수 있는 환경 자체를 줄이는 예방 설정이 중요하다.

##### 3. 관리 화면의 접근 범위를 제한한다
- Portainer는 가능한 한 Private Subnet에 둔다.
- VPN 또는 Bastion Host를 통해 접근한다.
- Admin 계정은 공유하지 않는다.

#### 주제 12: Docker Volume이란 무엇인가
- Docker Volume은 컨테이너 데이터의 영속성과 공유를 위해 호스트 측에 생성되는 독립적인 저장소이다.
- 컨테이너의 생명 주기와 데이터를 분리해 컨테이너를 삭제하거나 다시 만들어도 데이터를 유지할 수 있게 한다.

#### 주제 13: 컨테이너 내부에 파일을 저장하면 생기는 일
- MySQL 컨테이너는 기본적으로 `/var/lib/mysql`에 데이터를 저장한다.

```bash
docker run -d \
  --name mysql-test \
  -e MYSQL_ROOT_PASSWORD=1234 \
  mysql:8.0
```

```text
/var/lib/mysql
```

- 컨테이너를 중지했다가 같은 컨테이너를 다시 시작하면 데이터가 유지된다.
- 하지만 컨테이너를 삭제하면 컨테이너의 쓰기 가능한 레이어도 함께 삭제된다.

```bash
docker rm mysql-test
```

> 컨테이너 자체의 쓰기 레이어는 영속적인 저장소가 아니다.

#### 주제 14: 컨테이너 데이터가 삭제되는 이유
- 컨테이너는 읽기 전용 이미지 위에 쓰기 가능한 레이어를 추가해 동작한다.
- 실행 중 파일을 생성하거나 수정하면 변경 사항은 이미지가 아니라 컨테이너의 쓰기 레이어에 저장된다.
- 이 쓰기 레이어는 컨테이너의 생명 주기에 묶여 있다.

| 상황 | 데이터 상태 |
| --- | --- |
| 컨테이너 실행 중 | 컨테이너 내부 변경 사항 유지 |
| 컨테이너 중지 | 컨테이너가 남아 있으면 데이터도 유지 |
| 같은 컨테이너 재시작 | 기존 데이터 유지 |
| 컨테이너 삭제 | 컨테이너 쓰기 레이어도 삭제 |
| 새 컨테이너 생성 | 이전 컨테이너 내부 데이터가 이어지지 않음 |

#### 주제 15: 컨테이너가 비영속적으로 설계된 이유
- 컨테이너는 빠르게 생성하고 삭제할 수 있어야 한다.
- 같은 이미지로 언제든 동일한 실행 환경을 재현할 수 있어야 한다.
- 테스트, 배치, 임시 작업처럼 실행 후 제거하는 작업에 적합해야 한다.
- 서버마다 프로그램을 직접 설치하지 않고 이미지로 배포할 수 있어야 한다.

| 목적 | 설명 |
| --- | --- |
| 빠른 생성 | 컨테이너를 빠르게 만들 수 있음 |
| 빠른 삭제 | 필요 없어진 컨테이너를 쉽게 제거할 수 있음 |
| 동일한 실행 환경 | 이미지로 언제든 같은 환경을 재현할 수 있음 |
| 일회성 실행 | 테스트, 배치, 임시 작업에 적합 |
| 배포 단순화 | 서버마다 직접 설치하지 않고 이미지로 실행 |

- 애플리케이션 실행 환경에는 이런 특성이 유용하다.
- 문제가 생긴 백엔드 컨테이너를 삭제하고 같은 이미지로 빠르게 다시 만들 수 있다.

```bash
docker rm -f backend
docker run -d --name backend backend:1.3.1
```

- 영속성이 필요한 데이터는 RDS 같은 외부 관리형 서비스나 Docker Volume처럼 컨테이너 생명 주기와 분리된 저장소에 두어야 한다.

#### 주제 16: Volume으로 영속성을 확보하는 방법
- 데이터를 컨테이너의 쓰기 레이어가 아니라 호스트의 Docker Volume에 저장한다.
- 컨테이너에서는 `/var/lib/mysql`에 저장하는 것처럼 보이지만 실제 데이터는 호스트 측 볼륨에 기록된다.
- 컨테이너를 삭제하고 새로 만들어도 같은 볼륨을 다시 연결하면 기존 데이터를 사용할 수 있다.

```bash
docker run -d \
  --name mysql-test \
  -e MYSQL_ROOT_PASSWORD=1234 \
  -v mysql-data:/var/lib/mysql \
  mysql:8.0
```

| 부분 | 의미 |
| --- | --- |
| `mysql-data` | Docker가 호스트 측에서 관리하는 Volume 이름 |
| `/var/lib/mysql` | 컨테이너 내부에서 MySQL이 데이터를 저장하는 경로 |
| `:` | 왼쪽 저장소를 오른쪽 경로에 마운트한다는 의미 |

#### 주제 17: Volume을 사용하는 이유

| 사용 이유 | 설명 |
| --- | --- |
| 데이터 영속성 | 컨테이너를 삭제하거나 재생성해도 데이터 유지 |
| 재배포 안전성 | 새 컨테이너에서도 기존 데이터 재사용 가능 |
| 데이터 공유 | 같은 호스트의 여러 컨테이너가 동일한 볼륨 사용 가능 |
| 저장 위치 관리 | 호스트 경로를 직접 지정하지 않아도 Docker가 관리 |
| 운영 안정성 | DB, 업로드 파일, 설정 데이터, 로그 등 보호 |

#### 주제 18: Volume 기본 명령어

```bash
# 볼륨 생성
docker volume create mysql-data

# 볼륨 목록 확인
docker volume ls

# 볼륨 상세 정보 확인
docker volume inspect mysql-data

# 볼륨을 컨테이너에 연결
docker run -d \
  --name mysql-test \
  -e MYSQL_ROOT_PASSWORD=1234 \
  -v mysql-data:/var/lib/mysql \
  mysql:8.0
```

#### 주제 19: Named Volume과 Bind Mount
- `-v` 또는 `--volume` 옵션은 기본적으로 `[호스트 측 저장소]:[컨테이너 내부 경로]` 형식으로 사용한다.

##### Named Volume
- 왼쪽에 볼륨 이름을 지정하면 Docker가 실제 저장 위치를 관리한다.

```bash
-v mysql-data:/var/lib/mysql
```

- Linux Docker Engine에서는 일반적으로 Docker 관리 디렉터리 아래에 데이터가 저장된다.

```text
/var/lib/docker/volumes/mysql-data/_data
```

- macOS의 Docker Desktop은 Linux 가상 머신 안에서 Docker Engine을 실행하므로 macOS 터미널에서 이 경로가 그대로 보이지 않을 수 있다.

##### Bind Mount
- 호스트의 특정 파일이나 디렉터리를 직접 연결하려면 왼쪽에 절대 경로를 사용한다.

```bash
-v /Users/lee-ych/kakaotech_bootcamp/db_data:/var/lib/mysql
```

| 구분 | Named Volume | Bind Mount |
| --- | --- | --- |
| 호스트 측 표기 | 볼륨 이름 | 파일 또는 디렉터리 절대 경로 |
| 저장 위치 관리 | Docker | 사용자 |
| 대표 예시 | DB 데이터, 애플리케이션 데이터 | 설정 파일, 개발 소스, 지정된 호스트 폴더 |

#### 주제 20: 실무에서 Volume을 사용하는 경우

##### 1. 데이터베이스 컨테이너
- MySQL, Redis처럼 데이터를 유지해야 하는 컨테이너에 사용한다.
- 운영 데이터베이스는 요구되는 안정성에 따라 RDS 같은 관리형 서비스를 사용하는 방안도 함께 고려한다.

##### 2. 파일 업로드와 임시 파일
- 같은 호스트에서 실행되는 여러 WAS 컨테이너가 공통 임시 파일을 공유해야 할 때 볼륨을 연결할 수 있다.
- 서로 다른 EC2의 컨테이너가 파일을 공유해야 한다면 단일 호스트의 Named Volume만으로는 부족하므로 EFS나 S3 같은 외부 저장소가 필요하다.

##### 3. 설정 파일 마운트
- Nginx 설정 파일이나 Spring 환경 설정 파일 등을 컨테이너에 연결할 수 있다.

##### 4. 로그 보관
- 컨테이너 내부에만 로그를 저장하면 컨테이너 삭제 시 로그도 함께 사라진다.
- 로그 디렉터리를 볼륨에 연결하면 컨테이너를 교체한 뒤에도 로그를 보존할 수 있다.

#### 주제 21: Portainer와 Volume의 연결
- Portainer에서는 Docker Volume을 생성하고 조회하며 컨테이너에 연결할 수 있다.
- 컨테이너 상태뿐 아니라 어떤 볼륨과 네트워크가 연결되어 있는지 화면에서 확인할 수 있다.
- GUI 조작은 실제 Docker 환경을 변경하므로 볼륨 삭제나 연결 해제 역시 신중해야 한다.

#### 주제 22: Docker Volume 핵심 정리

| 항목 | 내용 |
| --- | --- |
| Volume | 컨테이너 데이터의 영속성과 공유를 위한 호스트 측 저장소 |
| 필요한 이유 | 컨테이너 삭제 시 쓰기 레이어도 함께 삭제되기 때문 |
| Named Volume | Docker가 저장 위치를 관리하는 이름 기반 볼륨 |
| Bind Mount | 사용자가 지정한 호스트 경로를 직접 연결하는 방식 |
| 기본 문법 | `-v 호스트측저장소:컨테이너경로` |
| 대표 사용처 | DB 데이터, 업로드 파일, 설정 파일, 로그 |
| 범위 주의 | 일반 Named Volume은 해당 Docker 호스트에 속함 |
