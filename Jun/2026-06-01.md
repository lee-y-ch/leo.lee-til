### 새로 배운 내용

#### 주제 1: Spring
- Spring은 대규모 Java 애플리케이션을 더 편리하게 개발할 수 있도록 도와주는 프레임워크이다.
- 객체지향 설계를 지원하고, 개발자가 비즈니스 로직에 더 집중할 수 있도록 반복적인 설정과 기반 기능을 제공한다.
- Spring의 대표적인 특징에는 AOP, IoC, DI, POJO, Bean 관리가 있다.
- AOP(Aspect-Oriented Programming)는 로깅, 트랜잭션처럼 여러 곳에서 반복되는 공통 관심사를 비즈니스 로직과 분리하는 방식이다.
- IoC(Inversion of Control)는 객체 생성과 생명주기 관리의 제어권을 개발자가 아닌 프레임워크 컨테이너가 가지는 것이다.
- DI(Dependency Injection)는 객체가 필요한 의존성을 직접 생성하지 않고 외부에서 주입받는 방식이다.
- IoC와 DI를 사용하면 객체 간 결합도를 낮추고, 변경과 테스트를 쉽게 만들 수 있다.
- POJO(Plain Old Java Object)는 특정 프레임워크 클래스 상속이나 과도한 규칙에 종속되지 않은 평범한 Java 객체이다.
- Bean은 Spring 컨테이너가 생성하고 관리하는 객체이다.

#### 주제 2: Spring Boot
- Spring Boot는 Spring을 대체하는 기술이 아니라, Spring 애플리케이션을 더 쉽고 빠르게 시작할 수 있도록 돕는 도구이다.
- Spring Boot의 핵심 기능에는 자동 설정, Starter Dependencies, 내장 서버가 있다.
- Auto-Configuration은 클래스패스에 포함된 라이브러리를 바탕으로 자주 사용하는 Bean과 설정을 자동으로 구성한다.
- 예를 들어 `spring-boot-starter-web` 의존성이 있으면 Spring MVC와 내장 Tomcat 구성을 자동으로 준비한다.
- Starter Dependencies는 웹, 데이터베이스, 보안처럼 목적별로 자주 함께 사용하는 라이브러리를 묶어서 제공한다.
- JPA를 사용하려면 일반적으로 `spring-boot-starter-data-jpa`를 추가한다.
- Spring Boot는 내장 서버를 제공하므로 외부 WAS에 WAR 파일을 별도로 배포하지 않고도 실행 가능한 JAR 파일 하나로 애플리케이션을 구동할 수 있다.

#### 주제 3: 어노테이션
- 어노테이션은 사람이 읽는 설명이면서 컴파일러, 런타임, 프레임워크가 읽을 수 있는 메타데이터이다.
- 어노테이션 자체가 비즈니스 로직을 수행하는 것은 아니다.
- 대신 컴파일러나 Spring, JPA 같은 프레임워크가 어노테이션을 읽고 정해진 동작을 수행한다.
- 예를 들어 `@Override`는 부모 클래스의 메서드를 올바르게 재정의했는지 컴파일 시점에 검증한다.

```java
class Child extends Parent {
    @Override
    void gret() {
        System.out.println("Hello from Child");
    }
}
```

- 위 코드처럼 메서드 이름에 오타가 있으면 컴파일 에러가 발생하므로 실수를 빠르게 발견할 수 있다.
- `@Deprecated`는 더 이상 권장하지 않는 API임을 알린다.
- `@SuppressWarnings`는 의도적으로 무시할 경고를 지정한다.
- Lombok의 `@Getter`, `@Setter`, `@NoArgsConstructor`도 코드를 자동 생성하는 어노테이션이므로 의미를 이해하고 사용해야 한다.
- 어노테이션을 사용하면 코드와 설정을 가까이 둘 수 있고, 정적 검증과 런타임 검증을 자동화할 수 있다.

#### 주제 4: ORM
- ORM(Object-Relational Mapping)은 객체와 관계형 데이터베이스 테이블을 연결하고 변환하는 기술이다.
- Java 애플리케이션은 객체지향 모델을 사용하지만, 관계형 데이터베이스는 테이블과 외래키를 중심으로 데이터를 관리한다.
- ORM은 이 차이를 중간에서 연결해 객체 중심으로 데이터를 저장하고 조회할 수 있게 한다.
- JDBC만 직접 사용하면 연결 관리, SQL 작성, 결과 매핑 코드를 반복해서 작성해야 한다.
- ORM을 사용하면 객체 상태와 매핑 정보를 바탕으로 SQL을 생성하고 실행할 수 있다.
- 개발자는 반복적인 SQL 매핑 작업을 줄이고 도메인 로직에 더 집중할 수 있다.

#### 주제 5: 객체와 관계형 데이터베이스의 차이
- 객체지향 모델과 관계형 데이터베이스는 데이터를 바라보는 방식이 다르다.
- Java에서는 상속과 다형성을 사용할 수 있지만, 관계형 데이터베이스에는 동일한 형태의 상속 개념이 없다.
- Java 객체는 다른 객체를 참조해서 관계를 표현한다.
- 객체 참조는 기본적으로 단방향이다.
- 관계형 데이터베이스는 외래키와 JOIN을 사용해 테이블 사이 관계를 표현한다.
- 외래키를 기준으로 양쪽 테이블에서 JOIN할 수 있다.
- 객체는 참조를 따라 그래프 형태로 탐색하지만, 데이터베이스는 SQL에 따라 필요한 범위의 데이터를 조회한다.
- ORM은 이런 차이를 매핑 규칙과 프록시, 영속성 컨텍스트 같은 기능으로 연결한다.

#### 주제 6: JPA와 Hibernate
- JPA(Java Persistence API)는 Java에서 ORM을 사용하기 위한 표준 명세이다.
- JPA는 엔티티 관리, 저장, 조회, 연관관계 매핑, 어노테이션 사용 방식 같은 규칙과 인터페이스를 정의한다.
- JPA 자체가 실제 SQL을 실행하는 엔진은 아니다.
- Hibernate는 JPA 명세를 구현한 대표적인 ORM 프레임워크이다.
- 개발자는 보통 JPA 인터페이스를 사용하고, 내부에서는 Hibernate 같은 구현체가 SQL을 생성해 JDBC를 통해 DB에 전달한다.
- JDBC(Java Database Connectivity)는 Java 애플리케이션과 데이터베이스를 연결하는 표준 통로이다.

#### 주제 7: Entity
- Entity는 JPA가 관리하며 데이터베이스 테이블과 매핑되는 Java 객체이다.
- 일반적으로 엔티티 객체 하나는 테이블의 행 하나에 대응한다.
- `@Entity`가 붙은 클래스는 JPA가 관리하는 엔티티로 인식된다.
- `@Id`는 엔티티를 구분하는 식별자를 지정한다.
- `@Column`은 필드와 DB 컬럼의 이름, null 허용 여부, 유일성 같은 속성을 설정할 때 사용한다.

```java
@Entity
public class User {
    @Id
    private Long id;

    private String email;
    private String password;
    private String nickname;

    protected User() {}

    public User(String email, String password, String nickname) {
        this.email = email;
        this.password = password;
        this.nickname = nickname;
    }
}
```

- 엔티티는 데이터 필드만 담는 객체라기보다, 해당 데이터가 지켜야 할 규칙과 핵심 비즈니스 동작을 응집할 수 있는 객체이다.
- 엔티티의 상태를 변경할 때는 무분별한 Setter보다 의도가 드러나는 메서드를 사용하는 것이 좋다.

#### 주제 8: Entity 작성 규칙
- JPA Entity에는 매개변수가 없는 기본 생성자가 필요하다.
- 기본 생성자는 `public` 또는 `protected`로 선언해야 한다.
- 보통 외부에서 무분별하게 호출하지 못하도록 `protected`를 사용한다.
- Entity 클래스는 `final`로 선언하지 않는 것이 좋다.
- JPA가 지연 로딩을 위해 프록시 객체를 만들 때 상속 가능한 클래스와 메서드가 필요할 수 있기 때문이다.
- `enum`, `interface`, 내부 클래스는 Entity로 지정할 수 없다.
- 영속 상태로 저장할 필드는 `final`로 선언하지 않는다.
- JPA 규칙을 지켜야 구현체가 Entity를 생성하고 상태를 관리할 수 있다.

#### 주제 9: DTO
- DTO(Data Transfer Object)는 계층 간 데이터 전달을 위해 사용하는 값 중심 객체이다.
- Entity에는 비밀번호처럼 외부에 노출하면 안 되는 정보가 포함될 수 있다.
- Entity를 API 응답으로 직접 반환하면 보안 문제와 계층 결합 문제가 생길 수 있다.
- DTO를 사용하면 요청과 응답에 필요한 필드만 선택할 수 있다.
- DTO는 데이터 전달에 집중하고, DB 접근이나 핵심 비즈니스 로직을 포함하지 않는 것이 좋다.
- Request DTO와 Response DTO를 분리하면 API 규격을 명확하게 표현할 수 있다.

```java
public record UserResponse(
    Long id,
    String email,
    String nickname
) {}
```

- 위 DTO에는 `password`가 없으므로 민감한 정보가 응답에 포함되는 것을 막을 수 있다.

#### 주제 10: Entity 조회 후 DTO 변환과 DTO 직접 조회
- JPA에서 DTO를 만드는 방식은 크게 두 가지이다.
- 첫 번째 방식은 Entity를 조회한 뒤 Service 계층 등에서 필요한 필드만 DTO로 변환하는 것이다.

```java
List<MemberDto> result = memberRepository.findAll().stream()
    .map(member -> new MemberDto(member.getName(), member.getEmail()))
    .toList();
```

- 이 방식은 Repository를 재사용하기 쉽고 구조가 단순하다.
- 하지만 필요한 필드가 적더라도 Entity 전체를 로딩할 수 있어 대량 조회에서는 비효율적일 수 있다.
- 두 번째 방식은 JPQL이나 QueryDSL을 사용해 DTO에 필요한 필드만 직접 조회하는 것이다.

```java
@Query("select new com.example.MemberDto(m.name, m.email) from Member m")
List<MemberDto> findMemberDtos();
```

- DTO 직접 조회는 불필요한 데이터 로딩을 줄일 수 있어 조회 성능 최적화가 필요한 경우 유용하다.
- 대신 쿼리가 DTO 구조에 의존하므로 요구사항 변경 시 함께 수정해야 할 수 있다.
- 일반적인 CRUD에서는 Entity 조회 후 DTO 변환을 우선 고려하고, 조회 성능 최적화가 필요한 지점에서는 DTO 직접 조회를 선택할 수 있다.

#### 주제 11: JPQL과 QueryDSL
- JPQL(Java Persistence Query Language)은 테이블이 아니라 Entity 객체와 필드를 대상으로 작성하는 객체지향 쿼리 언어이다.
- SQL과 문법이 비슷하지만 DB 테이블 이름 대신 Entity 이름을 사용한다.
- QueryDSL은 Java 코드로 타입 안전한 쿼리를 작성할 수 있도록 돕는 라이브러리이다.
- 문자열 기반 JPQL보다 컴파일 시점에 오류를 발견하기 쉽고, 동적 쿼리를 읽기 좋게 작성할 수 있다.

#### 주제 12: @Id와 기본 키 생성 전략
- `@Id`는 Entity의 식별자를 지정하는 어노테이션이다.
- DB 테이블의 Primary Key와 연결되며, 영속성 컨텍스트에서 Entity를 구분하는 기준이 된다.
- 식별자는 개발자가 직접 할당하거나 자동 생성 전략을 사용할 수 있다.

```java
@Entity
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
}
```

- `@GeneratedValue`를 사용하면 DB 또는 JPA 구현체에 기본 키 생성을 위임할 수 있다.
- 주요 전략에는 `IDENTITY`, `SEQUENCE`, `TABLE`, `AUTO`가 있다.
- `IDENTITY`는 MySQL의 `AUTO_INCREMENT`처럼 DB 자동 증가 컬럼에 식별자 생성을 위임한다.
- `IDENTITY`는 INSERT를 실행해야 생성된 ID를 알 수 있으므로, `persist()` 시점에 INSERT가 실행될 수 있다.
- 이 특성 때문에 INSERT 배치 처리와 쓰기 지연 활용에 제약이 생길 수 있다.
- `SEQUENCE`는 DB가 제공하는 Sequence Object를 사용해 ID를 미리 가져오는 방식이다.
- `allocationSize`를 사용하면 일정 범위의 ID를 미리 확보해 DB 접근 횟수를 줄일 수 있다.
- `TABLE`은 키 생성 전용 테이블을 만들어 Sequence와 비슷한 동작을 구현한다.
- `TABLE` 전략은 DB 종류와 무관하게 사용할 수 있지만 추가 조회와 갱신 비용이 있어 일반적으로 느리다.
- `AUTO`는 DB 종류와 JPA 구현체에 맞춰 적절한 전략을 선택하도록 위임한다.

#### 주제 13: @Column, @Enumerated, @Transient
- `@Column`은 Entity 필드가 DB 컬럼에 어떤 이름과 속성으로 저장될지 지정한다.
- 대표 속성에는 `name`, `nullable`, `unique` 등이 있다.
- `@Enumerated`는 Enum 값을 DB에 저장하는 방식을 지정한다.
- `EnumType.ORDINAL`은 Enum 순서를 숫자로 저장하지만, Enum 순서가 바뀌면 기존 데이터 의미가 달라질 수 있다.
- 일반적으로는 읽기 쉽고 변경에 더 안전한 `EnumType.STRING` 사용을 우선 고려한다.
- `@Transient`는 Entity 안에 존재하지만 DB에는 저장하지 않을 필드를 지정한다.

#### 주제 14: 영속성 컨텍스트
- 영속성 컨텍스트(Persistence Context)는 JPA가 Entity를 관리하는 논리적인 공간이다.
- EntityManager를 통해 Entity를 저장, 조회, 수정, 삭제하면 영속성 컨텍스트가 Entity 상태를 추적한다.
- 영속성 컨텍스트는 1차 캐시, 쓰기 지연, 변경 감지 같은 기능을 제공한다.
- 보통 하나의 트랜잭션 범위 안에서 Entity를 관리하며, 트랜잭션이 커밋될 때 DB와 동기화된다.

#### 주제 15: 1차 캐시
- 1차 캐시는 Entity와 식별자를 Map 형태로 저장하는 영속성 컨텍스트 내부 캐시이다.
- 같은 영속성 컨텍스트 안에서 이미 조회한 Entity를 다시 찾으면 DB를 다시 조회하지 않고 1차 캐시의 객체를 반환할 수 있다.

```java
entityManager.persist(user);
entityManager.find(User.class, user.getId());
```

- 1차 캐시는 보통 트랜잭션 범위가 짧기 때문에 애플리케이션 전체에서 공유하는 캐시와는 다르다.
- 같은 트랜잭션 안에서 동일한 Entity의 일관성을 유지하는 데 의미가 있다.

#### 주제 16: 쓰기 지연과 flush
- 쓰기 지연(Write-behind)은 Entity 변경에 필요한 SQL을 즉시 DB로 보내지 않고 모아두었다가 나중에 반영하는 기능이다.
- `persist()`를 호출하면 Entity는 1차 캐시에 저장되고, INSERT SQL은 쓰기 지연 SQL 저장소에 쌓일 수 있다.
- `flush()`가 호출되면 영속성 컨텍스트의 변경 내용이 DB에 SQL로 반영된다.
- 보통 트랜잭션 커밋 직전에 flush가 자동으로 실행된다.
- flush는 영속성 컨텍스트의 내용을 DB와 동기화하는 것이며, 트랜잭션을 커밋하는 것과 동일한 의미는 아니다.
- 아직 커밋되지 않은 데이터는 다른 트랜잭션에서 일반적으로 조회할 수 없다.

#### 주제 17: 변경 감지
- 변경 감지(Dirty Checking)는 영속 상태 Entity의 변경을 추적해 자동으로 UPDATE SQL을 생성하는 기능이다.
- JPA는 Entity가 영속성 컨텍스트에 들어올 때 초기 상태의 스냅샷을 저장한다.
- flush 시점에 현재 Entity와 스냅샷을 비교한다.
- 값이 달라졌다면 UPDATE SQL을 생성해 DB에 반영한다.
- Entity를 여러 번 수정해도 flush 전에 최종 상태를 기준으로 DB에 반영할 수 있다.

```java
@Transactional
public void updateNickname(Long id, String nickname) {
    User user = entityManager.find(User.class, id);
    user.changeNickname(nickname);
}
```

- 위 코드처럼 영속 상태 Entity를 수정하면 별도의 update 메서드를 호출하지 않아도 변경 감지가 동작할 수 있다.

#### 주제 18: Entity의 네 가지 상태
- 비영속(New/Transient) 상태는 객체가 생성되었지만 영속성 컨텍스트가 관리하지 않는 상태이다.
- 영속(Managed) 상태는 Entity가 영속성 컨텍스트에 저장되어 관리되는 상태이다.
- 영속 상태의 Entity는 1차 캐시, 쓰기 지연, 변경 감지의 대상이 된다.
- 준영속(Detached) 상태는 이전에는 관리되었지만 현재 영속성 컨텍스트에서 분리된 상태이다.
- `entityManager.detach(entity)`를 호출하거나 영속성 컨텍스트가 종료되면 Entity는 준영속 상태가 될 수 있다.
- 준영속 Entity의 이후 변경은 자동으로 DB에 반영되지 않는다.
- 아직 flush되지 않은 변경 사항을 확실히 반영해야 한다면 detach 전에 flush 여부를 확인해야 한다.
- 삭제(Removed) 상태는 Entity가 삭제 대상으로 예약된 상태이다.
- `entityManager.remove(entity)`를 호출하면 삭제 상태가 되고, flush 시점에 DELETE SQL이 실행된다.

#### 주제 19: 영속성 컨텍스트와 동시성
- 영속성 컨텍스트는 보통 트랜잭션마다 별도로 존재한다.
- 서로 다른 트랜잭션은 같은 DB row를 각각 별도의 Entity 객체로 읽을 수 있다.
- 두 트랜잭션이 같은 데이터를 수정한 뒤 순서대로 커밋하면 나중에 반영된 변경이 앞선 변경을 덮어쓰는 Lost Update가 발생할 수 있다.
- 이런 상황에서는 비관적 락이나 `@Version`을 사용한 낙관적 락 같은 동시성 제어 전략을 고려해야 한다.

#### 주제 20: 연관관계 매핑
- 연관관계 매핑은 테이블의 외래키 관계를 Entity 사이의 참조 관계로 표현하는 방법이다.
- 객체 간 관계를 DB 외래키와 연결하면 객체지향적으로 연관 데이터를 탐색할 수 있다.
- 단방향 연관관계는 한 Entity에서만 다른 Entity를 참조하는 방식이다.
- 참조 필드를 가진 쪽에서는 반대 Entity를 탐색할 수 있지만, 반대쪽에서는 접근할 수 없다.
- 데이터베이스에서는 외래키를 이용해 어느 방향으로든 JOIN할 수 있지만, 객체에서는 참조 필드가 있어야 탐색할 수 있다.
- 양방향 연관관계는 두 Entity가 서로를 참조하는 방식이다.
- 양방향 관계에서는 연관관계의 주인을 정하고, 양쪽 참조가 일치하도록 관리해야 한다.
- 처음에는 단방향으로 단순하게 설계하고, 반대 방향 탐색이 실제로 필요할 때 양방향 관계를 추가하는 것이 좋다.

#### 주제 21: 프록시와 지연 로딩
- 프록시는 JPA가 지연 로딩을 구현하기 위해 실제 Entity 대신 먼저 전달하는 가짜 객체이다.
- 연관 Entity가 당장 필요하지 않다면 JPA는 DB를 즉시 조회하지 않고 프록시를 넣어둘 수 있다.
- 이후 실제 데이터에 접근하는 시점에 DB 조회가 실행된다.
- 이를 지연 로딩(Lazy Loading)이라고 한다.
- 즉시 로딩(Eager Loading)은 연관 Entity를 즉시 조회하는 방식이다.
- 즉시 로딩은 상황에 따라 JOIN 또는 추가 SELECT를 발생시킬 수 있다.
- 불필요한 데이터 조회와 예상하지 못한 쿼리를 피하기 위해 실무에서는 연관관계를 기본적으로 LAZY로 설정하고, 필요한 시점에 Fetch Join 등으로 명시적으로 조회하는 방식을 많이 사용한다.

#### 주제 22: N+1 문제
- N+1 문제는 Entity 목록을 조회하는 1번의 쿼리 이후, 각 Entity의 연관 데이터를 조회하기 위해 N번의 추가 쿼리가 실행되는 문제이다.
- 예를 들어 사용자 목록을 조회한 뒤 반복문에서 각 사용자의 팀 이름에 접근하면 사용자 수만큼 팀 조회 쿼리가 추가로 실행될 수 있다.

```java
for (User user : users) {
    System.out.println(user.getTeam().getName());
}
```

- 사용자가 1,000명이라면 최초 사용자 목록 조회 1번과 팀 조회 최대 1,000번이 실행될 수 있다.
- N+1 문제는 연관관계 로딩 전략과 실제 객체 접근 시점을 함께 고려해야 발견할 수 있다.
- EAGER로 설정했다고 N+1 문제가 항상 해결되는 것은 아니다.

#### 주제 23: N+1 해결 방법
- Fetch Join은 JPQL에서 필요한 연관 Entity를 한 번의 쿼리로 함께 조회하는 방식이다.
- Fetch Join을 사용하면 여러 번 발생할 쿼리를 줄일 수 있다.

```java
select user
from User user
join fetch user.team
```

- Batch Size를 설정하면 지연 로딩이 필요한 연관 Entity를 일정 개수씩 묶어서 조회할 수 있다.
- 대량 조회에서는 페이징과 조회 전용 DTO를 함께 고려할 수 있다.
- 컬렉션 Fetch Join과 페이징을 함께 사용할 때는 데이터 중복과 메모리 페이징 문제에 주의해야 한다.
- 조회 목적과 데이터 규모에 맞춰 Fetch Join, Batch Size, DTO 직접 조회, 페이징을 선택해야 한다.

#### 주제 24: 연관관계의 기본 로딩 전략
- JPA 기본 설정에서 `@ManyToOne`과 `@OneToOne`은 EAGER이다.
- `@OneToMany`와 `@ManyToMany`는 LAZY이다.
- 하지만 실무에서는 예측하기 어려운 쿼리를 줄이기 위해 `@ManyToOne`과 `@OneToOne`도 LAZY로 명시하는 경우가 많다.
- 이후 실제 사용 시점에 필요한 조회 방식만 명확하게 선택하는 것이 성능 관리에 유리하다.
