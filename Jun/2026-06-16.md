# TIL

## 날짜: 2026-06-16
## 소제목: Inline, Out-of-Path, Wireshark를 통한 네트워크 트래픽 이해

### 새로 배운 내용

#### 주제 1: 네트워크 장비는 어디에 놓이는지가 중요하다
- 네트워크 장비를 이해할 때는 장비가 어떤 기능을 하는지도 중요하지만, 트래픽 흐름상 어디에 놓이는지도 중요하다.
- 같은 보안 장비라도 모든 요청이 반드시 거쳐야 하는 위치에 있으면 트래픽을 직접 제어할 수 있다.
- 반대로 트래픽 경로 밖에서 복사본만 보는 위치에 있으면 실제 서비스 흐름에는 직접 개입하지 않고 분석 중심으로 동작한다.
- 따라서 네트워크 장비를 볼 때는 "이 장비가 무엇을 하는가?"뿐 아니라 "트래픽이 이 장비를 반드시 지나가는가?"도 함께 봐야 한다.

#### 주제 2: Inline 방식
- Inline 방식은 네트워크 상의 데이터 패킷이 반드시 해당 장치를 통과하도록 설계된 네트워크 구조이다.
- 트래픽이 지나가는 경로 위에 장비를 배치하여 요청과 응답이 항상 그 장비를 거치도록 만든다.
- 예를 들어 사용자의 요청이 서버로 가기 전에 반드시 보안 장비를 거치도록 구성하면 Inline 구조라고 볼 수 있다.

```text
사용자 -> 인터넷 -> 보안 장비 -> 서버
```

- Inline 방식은 네트워크의 검문소와 비슷하다.
- 목적지로 가려면 반드시 검문소를 거쳐야 하듯, 서버로 가려면 반드시 Inline 장비를 거쳐야 한다.

#### 주제 3: Inline 방식의 특징
- Inline 구조의 핵심은 강제성이다.
- 트래픽이 Inline 장비를 우회하지 못하고 반드시 거쳐야만 목적지에 도달한다.
- Inline 장비는 트래픽을 직접 제어할 수 있다.
- 예를 들어 요청이 정상인지, 특정 IP가 차단 대상인지, 포트가 허용되었는지, 요청량이 너무 많은지, 악성 패턴이 있는지 판단할 수 있다.
- 판단 결과에 따라 트래픽을 허용하거나, 차단하거나, 필터링하거나, 수정하거나, 로그로 기록할 수 있다.

| 처리 방식 | 의미 |
| --- | --- |
| 허용 | 정상 트래픽을 통과시킴 |
| 차단 | 위험하거나 정책에 맞지 않는 트래픽을 버림 |
| 필터링 | 특정 조건에 따라 트래픽을 제한하거나 조정 |
| 수정 | 필요하면 헤더나 요청 정보를 변경 |
| 기록 | 트래픽 로그를 남김 |

#### 주제 4: Inline 방식을 사용하는 이유
- Inline 방식은 실시간으로 보안을 적용하기 좋다.
- 모든 요청이 장비를 지나가기 때문에 악성 요청을 서버에 도달하기 전에 막을 수 있다.
- IP 기반 차단, 포트 기반 제어, 프로토콜 제어, Rate Limit, 접근 제어 등을 적용할 수 있다.
- 예를 들어 SSH 22번 포트는 사내망에서만 허용하거나, `/admin` 경로는 사내 IP에서만 접근하도록 제한할 수 있다.
- Inline 장비가 서버 앞에 있으면 모든 요청을 서버가 직접 처리하지 않아도 된다.

```text
악성 요청 -> Inline 장비에서 차단
정상 요청 -> Inline 장비 -> 서버
```

- 이런 구조는 백엔드 서버를 보호할 때 유용하며, Reverse Proxy, 방화벽, WAF, 로드밸런서 같은 장비나 구성에서 자주 활용된다.

#### 주제 5: 대표적인 Inline 장비
- 방화벽은 대표적인 Inline 장비이다.
- 보안을 위해 외부 인터넷에서 서버로 들어오는 트래픽이 방화벽을 거치도록 구성한다.

```text
외부 인터넷 -> 방화벽 -> 서버
```

- 방화벽은 HTTPS 443 포트를 허용하거나, 외부에서 DB 3306 포트 접근을 차단하거나, 사내 IP만 SSH 접속을 허용하는 정책을 적용할 수 있다.
- 로드밸런서도 Inline 구조로 배치되는 대표적인 장비이다.
- 로드밸런서는 외부 요청을 여러 WAS 서버로 분배한다.

```text
Client -> Load Balancer -> WAS A/B/C
```

- IPS, WAF, Reverse Proxy도 트래픽 경로 위에 놓이면 Inline 방식으로 동작할 수 있다.

#### 주제 6: Inline 방식의 장점
- Inline 방식은 모든 트래픽이 반드시 장비를 지나기 때문에 정책 적용의 강제성이 높다.
- 악성 요청을 서버 도달 전에 실시간으로 차단할 수 있다.
- 보안 정책이나 접근 제어를 확실하게 적용할 수 있다.
- 통과하거나 차단된 트래픽을 로그로 남길 수 있다.
- Rate Limit, 필터링, 라우팅 등 트래픽 제어가 가능하다.
- 백엔드 서버가 공격 트래픽을 직접 받지 않도록 보호할 수 있다.

#### 주제 7: Inline 방식의 단점과 대응 방법
- Inline 장비는 모든 트래픽이 지나가는 위치에 있기 때문에 병목 지점이 될 수 있다.
- 사용자 요청이 많아지면 Inline 장비가 먼저 처리 지연을 일으킬 수 있다.
- Inline 장비가 죽으면 전체 서비스가 영향을 받을 수 있으므로 SPOF(Single Point of Failure)가 될 수 있다.
- 정책을 잘못 설정하면 정상 트래픽까지 차단되어 서비스 장애가 발생할 수 있다.
- 이를 줄이기 위해 이중화, Failover, Bypass Mode, 로드밸런싱, 정책 테스트, 모니터링, 규칙 최적화가 필요하다.

| 방법 | 설명 |
| --- | --- |
| 이중화 | Inline 장비를 2대 이상 구성 |
| Failover | 장애 발생 시 대기 장비로 자동 전환 |
| Bypass Mode | 장비 장애 시 트래픽을 우회 통과시킴 |
| 로드밸런싱 | 여러 장비로 검사 부하 분산 |
| 정책 테스트 | 운영 반영 전 탐지 모드나 테스트 환경에서 검증 |
| 모니터링 | 지연, 차단 수, 에러율, CPU/메모리 감시 |
| 규칙 최적화 | 불필요하거나 과도한 규칙 제거 |

#### 주제 8: Out-of-Path 방식
- Out-of-Path 방식은 실제 트래픽 경로 밖에서 트래픽 복사본을 받아 분석하는 방식이다.
- Inline 방식이 트래픽이 반드시 지나는 배치 방식이라면, Out-of-Path는 실제 트래픽 경로는 그대로 두고 복사본만 옆으로 보내 분석한다.
- 원본 트래픽이 분석 장비를 직접 통과하지 않기 때문에 서비스 흐름에 직접 개입하지 않는다.
- 분석 장비가 장애를 일으켜도 실제 서비스 트래픽 흐름에는 영향을 적게 준다.

#### 주제 9: Out-of-Path 방식을 사용하는 이유
- Out-of-Path 방식은 서비스 트래픽에 영향을 주지 않고 분석할 수 있다는 장점이 있다.
- 트래픽을 직접 건드리지 않고 복사본만 보기 때문에 모니터링을 안정적으로 수행할 수 있다.
- 탐지, 분석, 기록, 알림에 집중하기 좋다.
- 이상 트래픽을 발견하면 로그를 저장하고, 알림을 발생시키고, 관리자가 확인한 뒤 필요한 조치를 수행하는 방식으로 운영할 수 있다.
- Inline 방식이 "이 트래픽은 이상하니 바로 차단"에 가깝다면, Out-of-Path 방식은 "이 트래픽이 이상하니 기록하고 알려준다"에 가깝다.

#### 주제 10: Out-of-Path 방식의 특징
- Out-of-Path 방식은 실제 트래픽 경로 밖에서 동작한다.
- 원본 트래픽 흐름에 직접 개입하지 않는 비간섭성이 있다.
- 차단보다는 탐지, 분석, 알림, 기록에 적합하다.
- 분석 장비 장애가 서비스 전체 장애로 이어질 가능성이 낮다.
- 분석 장비를 추가하거나 교체하기 비교적 쉽다.
- 단점은 원본 트래픽을 이미 지나가게 두기 때문에 직접 차단에는 한계가 있다는 점이다.
- 대표적인 장비나 도구로 IDS, SIEM, Zeek, Wireshark, Flow Logs 등이 있다.

#### 주제 11: Inline과 Out-of-Path 비교

| 구분 | Inline | Out-of-Path |
| --- | --- | --- |
| 위치 | 실제 트래픽 경로 위 | 실제 트래픽 경로 밖 |
| 원본 트래픽 처리 | 직접 통과시킴 | 복사본을 분석 |
| 차단 능력 | 직접 차단 가능 | 직접 차단은 제한적 |
| 서비스 영향 | 장비 장애 시 서비스 영향 큼 | 분석 장비 장애 시 서비스 영향 작음 |
| 주요 목적 | 제어, 차단, 필터링 | 탐지, 분석, 모니터링 |
| 대표 장비 | 방화벽, IPS, WAF, 로드밸런서 | IDS, SIEM, Zeek, Wireshark, Flow Logs |
| 비유 | 도로 위 검문소 | 도로 옆 CCTV |

- Inline은 막는 구조이고, Out-of-Path는 보는 구조라고 정리할 수 있다.
- 반드시 차단해야 하는 트래픽이면 Inline이 적합하고, 서비스 영향 없이 분석하고 싶다면 Out-of-Path가 적합하다.

#### 주제 12: Wireshark
- Wireshark는 네트워크 문제 분석, 소프트웨어 및 통신 프로토콜 개발, 교육에 쓰이는 오픈 소스 패킷 분석 프로그램이다.
- 네트워크 통신은 눈에 보이지 않는다.
- 브라우저 접속 하나에도 DNS 조회, TCP 연결, TLS Handshake, HTTP 요청, 서버 응답 같은 많은 과정이 내부에서 일어난다.

```text
브라우저 접속
-> DNS 조회
-> TCP 연결
-> TLS Handshake
-> HTTP 요청
-> 서버 응답
```

- Wireshark는 내 컴퓨터나 네트워크 인터페이스를 지나가는 패킷을 캡처하고 분석하여 보이지 않는 네트워크 흐름을 눈으로 볼 수 있게 해주는 도구이다.

#### 주제 13: Wireshark를 사용하는 이유
- 애플리케이션 로그만으로는 네트워크 문제를 확인하기 어려운 경우가 있다.
- 예를 들어 API 서버에 요청 로그가 찍히지 않는다면 요청이 애플리케이션까지 도달하지 않았을 수 있다.
- 이때 DNS에서 서버 IP를 제대로 응답하는지, HTTPS 연결이 어디서 실패하는지, 포트 문제인지, TLS Handshake 문제인지 등을 확인해야 한다.
- Wireshark는 애플리케이션에 도달하기 전 네트워크 계층에서 실제로 어떤 패킷이 오가는지 확인하는 데 도움을 준다.

#### 주제 14: Wireshark로 확인할 수 있는 것

| 확인할 수 있는 것 | 예시 |
| --- | --- |
| DNS 조회 | 도메인이 어떤 IP로 해석되는지 |
| TCP 연결 | 3-way handshake가 성공하는지 |
| 재전송 | 네트워크 손실로 재전송이 발생하는지 |
| TLS Handshake | HTTPS 연결이 어디서 실패하는지 |
| HTTP 요청 | 평문 HTTP 요청/응답 내용 |
| 포트 통신 | 특정 포트로 패킷이 실제로 나가는지 |
| 응답 지연 | 요청 후 응답까지 시간이 얼마나 걸리는지 |

#### 주제 15: Wireshark에서 보는 네트워크 계층

| Wireshark 표시 | 네트워크 개념 |
| --- | --- |
| Frame | 캡처된 프레임 전체 |
| Ethernet II | L2, MAC 주소 |
| Internet Protocol | L3, IP 주소 |
| TCP/UDP | L4, 포트 번호 |
| HTTP/DNS/TLS | L7, 애플리케이션 프로토콜 |

- Wireshark 화면에서 보이는 계층 구조는 실제 네트워크 계층을 이해하는 데 도움이 된다.
- Frame에서 시작해 Ethernet, IP, TCP/UDP, HTTP/DNS/TLS 순서로 보면 데이터가 어떤 계층의 헤더를 가지고 이동하는지 확인할 수 있다.

#### 주제 16: Wireshark 필터
- Wireshark에서 모든 패킷을 그대로 보면 양이 너무 많아 원하는 패킷을 찾기 어렵다.
- 그래서 필터를 사용해 보고 싶은 패킷만 골라서 확인한다.
- Capture Filter는 패킷을 캡처하기 전에 적용하는 필터이다.
- 어떤 패킷을 저장할지 결정하며, 예를 들어 `host 8.8.8.8`, `port 22`, `tcp` 같은 조건을 사용할 수 있다.
- Display Filter는 캡처한 뒤 어떤 패킷을 화면에 보여줄지 정하는 필터이다.
- Display Filter를 잘못 걸어도 원본 캡처가 남아 있다면 나중에 조건을 바꿔 다시 볼 수 있다.

| 보고 싶은 것 | Display Filter |
| --- | --- |
| DNS만 보기 | `dns` |
| HTTP만 보기 | `http` |
| TLS만 보기 | `tls` |
| TCP만 보기 | `tcp` |
| UDP만 보기 | `udp` |
| 특정 IP 보기 | `ip.addr == 8.8.8.8` |
| 특정 출발지 IP | `ip.src == 192.168.0.10` |
| 특정 목적지 IP | `ip.dst == 8.8.8.8` |
| 특정 포트 | `tcp.port == 443` |
| TCP 연결 시작 | `tcp.flags.syn == 1` |
| TCP 재전송 | `tcp.analysis.retransmission` |
