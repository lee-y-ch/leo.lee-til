# TIL

## 소제목: AWS EFS, S3, RDS 스토리지와 데이터베이스 운영 이해

### 새로 배운 내용

#### 주제 1: EFS란 무엇인가
- EFS(Elastic File System)는 AWS에서 제공하는 관리형 네트워크 파일 시스템이다.
- 사용자가 스토리지 용량을 직접 설정하거나 관리하지 않아도 자동으로 확장, 축소된다.
- 여러 EC2 인스턴스가 같은 파일 시스템을 공유해야 할 때 사용할 수 있다.
- EFS는 AWS가 제공하는 NFS(Network File System)의 일종으로 볼 수 있다.
- EC2에 EFS를 마운트하면 특정 디렉토리를 로컬 폴더처럼 사용할 수 있다.
- 해당 경로에 저장한 파일은 EC2의 EBS가 아니라 EFS에 저장된다.

#### 주제 2: EFS가 필요한 문제 상황
- EC2가 한 대라면 서버 디스크에 파일을 저장해도 크게 문제가 없을 수 있다.
- 하지만 EC2가 두 대 이상이 되면 각 서버의 로컬 디스크가 서로 분리되어 있어 문제가 생긴다.
- 예를 들어 `.env` 파일처럼 Git으로 관리하기 어렵고 서버에 로컬 파일로 존재해야 하는 파일이 있다.
- EC2가 여러 대라면 각 서버에 직접 접속해서 `.env` 파일을 별도로 만들어야 한다.
- 서버가 늘어날수록 파일 관리가 번거롭고 누락이나 불일치가 발생할 수 있다.
- 이런 상황에서 EFS를 사용하면 여러 EC2가 하나의 공유 파일 시스템을 함께 사용할 수 있다.

```text
EC2 A -> /efs/.env
EC2 B -> /efs/.env

두 인스턴스가 같은 EFS를 마운트하면 같은 파일을 공유할 수 있다.
```

#### 주제 3: Mount 개념
- Mount는 외부 파일 시스템을 서버의 특정 디렉토리에 연결해서 로컬 폴더처럼 사용하는 작업이다.
- EFS는 외부에 있는 네트워크 저장소이고, EC2는 이 저장소를 특정 경로에 붙여 사용한다.

```bash
mkdir -p /efs
cd /efs
touch hello.txt
```

- EC2 A와 EC2 B가 같은 EFS를 `/efs` 경로에 마운트하면, 한쪽에서 만든 파일을 다른 쪽에서도 확인할 수 있다.
- 단일 인스턴스 환경에서는 EBS만으로 충분한 경우가 많다.
- EFS는 다중 인스턴스 환경에서부터 필요성이 커진다.

#### 주제 4: EFS를 사용하는 경우

##### 여러 서버가 같은 파일을 공유해야 할 때
- 여러 웹 서버가 같은 업로드 파일을 제공해야 할 때 사용할 수 있다.
- 예를 들어 S3 없이 커뮤니티 서비스에서 프로필 사진을 공유해야 하는 상황을 생각할 수 있다.
- 여러 EC2에서 동일한 환경변수 파일, 키 파일, 설정 파일을 공유해야 할 때도 사용할 수 있다.
- 컨테이너 환경에서 여러 컨테이너가 같은 영속 볼륨을 사용해야 할 때도 고려할 수 있다.
- 쿠버네티스에서 여러 Pod가 영속성을 가져야 하고, 여러 EC2 내부에 분산되어 있다면 EBS만으로는 부족할 수 있다.

##### 용량을 예상할 수 없을 때
- EBS는 생성할 때 디스크 용량을 정해야 한다.
- 예를 들어 8GB, 30GB, 500GB처럼 미리 용량을 프로비저닝한다.
- 반면 EFS는 사용량에 따라 자동으로 확장된다.
- 동영상 업로드를 처리하는 미디어 서버처럼 임시 저장 용량을 예측하기 어려운 경우 EFS가 도움이 될 수 있다.
- 예를 들어 사용자가 업로드한 동영상을 로컬 스토리지에 임시 저장하고 포맷 검사를 한 뒤 클라우드에 업로드한다고 가정할 수 있다.
- 동시에 여러 사용자가 대용량 파일을 업로드하면 EBS 용량이 부족해질 수 있다.

##### 여러 가용영역에서 공유해야 할 때
- EFS는 같은 리전 안의 여러 AZ에서 접근할 수 있다.
- Regional EFS는 같은 리전의 여러 가용영역에 데이터를 중복 저장하는 방식이다.
- 예를 들어 서울 리전의 여러 AZ에서 같은 파일 시스템에 접근할 수 있다.
- 이를 통해 가용성을 높일 수 있다.

```text
서울 리전
- ap-northeast-2a
- ap-northeast-2b
- ap-northeast-2c
- ap-northeast-2d

각 AZ의 EC2가 같은 EFS 파일 시스템을 사용할 수 있다.
```

#### 주제 5: EFS 구성 요소

##### 파일 시스템
- 실제로 파일을 저장하고 폴더를 만드는 공간이다.
- EC2에서 마운트한 뒤 일반 파일 시스템처럼 사용할 수 있다.

##### Mount Target
- Mount Target은 VPC 안에서 EC2가 EFS에 접속하기 위한 네트워크 진입점이다.
- EFS는 VPC 내부에서 접근해야 한다.
- EC2가 EFS에 접속하려면 각 AZ에 있는 Mount Target을 통해 접근한다.

```text
EFS = 공용 창고
Mount Target = 창고로 들어가는 출입구
EC2 = 창고를 사용하는 직원
```

##### Security Group
- EFS는 퍼블릭 인터넷에 공개하는 서비스가 아니다.
- VPC 내부에서 EC2와 EFS가 통신할 수 있도록 Security Group을 설정해야 한다.
- EFS는 NFS 프로토콜을 사용하므로 TCP 2049 포트를 허용해야 한다.

| 대상 | 방향 | 포트(NFS) | 허용 대상 |
| --- | --- | --- | --- |
| EFS 보안 그룹 | Inbound | TCP 2049 | EC2 보안 그룹 |

- IP를 직접 열기보다 EC2 보안 그룹을 Source로 지정하면 역할 중심으로 접근을 제어할 수 있다.
- NFS 포트 2049를 인터넷 전체에 열면 안 된다.

#### 주제 6: EBS, EFS, S3 비교
- EBS는 서버 한 대에 연결해서 사용하는 디스크이다.
- EFS는 여러 서버가 공유하는 파일 시스템이다.
- S3는 파일 시스템이 아니라 객체 저장소이다.

| 구분 | EBS | EFS | S3 |
| --- | --- | --- | --- |
| 저장 방식 | 블록 스토리지 | 파일 스토리지 | 객체 스토리지 |
| 접근 방식 | EC2 디스크처럼 연결 | 여러 서버에서 마운트 | API, SDK, HTTP로 접근 |
| 여러 EC2 동시 접근 | 일반적으로 제한적 | 가능 | 가능하지만 파일 시스템 방식은 아님 |
| 대표 사용처 | EC2 운영체제, DB 디스크 | 공유 업로드 폴더, 공유 작업 파일 | 이미지, 동영상, 백업, 로그 |
| 파일 시스템 명령어 | 가능 | 가능 | 기본적으로 불가 |
| 확장 방식 | 용량 증설 작업 필요 | 자동 확장 | 자동 확장 |
| 성능 특성 | 낮은 지연 시간, 디스크 I/O | 공유 파일 시스템 | 대규모 객체 저장, 배포 |
| 비용 관점 | 프로비저닝 용량 기준 | 저장 사용량 + 요청/전송 고려 | 저장량 + 요청 + 전송 고려 |

#### 주제 7: 어떤 스토리지를 선택해야 할까
- 여러 서버가 같은 파일을 로컬 폴더처럼 사용해야 한다면 EFS를 고려한다.
- 고성능 디스크가 필요하고 특정 EC2에 붙여 사용할 파일 시스템이 필요하다면 EBS를 고려한다.
- 이미지, 영상, 로그처럼 객체로 저장해도 되는 데이터라면 S3를 고려한다.
- S3는 파일 시스템이 아니므로 `mkdir`, `cd`, `ls` 같은 파일 시스템 방식으로 기본 접근하지 않는다.
- S3는 API, SDK, HTTP 같은 별도 통신 방식으로 접근한다.

```text
여러 서버가 같은 파일을 로컬 폴더처럼 사용해야 하는가?
-> 예: EFS
-> 아니오: 고성능 디스크가 필요한가?
   -> 예: EBS
   -> 아니오: 객체 저장으로 충분한가?
      -> 예: S3
```

#### 주제 8: EFS 성능 관점
- EFS는 네트워크 파일 시스템이므로 네트워크 통신 지연을 고려해야 한다.
- 로컬 디스크처럼 붙어 보이지만 실제로는 네트워크를 통해 접근한다.
- 따라서 지연 시간과 처리량을 서비스 특성에 맞게 확인해야 한다.

##### 성능 모드
- EFS는 보통 일반 설정으로 시작한 뒤 실제 사용 지표를 보고 최적화하는 것이 좋다.

| 구분 | 특징 | 추천 상황 |
| --- | --- | --- |
| General Purpose | 낮은 지연 시간 중심 | 일반 웹 서비스, CMS, 홈 디렉터리 |
| Max I/O | 높은 병렬 처리 중심 | 아주 많은 클라이언트가 동시에 접근하는 특수 상황 |

- 일반적인 서비스에서는 General Purpose를 먼저 고려한다.

##### Throughput Mode

| 모드 | 특징 |
| --- | --- |
| Elastic | 사용량에 따라 처리량을 자동으로 늘리고 줄임 |
| Bursting | 파일 시스템 크기와 버스트 크레딧 특성을 활용 |
| Provisioned | 필요한 처리량을 직접 지정 |

- EFS 도입 초기에는 Elastic 모드를 우선 고려할 수 있다.

#### 주제 9: EFS 비용과 Lifecycle Management
- 클라우드에서는 저장, 요청, 전송, 처리량 등 대부분의 사용량이 비용으로 이어진다.
- 접근 속도가 빠른 저장소일수록 비용이 비싼 경우가 많다.
- 오래 접근하지 않는 파일은 더 저렴한 스토리지 클래스로 이동시키는 것을 고려해야 한다.
- EFS Lifecycle Management를 사용하면 일정 기간 접근하지 않은 파일을 저렴한 스토리지 클래스로 이동할 수 있다.
- EFS는 편리하지만 모든 파일 저장소로 쓰기에는 비용이 부담될 수 있다.
- FinOps 관점에서 공유 파일 시스템이 꼭 필요한 경우에 선택하는 것이 좋다.

#### 주제 10: 실무 적용 시 고려 사항

##### 모든 파일 저장소로 EFS를 사용하지 않는다
- EFS는 상대적으로 비용이 비쌀 수 있다.
- 공유 파일 시스템이 반드시 필요한 경우에 선택하는 것이 좋다.
- 단순 이미지, 영상, 백업, 로그 저장은 S3가 더 적절할 수 있다.

##### DB 디렉토리로 사용하지 않는 것이 좋다
- EFS는 네트워크 파일 시스템이다.
- MySQL, PostgreSQL 같은 데이터베이스는 IOPS와 지연 시간이 중요하다.
- EC2에 MySQL을 직접 설치하더라도 DB 디렉토리는 EFS보다 EBS를 사용하는 방식이 더 적절하다.
- 가능하다면 데이터베이스는 RDS를 사용하는 것을 우선 고려한다.

##### NFS Port 2049를 인터넷에 열면 안 된다
- EFS는 VPC 내부에서 사용하는 파일 시스템이다.
- NFS 포트 2049를 `0.0.0.0/0`으로 열어두면 위험하다.
- EFS 보안 그룹의 인바운드는 필요한 EC2 보안 그룹에서만 접근할 수 있게 제한해야 한다.

##### 백업 전략을 설계해야 한다
- EFS도 결국 스토리지이므로 중요한 파일은 백업 정책을 세워야 한다.
- RDS, ElastiCache, DocumentDB처럼 AWS의 관리형 서비스가 기본 백업을 제공하는 경우도 있지만, 파일 시스템은 사용자가 백업 정책을 직접 고려해야 한다.
- AWS Backup을 사용해 EFS 파일 시스템 백업 정책을 구성할 수 있다.

##### Security Group은 분리해서 붙이는 방식이 좋다
- 보안 그룹은 인스턴스 자체의 규칙을 계속 수정하는 방식보다, 목적별 보안 그룹을 따로 만들어 붙이는 방식이 관리하기 좋다.
- 예를 들어 EC2용 보안 그룹, EFS용 보안 그룹을 분리하고 EFS 인바운드에는 EC2 보안 그룹만 허용한다.

#### 주제 11: EFS 핵심 정리

| 항목 | 내용 |
| --- | --- |
| EFS | 여러 서버가 공유하는 관리형 파일 시스템 |
| 핵심 목적 | 여러 EC2가 같은 파일을 동시에 읽고 쓰기 |
| 접근 방식 | Linux에서 NFS로 마운트 |
| 대표 포트 | TCP 2049 |
| 주요 구성 | File System, Mount Target, Security Group, Access Point |
| 장점 | 자동 확장, 공유 파일 시스템, 다중 EC2 접근 |
| 적합한 사례 | 공유 업로드 파일, CMS, 컨테이너 공유 볼륨, 배치 파일 공유 |
| 부적합한 사례 | DB 데이터 디렉터리, CDN용 대규모 정적 콘텐츠 |
| EBS와 차이 | EBS는 서버 한 대의 디스크에 가깝고, EFS는 여러 서버 공유 파일 시스템 |

#### 주제 12: EFS 실습 흐름
- EC2 인스턴스를 생성한다.
- EC2 보안 그룹에 NFS 접근을 허용한다.
- EFS를 생성한다.
- EFS 네트워크 설정에서 EC2 보안 그룹을 선택하고 AZ를 확인한다.
- EC2에 SSH로 접속한다.
- NFS 클라이언트를 설치한다.

```bash
sudo apt update
sudo apt install -y nfs-common
```

- `which mount.nfs` 또는 `nfs4`로 NFS 클라이언트 프로그램 설치 여부를 확인한다.
- `mkdir -p /efs`로 마운트할 폴더를 생성한다.
- EFS 상세 화면의 연결 정보에서 가용영역에 맞는 IP 또는 연결 명령을 확인한다.
- EC2에서 EFS를 마운트한다.
- 마운트 성공 여부를 확인한다.

```bash
df -h | grep efs
findmnt /efs
```

#### 주제 13: S3란 무엇인가
- S3(Simple Storage Service)는 이미지, 동영상, 백업 파일, 로그처럼 많은 파일을 객체 단위로 저장하는 객체 스토리지 서비스이다.
- S3는 인터넷 또는 AWS 서비스에서 접근할 수 있게 해주는 관리형 스토리지이다.
- 서버 디스크를 폴더처럼 마운트해서 사용하는 서비스가 아니다.
- 파일을 업로드하면 S3에서는 이를 객체(Object)로 저장한다.
- S3 객체는 HTTP, AWS SDK, CLI, REST API 등을 통해 접근한다.
- 사용자의 파일이나 이미지를 EC2의 EBS에 직접 저장하면 서버가 바뀌거나 여러 대로 늘어났을 때 파일 관리가 어려워진다.
- EFS는 VPC 내부 공유 파일 시스템에 가깝고, 외부 브라우저에서 바로 접근해야 하는 이미지나 정적 파일은 S3가 더 적합한 경우가 많다.

[이미지 위치: 서버 디스크에 사용자 파일을 직접 저장할 때의 문제]
[이미지 위치: EFS로 묶기 애매하고 외부 접근이 필요한 정적 파일 구조]

#### 주제 14: 객체 스토리지란 무엇인가
- 객체는 S3에 저장되는 실제 데이터 단위이다.
- 이미지, 동영상, PDF 같은 파일은 S3에서 객체로 저장될 수 있다.
- S3 객체는 파일 데이터뿐 아니라 Bucket, Key, Metadata, Version ID 같은 정보를 함께 가진다.

| 구성 요소 | 설명 |
| --- | --- |
| Bucket | 객체가 저장되는 버킷 |
| Key | 객체의 고유한 경로 이름 |
| Value | 실제 파일 데이터 |
| Metadata | Content-Type, 생성 시각, 사용자 정의 메타데이터 등 |
| Version ID | 버전 관리 활성화 시 객체 버전 식별자 |

- EBS와 EFS는 파일 시스템이므로 마운트하거나 파일 시스템 명령어를 사용할 수 있다.
- S3는 객체 스토리지이므로 파일 시스템처럼 직접 `cd`, `touch`, `chmod`를 사용하는 구조가 아니다.

```text
s3://my-service-bucket/image/profile/charlie.png
HTTP GET https://my-service-bucket.s3.ap-northeast-2.amazonaws.com/image/profile/charlie.png
```

#### 주제 15: EFS와 S3 비교

| 구분 | EFS | S3 |
| --- | --- | --- |
| 저장 방식 | 파일 스토리지 | 객체 스토리지 |
| 접근 방식 | Linux 파일 시스템처럼 마운트 | SDK, CLI, REST API, HTTP |
| `cd`, `touch`, `chmod` 사용 | 가능 | 직접 사용 불가 |
| 여러 서버가 동시에 사용 | 가능 | 가능하지만 파일 시스템 방식은 아님 |
| 대표 용도 | 공유 폴더, CMS, 컨테이너 공유 볼륨 | 이미지, 동영상, 백업, 로그, 정적 콘텐츠 |
| 외부 브라우저 접근 | 직접 목적은 아님 | URL, CloudFront, Presigned URL로 가능 |

#### 주제 16: S3 핵심 구성 요소

##### Bucket
- Bucket은 S3 객체를 담는 최상위 저장 공간이다.
- 폴더와 비슷하게 보이지만 실제 파일 시스템의 폴더와는 다르다.

```text
my-service-bucket
├── image/
│   ├── profile/
│   └── post/
├── backup/
├── logs/
└── deploy/
```

- 버킷 이름은 AWS 전체에서 고유해야 한다.
- 일반적으로 소문자, 숫자, 하이픈을 사용한다.
- 이미 다른 사람이 사용 중인 버킷 이름은 사용할 수 없다.
- 버킷은 특정 리전에 생성된다.

##### Object
- Object는 S3에 실제로 저장되는 데이터 단위이다.
- 객체는 실제 파일 데이터와 메타데이터를 함께 가진다.

##### Key
- Key는 버킷 안에서 객체를 구분하는 고유한 이름이다.

```text
Bucket: my-service-bucket
Key: image/profile/charlie-01.png
URI: s3://my-service-bucket/image/profile/charlie-01.png
```

- S3 콘솔에서는 계층형 폴더처럼 보이지만 실제로는 디렉토리 구조를 관리하는 파일 시스템이 아니다.
- `image/profile/charlie-01.png` 전체가 하나의 Key로 저장되는 객체 스토리지 구조이다.

#### 주제 17: S3를 사용하는 이유

##### 제한 없이 확장 가능
- EC2 EBS는 용량이 부족하면 디스크를 늘리는 작업이 필요하다.
- S3는 저장할 객체가 늘어나도 사용자가 직접 디스크를 증설하지 않는다.
- AWS가 내부 저장 용량을 자동으로 확장한다.

##### 서버가 바뀌어도 파일이 유지
- EC2는 언제든지 종료되거나 교체될 수 있는 리소스이다.
- 파일을 S3에 저장하면 새로운 EC2가 IAM Role을 통해 S3에 접근해 기존 파일을 그대로 사용할 수 있다.

##### 내구성과 가용성이 높다
- S3 Standard는 매우 높은 객체 내구성을 제공한다.
- 내구성은 저장한 데이터가 사라지지 않을 가능성이다.
- 가용성은 필요할 때 서비스를 사용할 수 있는 가능성이다.

| 개념 | 의미 |
| --- | --- |
| 내구성(Durability) | 저장한 데이터가 사라지지 않을 가능성 |
| 가용성(Availability) | 필요할 때 서비스를 사용할 수 있는 가능성 |

#### 주제 18: S3와 EC2를 함께 사용하는 방식

##### 백엔드가 업로드를 처리하는 방식
- 사용자가 업로드한 파일을 일관적으로 관리해야 할 때 백엔드가 업로드를 처리한다.
- 파일 포맷을 맞춰야 하거나, 파일 사이즈를 제한해야 하거나, 리사이징과 압축이 필요한 경우 백엔드 처리 방식이 더 안전하다.
- S3는 파일을 저장하고 조회하게 하는 저장소일 뿐, 업로드된 파일이 안전한지 검사해주는 서비스가 아니다.
- 악성 코드 파일이나 잘못된 형식의 파일이 들어올 수 있으므로 보안적으로 중요한 파일은 애플리케이션에서 검증과 가공을 수행해야 한다.

[이미지 위치: 백엔드가 파일 업로드를 받아 검증 후 S3에 저장하는 구조]

##### Presigned URL 구조
- Presigned URL은 일정 시간 동안 특정 S3 버킷과 객체에 접근할 수 있게 만든 서명된 URL이다.
- 특정 객체에 대해 시간 제한이 있는 업로드 또는 다운로드 권한을 부여한다.
- 백엔드 서버가 큰 파일 데이터를 직접 받지 않아도 되므로 EC2 네트워크 자원을 덜 사용한다.
- 업로드 가능한 시간, 파일 경로, 권한을 제한할 수 있다.
- 단점은 파일에 대한 검증을 클라이언트에게 맡기게 된다는 점이다.
- 클라이언트는 변조하기 쉬우므로 항상 신뢰하면 안 된다.
- 파일 압축이나 형 변환을 클라이언트가 수행하면 브라우저와 클라이언트 환경 차이로 결과가 일정하지 않을 수 있다.
- 필요하다면 업로드 후 별도 배치 프로그램으로 검증, 압축, 변환을 처리할 수 있다.

[이미지 위치: Presigned URL 업로드 구조]

#### 주제 19: S3 주요 기능

##### Versioning
- Versioning은 같은 Key의 파일을 다시 올려도 이전 버전을 보관하는 기능이다.
- 실수로 삭제하거나 덮어쓴 경우에도 복구할 수 있다.
- 버저닝을 켜면 보관되는 데이터가 늘어나므로 Lifecycle Rule과 함께 설계하는 것이 좋다.

[이미지 위치: S3 Versioning 구조]

##### Lifecycle Rule
- Lifecycle Rule은 오래된 객체를 더 저렴한 스토리지 클래스로 옮기는 기능이다.
- 자주 접근하지 않는 백업, 감사 로그 같은 데이터는 더 저렴한 계층으로 이동시켜 비용을 줄일 수 있다.

[이미지 위치: S3 Lifecycle Rule 구조]

##### Storage Class
- 스토리지 클래스는 접근 속도, 복구 속도, 비용에 따라 선택한다.

| 스토리지 클래스 | 대표 사용처 |
| --- | --- |
| S3 Standard | 자주 사용하는 이미지, 애플리케이션 파일 |
| S3 Intelligent-Tiering | 접근 패턴이 예측하기 어려운 파일 |
| S3 Standard-IA | 가끔 읽는 백업 파일 |
| S3 One Zone-IA | AZ 장애 허용이 가능한 재생성 가능 데이터 |
| Glacier Instant Retrieval | 거의 안 쓰지만 빠른 조회가 필요한 데이터 |
| Glacier Flexible Retrieval | 장기 보관 백업 |
| Glacier Deep Archive | 매우 장기 보관, 가장 저렴한 수준의 아카이브 |

```text
서비스 이미지 -> S3 Standard
접근 패턴이 불확실한 파일 -> S3 Intelligent-Tiering
백업, 감사 로그 -> Lifecycle Rule로 IA 또는 Glacier 이동
```

#### 주제 21: EC2에서 S3 접근 흐름
- EC2에서 S3에 접근할 때는 EC2에 IAM Role을 연결하는 방식이 안전하다.
- EC2 내부 애플리케이션은 Role을 나타내는 임시 자격 증명을 받아 S3 API 요청에 서명한다.
- S3는 해당 Role의 권한 정책을 검사하고, 허용되면 업로드나 조회를 수행한다.

```text
IAM Role 생성
-> S3 접근 권한 정책 연결
-> Role을 EC2에 연결
-> EC2 내부 애플리케이션이 임시 자격 증명 획득
-> S3 API 요청에 서명
-> S3가 Role과 정책 확인
-> 허용되면 업로드, 조회 수행
```

- EFS는 VPC 내부에서 사용하는 파일 시스템이므로 외부에서 접근하려면 Web Server나 WAS에서 정적 파일을 서빙해야 한다.
- 외부 접근이 필요한 이미지, 동영상, 정적 콘텐츠는 S3가 더 적합한 경우가 많다.

#### 주제 22: RDS란 무엇인가
- RDS(Relational Database Service)는 클라우드에서 관계형 데이터베이스를 손쉽게 생성, 운영, 확장할 수 있도록 제공하는 완전관리형 서비스이다.
- 애플리케이션은 보통 데이터를 저장할 때 관계형 데이터베이스를 사용한다.
- 가장 단순한 방법은 EC2에 MySQL이나 PostgreSQL을 직접 설치하는 것이다.
- 하지만 운영 환경에서 DB를 설치하는 것보다 안정적으로 계속 운영하는 일이 훨씬 어렵다.
- OS와 DB 엔진 설치, 버전 관리, 보안 패치, 디스크 용량 관리, 백업과 복구, 장애 감지와 복구, 모니터링, 고가용성 구성, 읽기 성능 확장을 모두 직접 관리해야 한다.
- RDS는 이런 운영 작업을 AWS가 대신 처리하도록 만든 관계형 데이터베이스 운영 관리 서비스이다.

[이미지 위치: EC2에 백엔드, 프론트, DB, Cache를 함께 구성한 예시]

#### 주제 23: RDS의 의미

| 단어 | 의미 |
| --- | --- |
| Relational | 테이블 간 관계를 기반으로 하는 |
| Database | 데이터를 저장하고 관리하는 시스템 |
| Service | AWS가 제공하는 관리형 서비스 |
| RDS | 관계형 데이터베이스를 운영하기 쉽게 만든 서비스 |

- RDS 자체가 MySQL 같은 데이터베이스 프로그램은 아니다.
- RDS는 데이터베이스를 운영하기 위한 AWS 관리 서비스이다.

#### 주제 24: EC2에 DB 직접 설치 vs RDS

| 구분 | EC2에 DB 직접 설치 | RDS |
| --- | --- | --- |
| DB 설치 | 직접 설치 | AWS가 프로비저닝 지원 |
| 운영체제 관리 | 직접 관리 | AWS가 관리 |
| DB 패치 | 직접 계획, 수행 | 유지보수 설정 기반 관리 가능 |
| 백업 | 직접 스크립트, 스케줄 구성 | 자동 백업 기능 제공 |
| 장애 복구 | 직접 구성 | Multi-AZ 등 관리형 옵션 제공 |
| 모니터링 | 직접 도구 설치, 구성 | CloudWatch 등과 통합 |
| 디스크 관리 | EBS 직접 관리 | RDS 스토리지 설정으로 관리 |
| 유연성 | 매우 높음 | 엔진별 제약 존재 |
| 운영 부담 | 큼 | 상대적으로 작음 |

- EC2에 MySQL을 직접 설치하면 모든 관리를 직접 해야 한다.
- RDS를 사용하면 운영의 상당 부분을 AWS에 맡길 수 있다.
- 다만 RDS가 항상 정답은 아니다.
- 비용 문제와 회사 상황을 함께 보고 판단해야 한다.
- 초기 프로젝트라면 개발 속도와 운영 안정성이 중요하므로 RDS가 더 적절할 수 있다.
- 반대로 비용을 강하게 줄여야 하는 상황에서는 EC2 기반 DB 운영을 검토할 수도 있다.

#### 주제 25: 일반적인 RDS 구성
- RDS는 컴퓨팅 자원, DB 스토리지, AWS 관리 기능으로 구성된다.
- 컴퓨팅 자원에서는 MySQL, PostgreSQL 같은 DBMS가 실행된다.
- DB 스토리지에는 테이블 데이터, 인덱스, 트랜잭션 로그 등 실제 데이터가 저장된다.
- AWS 관리 기능으로 자동 백업, 모니터링, 장애 복구, DB 엔진 패치와 유지보수가 제공된다.
- 운영 환경에서는 RDS를 외부 인터넷에 노출하지 않고 Private Subnet에 두는 것이 일반적이다.
- 사용자는 RDS에 직접 접속하지 않는다.
- 애플리케이션 서버만 RDS에 접속하도록 구성한다.
- 개발자는 필요할 때 Bastion Host를 통해 DBeaver나 MySQL CLI로 RDS를 확인할 수 있다.

```text
사용자 요청
-> GET /posts
-> Spring Boot가 SELECT 실행
-> RDS가 결과 반환
-> Spring Boot가 JSON으로 응답
```

#### 주제 26: RDS 구성 요소

##### DB Engine
- DB Engine은 실제 데이터를 저장하고 SQL을 처리하는 데이터베이스 엔진이다.

```text
예시
- MySQL
- PostgreSQL
- MariaDB
- Oracle
- SQL Server
- Amazon Aurora
```

##### DB Instance
- DB Instance는 실제 DB 엔진이 실행되는 서버 자원이다.
- EC2 인스턴스 타입을 고르듯 RDS에서도 DB 인스턴스 클래스를 설정한다.
- DB 인스턴스 클래스는 CPU, 메모리, 네트워크 성능에 영향을 준다.

##### Storage
- RDS에는 데이터베이스 로우뿐 아니라 인덱스, 트랜잭션 로그, 자동 백업본, Slow Query Log 등이 저장된다.

| 항목 | 의미 |
| --- | --- |
| Storage Size | DB 데이터를 저장할 수 있는 용량 |
| IOPS | 초당 디스크 읽기, 쓰기 처리 횟수 |
| Throughput | 초당 읽고 쓸 수 있는 데이터 양 |

##### Endpoint
- Endpoint는 애플리케이션이나 DB 클라이언트가 RDS에 연결하기 위해 사용하는 네트워크 주소이다.

```text
mydb.abc123.ap-northeast-2.rds.amazonaws.com
```

```yaml
spring:
  datasource:
    url: jdbc:mysql://mydb.abc123.ap-northeast-2.rds.amazonaws.com:3306/app_db
    username: app_user
    password: ${DB_PASSWORD}
```

##### Security Group
- Security Group은 어떤 서버가 데이터베이스에 접근할 수 있는지 제어한다.

```text
sg-db 인바운드 규칙

Type   : MySQL/Aurora
Port   : 3306
Source : sg-app
```

#### 주제 27: IOPS와 Throughput

##### IOPS
- IOPS는 Input/Output Operation Per Second의 약자이다.
- 디스크가 1초 동안 처리할 수 있는 I/O 작업 횟수를 의미한다.
- 데이터베이스에서 데이터는 결국 디스크에 쓰이기 때문에 IOPS가 중요하다.
- PK나 인덱스 기반 조회가 많은 경우, Update가 많은 경우, 랜덤 액세스가 많은 경우 IOPS가 중요해진다.
- 주문, 결제, 실시간 로그 데이터처럼 작은 읽기와 쓰기가 자주 발생하는 서비스에서 특히 중요하다.

```text
게시글 상세 조회 API가 초당 500번 호출
한 요청에 DB I/O 평균 8번 발생
500 x 8 = 4,000 IOPS
```

- 실제 필요한 IOPS는 버퍼 풀, 인덱스, 캐시 여부에 따라 달라진다.

##### Throughput
- Throughput은 디스크가 1초에 얼마나 많은 데이터 양을 읽고 쓸 수 있는지를 의미한다.
- 단위는 MiB/s 또는 MB/s를 사용한다.
- 대량 조회, 리포트 생성, CSV/엑셀 처리, 대규모 배치 프로그램, 데이터 마이그레이션처럼 데이터 양이 큰 작업에서 중요하다.

| 구분 | IOPS | Throughput |
| --- | --- | --- |
| 의미 | 초당 I/O 작업 횟수 | 초당 전송 가능한 데이터 양 |
| 단위 | IOPS | MiB/s, MB/s |
| 병목이 자주 나는 작업 | 작은 랜덤 조회, 쓰기 | 대용량 순차 읽기, 쓰기 |
| 대표 예시 | 사용자 조회, 주문 처리, 재고 차감 | 배치, 백업, 리포트, 대량 데이터 처리 |
| 비유 | 택배기사가 1초에 처리하는 상자 개수 | 1초에 옮기는 전체 물량 |

- DB 선택 시에는 기본적으로 Throughput보다 IOPS를 더 우선해서 고려하는 경우가 많다.

#### 주제 30: RDS 백업 기능을 맹신하지 않기
- RDS가 자동 백업을 제공하는 것은 맞지만, 실제 복구가 검증된 것은 아니다.
- 백업은 과거로 돌아가는 기능이므로 DB가 터진 순간과 그 이후의 트랜잭션은 복구 과정에서 사라질 수 있다.
- 따라서 장애가 발생한 이후의 트랜잭션을 어떻게 처리할지 별도 전략이 필요하다.
- Redis 같은 인메모리 DB에 실패한 트랜잭션을 일정 기간 모아두는 방식도 고려할 수 있다.

#### 주제 31: DB 커넥션 풀
- 커넥션 풀은 애플리케이션이 DB 연결을 미리 만들어 두고, 요청이 들어올 때 빌려서 사용한 뒤 다시 반납하는 방식이다.

```text
요청
-> 커넥션 풀에서 연결 대여
-> SQL 실행
-> 연결 반납
```

- 매 요청마다 DB 연결을 새로 생성하는 비용을 줄일 수 있다.
- 커넥션 풀은 RDS가 아니라 각각의 애플리케이션 서버 내부에 존재한다.

```text
App A: 최대 20개
App B: 최대 20개
App C: 최대 20개

전체 최대 연결 수: 60개
```

```text
전체 최대 커넥션 수 = 애플리케이션 수 x 인스턴스당 커넥션 풀 크기
```

- 서버나 Pod가 늘어나면 RDS에 연결되는 전체 커넥션 수도 함께 증가한다.
- RDS에는 동시에 허용할 수 있는 최대 연결 수인 `max_connections`가 있다.
- 각 DB 연결은 메모리, CPU, 네트워크 소켓, 세션과 트랜잭션 정보를 사용한다.
- 연결 수를 무한정 늘리면 DB가 처리할 수 있는 쿼리보다 대기 중인 연결만 많아져 성능이 오히려 떨어질 수 있다.

```text
연결 수 증가
-> 메모리와 CPU 사용량 증가
-> 쿼리 대기 증가
-> 응답 지연 및 타임아웃 발생
```

- 커넥션 풀이 모두 사용 중이면 새로운 요청은 연결이 반납될 때까지 기다린다.
- 대기 시간이 초과되면 타임아웃이 발생한다.
- 애플리케이션에서 요청을 대기시키는 것이 DB에 계속 새로운 연결을 만드는 것보다 안전하다.

##### 커넥션 풀 설정 시 고려할 요소
- 애플리케이션 서버 또는 Pod의 개수
- 인스턴스당 커넥션 풀 크기
- RDS의 `max_connections`
- RDS의 CPU와 메모리
- 쿼리 실행 시간
- 트랜잭션 유지 시간
- 관리자, 배치, 모니터링용 여유 연결
- Spring Boot에서는 일반적으로 HikariCP를 사용하며, `maximumPoolSize`로 애플리케이션 하나가 사용할 최대 커넥션 수를 설정한다.

#### 주제 32: RDS 핵심 정리

| Multi-AZ | 장애 대응과 고가용성 목적 |
| Read Replica | 읽기 성능 확장 목적 |
