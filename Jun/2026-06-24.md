### 새로 배운 내용

#### 주제 1: ElastiCache란 무엇인가
- ElastiCache는 Redis나 Memcached 같은 인메모리 캐시 서버를 직접 EC2에 설치하고 운영하지 않아도 AWS에서 간편하게 생성하고 사용할 수 있도록 제공하는 관리형 캐시 서비스이다.
- AWS에서 관리해주는 인메모리 캐시 서비스라고 볼 수 있다.
- 분산형 인메모리 데이터 저장소로 사용할 수 있다.
- 반복 조회를 빠르게 처리하고 RDS 같은 원본 데이터베이스의 부하를 줄이는 것이 핵심 목적이다.

#### 주제 2: 데이터베이스만으로 서비스할 때 생기는 문제
- 커뮤니티 서비스에서 인기글이나 게시글 목록을 조회한다고 가정할 수 있다.
- 처음에는 RDS, MySQL 같은 관계형 데이터베이스에서 직접 조회해도 크게 문제가 되지 않는다.
- 하지만 1분 동안 1만 명이 같은 데이터를 조회한다면 MySQL에 부하가 집중된다.
- MySQL은 결국 디스크 조회가 발생하고, IOPS 한계 지점이 병목이 될 수 있다.
- Spring 서버가 여러 대로 늘어나도 모든 서버가 같은 DB를 반복 조회하면 DB가 병목 구간이 되는 경우가 많다.

#### 주제 3: 캐시란 무엇인가
- 캐시는 원본 데이터를 매번 다시 조회하지 않도록, 자주 사용하는 데이터를 빠르게 꺼낼 수 있게 임시로 저장하는 기술이다.
- 캐시에 데이터가 있으면 Cache Hit가 발생하고, 캐시에 있는 값을 바로 응답한다.
- 캐시에 데이터가 없으면 Cache Miss가 발생하고, RDS에서 조회한 뒤 응답하면서 캐시에 저장한다.

[이미지 위치: 캐시 조회 흐름]

```text
요청
-> 캐시 조회
-> Cache Hit이면 캐시 값 응답
-> Cache Miss이면 DB 조회
-> DB 조회 결과를 캐시에 저장
-> 응답
```

#### 주제 4: 캐시를 메모리에 저장하는 이유
- 캐시 저장소는 일반적으로 In-Memory 기반이다.
- 캐시는 자주 접근되고 빠른 속도가 필요하므로 RAM에 저장한다.
- 자주 변경되거나 빠르게 조회되어야 하는 데이터에 적합하다.

[이미지 위치: RDS와 ElastiCache 비교]

| 구분 | RDS | ElastiCache |
| --- | --- | --- |
| 핵심 역할 | 영구 데이터 저장 | 빠른 반복 조회 |
| 저장 위치 | 디스크 중심 | 메모리 중심 |
| 데이터 성격 | 원본 데이터 | 임시 복사본 또는 빠른 상태 데이터 |
| 정합성 | 강하게 관리 | TTL, 무효화 전략 필요 |
| 대표 사례 | 회원, 주문, 결제, 게시글 | 인기 목록, 세션, 랭킹, API 제한 |

- RDS를 사용하면서 ElastiCache를 함께 사용하는 구조가 일반적이다.

#### 주제 5: Cache-Aside 패턴
- Cache-Aside는 애플리케이션이 먼저 캐시를 조회하고, 캐시에 없을 때만 DB를 조회한 뒤 캐시에 저장하는 방식이다.
- 애플리케이션이 캐시 조회와 DB 조회, 캐시 저장 흐름을 직접 제어한다.

[이미지 위치: Cache-Aside 패턴]

##### Cache Hit
- 캐시에 데이터가 있는 경우이다.
- DB를 조회하지 않고 캐시 값으로 빠르게 응답할 수 있다.

##### Cache Miss
- 캐시에 요청한 데이터가 없는 경우이다.
- DB에서 데이터를 조회한 뒤 캐시에 저장하고 응답한다.

#### 주제 6: TTL 개념
- TTL(Time To Live)은 캐시 데이터가 자동으로 만료되기까지의 시간이다.

```text
Key = post::1::likeCount
Value = 10
TTL = 300s
```

- TTL은 캐시에 데이터가 오래 남아 있는 것을 방지하기 위해 필요하다.
- 캐시는 메모리 자원을 사용하므로 자원이 제한적이다.
- 캐시 데이터는 원본 데이터와 달리 정합성을 항상 보장하지 않는다.
- 캐시 데이터가 너무 오래 남아 있으면 최신 데이터와 달라질 수 있다.

#### 주제 7: TTL을 어떻게 설정해야 할까
- TTL은 짧다고 항상 좋은 것도 아니고, 길다고 항상 좋은 것도 아니다.
- TTL이 너무 짧으면 캐시 미스가 많이 생기고 RDBMS 조회가 늘어나 캐시 효과가 줄어든다.
- 대신 데이터 정합성은 상대적으로 높일 수 있다.
- TTL이 너무 길면 오래된 데이터를 보여줄 수 있고, 데이터 변경이 반영되지 않아 사용자 경험이 깨질 수 있다.
- 어떤 값을 캐싱하느냐에 따라 TTL을 다르게 설정해야 한다.

```text
자주 바뀌는 데이터
-> 짧은 TTL 검토

거의 바뀌지 않는 데이터
-> 긴 TTL 검토

즉시 최신 값이 필요한 데이터
-> TTL만 믿지 말고 캐시 삭제 또는 갱신 필요
```

#### 주제 8: 캐시 무효화 전략
- 캐시 무효화는 원본 데이터가 변경되었을 때 기존 캐시 값을 삭제하거나 수정하는 작업이다.
- 예를 들어 게시글 좋아요 수가 바뀌면 캐시된 좋아요 수를 함께 갱신하거나 삭제해야 한다.
- 일반 비즈니스 로직에서는 좋아요를 누르거나 취소할 때 캐시도 갱신하는 로직을 만들 수 있다.
- 하지만 중간에 트랜잭션이 실패하거나, 어드민에서 좋아요 수를 직접 수정하는 등 일반 흐름과 다른 변경이 발생하면 캐시 정합성이 깨질 수 있다.
- 따라서 캐시 무효화 전략은 TTL과 함께 설계해야 한다.

#### 주제 9: ElastiCache에서 사용할 수 있는 엔진
- ElastiCache에서는 Valkey, Redis OSS, Memcached 같은 엔진을 사용할 수 있다.

| 엔진 | 특징 | 대표 활용 |
| --- | --- | --- |
| Valkey | Redis OSS 호환 계열의 인메모리 저장소 | 캐시, 세션, 랭킹, Pub/Sub |
| Redis OSS | 다양한 자료구조와 기능 제공 | 캐시, 세션, 분산 락, 실시간 기능 |
| Memcached | 단순하고 가벼운 분산 키-값 캐시 | 단순 조회 캐시 |

- 캐시 저장소를 하나 만들면 한 가지 목적으로만 사용하지 않는 경우가 많다.
- 세션 스토어, 인기글, 랭킹, API Limiter 같은 여러 목적을 함께 수행할 수 있다.
- 목적들이 단순한 Key-Value 캐시만으로 해결되지 않을 때 Redis 계열의 자료구조가 유용하다.

```text
String
Hash
List
Set
Sorted Set
Stream
Pub/Sub
```

- 로그인 세션, 인기 검색어, API Limiter, 분산 락, 실시간 채팅 같은 기능에 활용할 수 있다.
- Memcached는 단순한 Key-Value Store 성격의 캐시에 적합하다.

#### 주제 10: ElastiCache 고가용성 구성
- ElastiCache는 Replica, Multi-AZ, Shard 구성을 통해 가용성과 확장성을 높일 수 있다.

##### Replica
- Replica는 고가용성과 읽기 확장을 위해 사용한다.
- Primary 노드에 장애가 발생했을 때 Replica를 승격해 장애 대응을 할 수 있다.

##### Multi-AZ
- Multi-AZ는 여러 가용영역에 캐시 노드를 배치해 장애에 대응하는 구성이다.
- 특정 AZ 장애가 발생해도 다른 AZ의 노드를 통해 서비스 연속성을 높일 수 있다.

##### Shard
- Shard는 데이터를 여러 조각으로 나누어 저장하는 방식이다.
- 저장 용량과 쓰기 처리량을 확장할 때 사용한다.
- 예를 들어 Key를 기준으로 여러 Shard에 분산 저장한다고 이해할 수 있다.

```text
1의 배수 -> Shard 1
2의 배수 -> Shard 2
3의 배수 -> Shard 3
```

#### 주제 11: 캐시를 사용할 때 알아야 하는 문제

##### 캐시는 원본 데이터가 아니다
- 캐시는 애초에 휘발성 데이터이다.
- Redis가 꺼지거나 RAM에 전기 공급이 끊기면 데이터가 사라질 수 있다.
- TTL이 끝나거나 장애로 제거될 수도 있다.
- 캐시에만 의존해 데이터를 조회하는 시스템은 위험하다.
- Cache Miss가 발생했을 때 영구 저장소를 조회하는 로직을 항상 준비해야 한다.
- 캐시가 사라졌을 때 복구할 수 있는 정책이 필요하다.

##### 캐시 스탬피드
- 캐시 스탬피드는 많은 캐시 키가 동시에 만료되어 갑자기 대량의 요청이 DB로 몰리는 문제이다.
- 예를 들어 매일 자정 인기글 10,000개를 캐시에 등록하고, 모두 TTL을 86,400초로 설정하면 같은 시각에 10,000개 키가 동시에 만료될 수 있다.
- 이때 많은 요청이 동시에 RDBMS로 폭증해 응답 지연, 타임아웃, 서비스 안정성 저하가 발생할 수 있다.

[이미지 위치: 캐시 스탬피드 구조]

- 실무에서는 TTL에 임의 값을 추가해 만료 시점을 분산한다.

```text
기본 TTL: 300초
실제 TTL: 300초 + 0~30초 랜덤 값
```

##### 메모리 부족 현상
- 캐시는 메모리에서 동작하고, 메모리는 한정된 자원이다.
- 캐시 메모리가 가득 차면 새 캐시가 생성되지 않거나 새 쓰기가 실패할 수 있다.
- Eviction 정책을 설정해 메모리가 부족할 때 오래되었거나 덜 사용된 키를 제거해야 한다.

#### 주제 13: ELB란 무엇인가
- ELB(Elastic Load Balancer)는 사용자의 요청을 여러 서버에 나누어 전달하고, 장애 난 서버는 자동으로 제외하여 서비스가 느려지거나 멈추는 일을 줄여주는 AWS 관리형 로드 밸런서 서비스이다.
- ALB는 ELB의 한 종류이다.

#### 주제 14: Load Balancer가 필요한 이유
- 웹 서비스는 처음 만들 때 서버 한 대에서 시작하는 경우가 많다.
- 서버 한 대로 운영하면 사용자가 많아졌을 때 한 서버에 요청이 몰려 응답 속도가 느려진다.
- 서버의 CPU와 메모리가 부족해지면 요청 처리 실패나 5xx 오류가 증가할 수 있다.
- 서버 프로세스가 종료되면 서비스 전체 접속이 불가능해질 수 있다.
- 배포를 위해 서버를 재시작하면 배포 중 사용자 요청이 실패할 수 있다.
- 서버를 여러 대 추가하면 어느 서버로 요청을 보내야 하는지 결정해야 한다.

| 상황 | 발생하는 문제 |
| --- | --- |
| 사용자가 많아짐 | 한 서버에 요청이 몰려 응답 속도가 느려짐 |
| 서버 CPU, 메모리 부족 | 요청 처리 실패, 5xx 오류 증가 |
| 서버 프로세스 종료 | 서비스 전체 접속 불가 |
| 배포를 위해 서버 재시작 | 배포 중 사용자 요청 실패 |
| 서버를 여러 대 추가 | 어느 서버로 요청을 보내야 하는지 결정 필요 |

- 서버를 여러 개 추가한다고 자동으로 서비스가 안정화되는 것은 아니다.
- 사용자 요청이 특정 서버에만 몰리거나 장애 난 서버로 계속 전달되면 서비스 품질이 떨어진다.

#### 주제 15: ELB가 해결하는 방식
- 사용자는 ELB로 접속을 요청한다.
- ELB는 연결된 리소스 중 건강하고 트래픽 여유가 있는 리소스에 요청을 분산한다.

[이미지 위치: ELB 요청 분산 구조]

| ELB의 역할 | 설명 |
| --- | --- |
| 요청 분산 | 여러 서버에 요청을 나누어 전달 |
| 장애 서버 제외 | 응답하지 않는 서버에는 새 요청을 보내지 않음 |
| 단일 진입점 제공 | 사용자는 하나의 도메인 또는 주소로 접속 |
| 서버 확장 지원 | 서버가 늘어나도 ELB가 새 서버에 요청 분산 |
| HTTPS 처리 | 인증서를 연결해 HTTPS 요청을 받을 수 있음 |
| 요청 분기 | URL 경로, 도메인 등에 따라 다른 서버 그룹으로 전달 가능 |

#### 주제 17: Health Check
- Health Check는 ELB가 서버가 정상인지 주기적으로 확인하는 기능이다.
- Spring 서버에서는 예를 들어 `/actuator/health` 경로를 사용할 수 있다.

```text
GET /actuator/health
```

- 정상 응답 예시는 다음과 같다.

```json
{
  "status": "UP"
}
```

- ELB는 이 경로를 주기적으로 요청하고, 정상 응답을 주는 서버에만 요청을 전달한다.

#### 주제 18: ELB 구조

##### Load Balancer
- 사용자가 접속하는 입구이다.
- 사용자는 Load Balancer 경로만 알면 요청할 수 있다.
- Route 53에서 `api.domain.com` 같은 도메인을 ALB Alias로 연결할 수 있다.

##### Listener
- Listener는 ELB가 특정 포트에서 요청을 기다리는 입구이다.

| Listener | 의미 |
| --- | --- |
| HTTP: 80 | 일반 웹 요청을 받는 입구 |
| HTTPS: 443 | 암호화된 웹 요청을 받는 입구 |

- 사용자는 HTTPS로 안전하게 요청을 전달하고, ALB는 내부 서버에 HTTP 요청을 전달할 수 있다.
- Listener에서는 포트 포워딩과 TLS 터미네이션까지 수행한다.

[이미지 위치: Listener와 TLS Termination 구조]

##### Rule
- Rule은 이 요청을 어디로 보낼지 결정하는 규칙이다.

| 요청 조건 | 전달 대상 |
| --- | --- |
| `/api/*` | API 서버 Target Group |
| `/admin/*` | 관리자 서버 Target Group |
| `/socket/*` | WebSocket 서버 Target Group |
| 그 외 요청 | 프론트엔드 서버 Target Group |

[이미지 위치: ALB Rule 기반 요청 분기]

##### Target Group
- Target Group은 실제 요청을 처리할 서버들의 묶음이다.
- 지정한 프로토콜과 포트로 등록된 대상에게 요청을 전달한다.

| 항목 | 예시 |

| 대상 유형 | EC2 인스턴스 |
| 프로토콜 | HTTP |
| 포트 | 8080 |
| Health Check 경로 | `/actuator/health` |

| 등록 대상 | EC2 서버 1, 2, 3 |

#### 주제 19: ELB 종류
- ELB에는 여러 종류의 로드 밸런서가 포함된다.
- 웹 서비스와 REST API라면 ALB를 우선 검토한다.
- TCP, UDP처럼 HTTP가 아닌 트래픽이면 NLB를 검토한다.

| 종류 | 주로 다루는 트래픽 | 대표 사용 사례 |
| --- | --- | --- |
| ALB | HTTP, HTTPS | 웹 서비스, Spring Boot API, 마이크로서비스 |
| NLB | TCP, TLS, UDP, QUIC | 게임 서버, TCP 서비스, 초저지연 서비스 |
| GWLB | 네트워크 보안 장비 트래픽 | 방화벽, IDS/IPS, 보안 어플라이언스 |
| CLB | 이전 세대 로드 밸런서 | 기존 레거시 시스템 |

- ALB는 HTTP, HTTPS 요청을 이해한다.
- ALB는 L7 계층, 즉 응용 계층 로드 밸런서이다.
- URL 경로, 도메인, 헤더 조건 등을 기준으로 요청을 분기할 수 있다.

[이미지 위치: ALB L7 요청 분기]

- CDN(Content Delivery Network) 서비스라고 볼 수 있다.

#### 주제 24: CloudFront가 필요한 이유
- 웹 서비스를 운영하면 사용자가 요청하는 파일과 API 응답은 원본 서버에 만들어진다.
- 정적 웹 페이지 파일은 S3에 있고, 이미지와 영상도 S3에 저장될 수 있다.
- 백엔드 API는 ALB를 거쳐 EC2에서 처리될 수 있다.
- 처음에는 이 구조만으로도 동작하지만, 사용자가 많아지거나 사용자와 서버의 거리가 멀어지면 문제가 생긴다.

[이미지 위치: S3, ALB, EC2 원본 구조]

| 문제 | 왜 발생할까? |
| --- | --- |
| 페이지 로딩이 느림 | 사용자가 원본 서버와 멀리 떨어져 있으면 네트워크 왕복 시간이 길어짐 |
| 이미지 요청이 원본 서버에 집중 | 같은 이미지라도 모든 사용자가 원본 서버에 요청 |
| 갑작스러운 트래픽 증가 | 원본 서버가 정적 파일 요청까지 모두 처리해야 함 |
| 서버 비용 증가 | 파일 전송과 서버 처리량이 계속 증가 |

- CloudFront는 사용자와 원본 서버 사이에 캐시 계층을 둔다.
- 전 세계에 분산된 CDN을 통해 원본에 매번 요청하지 않아도 가까운 위치에서 콘텐츠를 받을 수 있게 한다.

[이미지 위치: CDN 역할]

#### 주제 25: CDN과 Edge Location
- CDN은 여러 지역에 콘텐츠 전달 서버를 분산 배치하고, 사용자와 가까운 서버에서 콘텐츠를 내려받도록 하는 방식이다.
- CloudFront는 AWS에서 제공하는 CDN이다.

[이미지 위치: CDN 분산 구조]

- Edge Location은 콘텐츠를 캐싱해서 들고 있는 AWS의 분산 네트워크 거점이다.
- Edge Location은 원본 데이터를 영구적으로 저장하지 않는다.
- 자주 요청되는 콘텐츠의 복사본을 잠시 들고 있는 서버라고 볼 수 있다.

[이미지 위치: Edge Location 구조]

#### 주제 26: CloudFront 동작 방식과 구성 요소
- 사용자가 CloudFront로 요청하면, 가까운 Edge Location에 캐시가 있는지 확인한다.
- 캐시가 있으면 Edge Location에서 바로 응답한다.
- 캐시가 없으면 Origin으로 요청해 콘텐츠를 가져온 뒤 Edge Location에 캐시하고 사용자에게 응답한다.

[이미지 위치: CloudFront 동작 방식]

| 구성 요소 | 역할 |
| --- | --- |
| Distribution | CloudFront 배포 단위. 어떤 원본과 캐시 정책을 사용할지 정의 |
| Viewer | CloudFront에 요청하는 사용자 또는 브라우저 |
| Edge Location | 사용자 가까이에서 캐시된 콘텐츠를 전달하는 위치 |
| Origin | 원본 콘텐츠가 실제 저장된 위치 |
| Cache Behavior | 어떤 경로를 어떤 원본으로 보내고, 어떻게 캐시할지 정하는 규칙 |
| Cache Policy | 캐시 키와 TTL 등 캐시 동작을 결정하는 정책 |
| OAC | S3 원본에 CloudFront만 접근하도록 제한하는 기능 |

#### 주제 27: Cache Behavior
- Cache Behavior는 URL 경로에 따라 어떤 원본으로 요청을 보내고, 캐시를 어떻게 적용할지 정하는 규칙이다.

[이미지 위치: Cache Behavior 구조]

| 요청 경로 | Origin | 캐시 전략 |
| --- | --- | --- |
| `/images/*` | S3 | 길게 캐시 |
| `/assets/*` | S3 | 길게 캐시 |
| `/api/*` | ALB | 짧게 캐시 또는 캐시 비활성화 |
| `/` | S3 | HTML 특성에 맞게 짧게 캐시 |

- HTML 같은 웹 정적 페이지도 CloudFront에 캐싱할 수 있다.
- HTML 파일은 배포 시점에 변경되는 주기가 뚜렷하다.
- 배포 스크립트에 캐시 무효화 코드를 함께 넣어 관리할 수 있다.

#### 주제 28: 어떤 콘텐츠를 캐시해야 할까
- 모든 요청을 똑같이 캐시하면 안 된다.
- 콘텐츠 특성에 따라 캐시 전략을 다르게 설정해야 한다.

| 콘텐츠 종류 | 예시 | 권장 캐시 전략 |
| --- | --- | --- |
| 변경이 거의 없는 정적 파일 | 로고, 폰트, 라이브러리 파일 | 길게 캐시 |
| 빌드 결과물 | `app.8f3a2.js`, `main.2c4d.css` | 매우 길게 캐시 |
| 일반 이미지 | 프로필 이미지, 게시글 이미지 | 변경 빈도에 맞춰 캐시 |
| HTML | `index.html` | 짧게 캐시 |
| 로그인, 결제, 개인 정보 API | `/api/me`, `/api/orders` | 기본적으로 캐시하지 않음 |
| 공개 조회 API | 상품 목록, 공지 목록 | 조건부로 짧게 캐시 가능 |

#### 주제 29: CloudFront와 ALB 비교
- CloudFront와 ALB는 모두 사용자 요청 앞단에 위치할 수 있다.
- 하지만 해결하려는 문제가 다르다.
- CloudFront는 콘텐츠 캐싱과 글로벌 전송 가속이 핵심이고, ALB는 여러 서버에 요청을 분산하는 것이 핵심이다.

| 구분 | CloudFront | ALB |
| --- | --- | --- |
| 핵심 목적 | 콘텐츠 캐싱과 글로벌 전송 가속 | 여러 서버에 요청 분산 |
| 주요 위치 | 사용자와 원본 사이의 글로벌 엣지 | AWS 리전 내부의 애플리케이션 앞단 |
| 대표 대상 | 이미지, CSS, JS, 영상, 정적 파일 | EC2, ECS, 컨테이너, API 서버 |
| 캐시 | 핵심 기능 | 핵심 기능 아님 |
| Health Check | Origin 장애 대응 기능은 가능 | Target 서버 상태 확인이 핵심 |
| 대표 구조 | CloudFront -> S3 | ALB -> EC2/ECS |
| 함께 사용 | CloudFront -> ALB -> EC2/ECS | CloudFront의 Origin으로 사용 가능 |

#### 주제 30: CloudFront와 ALB를 함께 사용하는 구조
- CloudFront의 Origin으로 ALB를 둘 수 있다.
- 사용자는 CloudFront에 요청하고, CloudFront는 캐시 가능한 요청은 Edge Location에서 처리한다.
- API 요청처럼 원본 처리가 필요한 요청은 ALB로 전달하고, ALB가 EC2나 ECS로 분산한다.

#### 주제 32: CloudFront 정리

| 개념 | 핵심 |
| --- | --- |
| CloudFront | AWS의 CDN 서비스 |
| CDN | 사용자 가까운 위치에서 콘텐츠를 전달하는 분산 네트워크 |
