### 새로 배운 내용

#### 주제 1: Zero-Downtime Deployment란
- Zero-Downtime Deployment는 사용자의 입장에서 서비스 중단 없이 애플리케이션을 업데이트하거나 배포하는 방식이다.
- 서버나 컨테이너 자체는 교체 과정에서 종료될 수 있지만, 다른 정상 인스턴스가 요청을 계속 처리하므로 서비스는 중단되지 않는다.
- 기존 버전을 종료하기 전에 새 버전을 실행하고 준비가 완료되면 트래픽을 전환한다.
- 새 버전이 안정적으로 동작하는 것을 확인한 뒤 기존 버전을 종료한다.

```text
새 버전 준비
-> Health Check
-> Traffic 전환
-> 안정성 확인
-> 기존 버전 종료
```

#### 주제 2: 중단 배포와 Downtime
- 일반적인 중단 배포는 기존 서버를 종료한 다음 새 코드를 배포하고 새 서버를 실행한다.

```text
기존 서버 종료 -> 새 코드 배포 -> 새 서버 실행
```

```bash
docker compose down
docker compose pull
docker compose up -d
```

- 기존 Container가 종료된 뒤 새 Container가 준비될 때까지 요청을 처리할 서버가 없다.
- 서비스가 정상적으로 요청을 처리하지 못하는 시간을 Downtime이라고 한다.

[이미지 위치: 중단 배포 과정에서 발생하는 Downtime]

| 구분 | 설명 |
| --- | --- |
| 중단 배포 | 기존 버전을 종료한 후 새 버전을 실행하는 방식 |
| 무중단 배포 | 요청을 계속 처리하면서 새 버전으로 전환하는 방식 |

#### 주제 3: 무중단 배포의 기본 흐름
- 무중단 배포에서는 새 버전을 먼저 실행한다.
- 새 버전이 요청을 받을 준비가 되었는지 확인한다.
- 준비가 끝난 뒤 사용자 Traffic을 새 버전으로 전환한다.
- 새 버전이 정상적으로 동작하면 기존 버전을 종료한다.

[이미지 위치: 기존 버전이 요청을 처리하는 동안 새 버전을 준비하는 구조]

> 새 버전을 먼저 준비하고 검증한 뒤 Traffic을 전환해야 한다.

#### 주제 4: 무중단 배포가 필요한 경우
- 현대 Web Service는 대부분 항상 동작하는 것을 기본으로 기대한다.
- 여러 국가와 시간대에서 Traffic이 발생하는 Global Service는 점검 시간을 정하기 어렵다.
- Commerce, SaaS, API, Realtime Service처럼 지속적인 요청 처리가 중요한 서비스에서 무중단 배포가 유리하다.
- 그러나 모든 서비스가 반드시 무중단 배포를 사용해야 하는 것은 아니다.
- 게임처럼 한 번에 큰 변경이 필요하거나 은행처럼 변경 전후의 엄격한 검증과 통제가 필요한 서비스는 계획된 중단 배포를 선택할 수 있다.

| 배포 방식 | 대표적인 적용 예시 |
| --- | --- |
| 계획된 중단 배포 | 게임, 은행 등 일괄 변경 또는 엄격한 점검이 필요한 서비스 |
| 무중단 배포 | Commerce, SaaS, API, Realtime Service |

#### 주제 5: 무중단 배포의 목적
- 무중단 배포는 단순히 빠르게 배포하기 위한 방법이 아니다.
- 안정적으로 새 버전으로 전환하고, 문제가 생기면 빠르게 복구하며, 배포 과정과 결과를 지속적으로 관측하기 위한 방식이다.

| 요구사항 | 설명 |
| --- | --- |
| Availability | 배포 중에도 사용자가 서비스를 이용할 수 있어야 함 |
| Stability | 새 버전이 정상인지 확인한 뒤 Traffic을 받아야 함 |
| Rollback 가능성 | 문제가 생기면 이전 버전으로 빠르게 돌아갈 수 있어야 함 |
| Observability | Error Rate, Response Time, CPU, Memory 등을 확인할 수 있어야 함 |
| Automation | 수동 작업과 사람의 실수를 줄여야 함 |
| Reproducibility | 누가 배포해도 같은 절차와 결과가 나와야 함 |

#### 주제 6: 무중단 배포의 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| 다중 Instance 또는 Container | 기존 버전과 새 버전을 동시에 실행 |
| Load Balancer 또는 Reverse Proxy | 사용자 요청을 정상 서버로 분산 |
| Health Check | 새 버전이 실제 요청을 받을 준비가 되었는지 확인 |
| Traffic 전환 정책 | 기존 버전과 새 버전의 요청 비율 조절 |
| Rollback 전략 | 새 버전 문제 발생 시 이전 버전으로 복귀 |
| Monitoring | 배포 후 Error Rate, Response Time, Resource 상태 확인 |
| CI/CD Pipeline | Build, Test, Deploy 과정 자동화 |

#### 주제 7: 기존 요청 처리와 Graceful Shutdown
- Traffic 전환 후 기존 서버가 파일 업로드, 대용량 다운로드, 결제, 외부 API 요청, WebSocket 연결 등을 처리 중일 수 있다.
- 새 요청 전달을 중단했다고 기존 서버를 즉시 종료하면 처리 중인 요청이 실패한다.
- Connection Draining 또는 Graceful Shutdown은 기존 서버에 새 요청을 보내지 않으면서 진행 중인 요청을 완료할 시간을 주는 방식이다.

[이미지 위치: Traffic 전환 후 기존 요청을 마무리하는 Connection Draining]

```text
1. 새 버전 실행
2. 새 버전 Health Check 통과
3. 새 버전에 Traffic 전달 시작
4. 기존 버전에는 새 요청 전달 중단
5. 기존 요청 완료 대기
6. 기존 버전 종료
```

- ECS와 EKS 같은 관리형 환경에서는 종료 유예 시간을 설정하여 Graceful Shutdown을 지원한다.
- 단순히 새 서버 Process가 실행되었다는 이유만으로 기존 서버를 즉시 종료하면 안 된다.

#### 주제 8: 대표적인 무중단 배포 전략

| 전략 | 핵심 개념 | 특징 |
| --- | --- | --- |
| Blue/Green | 두 환경을 준비하고 Traffic을 한 번에 전환 | 빠른 전환과 Rollback |
| Rolling | 기존 Instance를 순차적으로 새 버전으로 교체 | 구조가 비교적 단순하고 추가 Resource가 적음 |
| Canary | 일부 사용자 또는 Traffic에 새 버전을 먼저 제공 | 실제 운영 환경에서 위험 범위 축소 |

#### 주제 9: Stateless Application
- 무중단 배포를 위해 Application은 가능한 한 Stateless하게 설계해야 한다.
- 사용자 상태를 서버 Memory에 저장하면 요청이 다른 Instance로 전달되거나 서버가 교체될 때 문제가 발생한다.
- 로그인 Session, Ranking, Query Cache 같은 상태를 외부 저장소로 분리한다.

| 상태 데이터 | 일반적인 저장 위치 |
| --- | --- |
| 사용자 로그인 Session | Redis |
| 사용자 데이터 | MySQL, PostgreSQL 등 DB |
| 업로드 파일 | S3, EFS, Object Storage |
| Cache | Redis, Memcached |
| Message | Kafka, RabbitMQ, SQS |

#### 주제 10: 무중단 Database Schema 변경
- Application은 Blue/Green이나 Rolling 방식으로 무중단 배포할 수 있지만 DB Schema 변경은 더 신중해야 한다.
- 배포 중에는 V1과 V2가 동시에 요청을 처리할 수 있으므로 두 버전 모두 호환되는 Schema가 필요하다.

```text
V1: users.nickname 사용
V2: users.display_name 사용
```

- `nickname`을 먼저 삭제하면 아직 실행 중인 V1이 실패한다.
- 기존 버전과 새 버전이 함께 사용할 수 있도록 단계적으로 변경한다.

```text
1. display_name Column 추가
2. V2가 nickname과 display_name을 함께 처리하도록 개발
3. 기존 Data Migration
4. 모든 Server를 V2로 전환
5. V2 안정성 확인
6. 더 이상 사용하지 않는 nickname Column 제거
```

> DB 변경은 이전 버전과 새 버전이 함께 동작할 수 있는 호환 구간을 만들어야 한다.

#### 주제 11: Rollback 기준과 Monitoring
- Container 실행과 Health Check 성공만으로 배포가 안정적이라고 판단할 수 없다.
- 배포 직후에는 정상으로 보이더라도 실제 Traffic에서 HTTP 500 Error가 증가하거나 DB 부하가 발생할 수 있다.
- Rollback은 배포 Script 실패뿐 아니라 운영 지표가 불안정할 때도 실행해야 한다.

| 관측 항목 | 확인 이유 |
| --- | --- |
| HTTP 5xx 비율 | Server Error 증가 여부 |
| Response Time p95, p99 | 일부 사용자 요청 지연 여부 |
| CPU와 Memory | Resource 부족 여부 |
| DB Connection 수 | DB 과부하 여부 |
| Container 재시작 횟수 | Application 비정상 종료 여부 |
| 핵심 Business 지표 | 결제, 주문, 로그인 성공률 확인 |

- 배포 후 일정 시간 동안 지표를 관찰해야 한다.
- 어떤 지표가 어느 기준을 넘으면 어떤 버전으로 어떻게 Rollback할지 미리 정의한다.
- 무중단 배포 방식 자체보다 안정적인 Rollback 계획과 Observability가 더 중요하다.

| 해결하는 문제 | 배포 중 Downtime, 요청 실패, 사용자 불편 |

#### 주제 13: Blue/Green Deployment
- Blue/Green Deployment는 두 개의 독립된 환경을 동시에 운영하고 Traffic을 새 환경으로 전환하는 방식이다.
- 새 버전을 별도 환경에 배포하고 검증할 수 있어 Downtime과 배포 위험을 줄인다.
- 문제가 발생하면 이전 환경으로 Traffic을 되돌려 빠르게 Rollback할 수 있다.

##### Blue와 Green의 의미
- Blue가 항상 이전 버전이고 Green이 항상 새 버전인 것은 아니다.
- 이름보다 현재 Traffic을 받는 환경과 다음 배포를 위해 대기하는 환경을 분리하는 것이 핵심이다.

```text
현재 운영
app-blue:1.0.1

다음 배포
app-green:1.0.2

그다음 배포에서는
app-blue:1.0.3이 새 환경이 될 수 있음
```

#### 주제 14: Blue/Green의 장점

##### 빠른 Rollback
- 새 버전에 문제가 생기면 대기 중인 이전 환경으로 Traffic을 다시 전환한다.
- Reverse Proxy가 가리키는 대상을 Green에서 Blue로 바꾸고 설정을 Reload하는 방식으로 복구할 수 있다.

[이미지 위치: Reverse Proxy Traffic을 Green에서 Blue로 되돌리는 Rollback]

- 결제와 주문처럼 장애 영향이 큰 서비스에 유리하다.
- API 변경 위험이 큰 배포, 신규 기능 Release, 대규모 Refactoring, Infra 설정 변경처럼 빠른 Rollback이 필요한 상황에 적합하다.

##### 배포 구조가 비교적 명확하다
- 현재 환경과 신규 환경이 분리되어 있어 배포 흐름을 이해하기 쉽다.
- 새 환경을 Traffic 전환 전에 독립적으로 검증할 수 있다.

##### 장애 영향을 줄일 수 있다
- 사전 검증과 빠른 Rollback으로 사용자 영향을 줄일 수 있다.

#### 주제 15: Blue/Green의 단점

##### Resource 비용
- Blue의 구성을 Green에도 준비해야 하므로 배포 시점에는 Resource가 거의 두 배로 필요할 수 있다.
- 운영에 EC2 10대가 필요하다면 전환 전 Green 10대를 추가로 준비할 수 있다.

##### 이중 운영 위험
- 안정화 후 기존 환경을 제거하지 않으면 불필요한 비용과 운영 복잡도가 계속 발생한다.
- 배포 Script에 정리 단계가 누락되지 않도록 해야 한다.

##### DB 변경의 어려움
- Blue와 Green이 동시에 사용하는 동안 두 버전 모두 호환되는 DB Schema를 제공해야 한다.

#### 주제 16: Blue/Green 실무 주의점

##### Green 실행 직후 Traffic을 전환하지 않는다
- Green Process 실행과 정상 동작은 다르다.
- Health Check를 통과한 뒤 Traffic을 전환한다.

##### Traffic 전환 직후 Blue를 종료하지 않는다
- Health Check 통과는 장기 안정성을 보장하지 않는다.
- 실제 운영 지표가 정상임을 확인할 때까지 Blue를 Rollback 대상으로 유지한다.

##### Rollback 조건을 먼저 정의한다
- 어떤 지표가 어떤 수치에 도달하면 어떤 방식으로 Rollback할지 Code로 작성한다.

```text
예: HTTP 5xx Rate가 정의한 기준을 넘으면 Blue로 Traffic 복귀
```

##### Blue와 Green의 설정을 일치시킨다
- 환경 변수, Docker Network, CPU, Memory, IAM Role과 권한이 다르면 새 버전의 결과가 달라질 수 있다.

#### 주제 17: Blue/Green 핵심 정리

| 항목 | 핵심 내용 |
| --- | --- |
| Blue | 현재 운영 중이거나 Rollback 가능한 안정 환경 |
| Green | 새 버전을 배포하고 검증하는 환경 |
| 핵심 원리 | 새 버전을 먼저 준비한 뒤 Traffic만 전환 |
| 핵심 장점 | 빠른 Rollback, 낮은 Downtime, 분리된 사전 검증 |
| 핵심 단점 | 배포 중 이중 Resource 비용, DB 호환성 문제 |

#### 주제 18: Rolling Deployment
- Rolling Deployment는 여러 Instance를 한 번에 종료하지 않고 일부씩 새 버전으로 교체하는 전략이다.
- Infra를 두 배로 준비하지 않으면서 일정 수 이상의 Server가 요청을 처리하도록 유지한다.

```text
V1 10대
-> V1 9대 + V2 1대
-> V1 8대 + V2 2대
-> ...
-> V2 10대
```

- 기존 V1 Instance를 Load Balancer에서 제외하고 V2를 실행한다.
- V2 Health Check를 통과하면 Load Balancer에 등록한 뒤 다음 V1을 교체한다.
- AWS ECS, Kubernetes, EKS 같은 관리형 Platform에서 제공하는 Rolling 기능을 사용하는 경우가 일반적이다.

#### 주제 19: Rolling Deployment 방식

| 방식 | 핵심 | 특징 |
| --- | --- | --- |
| In-place | 기존 Instance를 종료한 뒤 같은 자리에서 새 버전 실행 | 추가 Resource가 적게 필요 |
| Side-by-side | 새 Instance를 먼저 추가한 뒤 기존 Instance 제거 | 처리 용량 유지에 유리 |

| 비교 항목 | In-place | Side-by-side |
| --- | --- | --- |
| 새 버전 실행 시점 | 기존 Server 제거 후 실행 | 새 Server 먼저 추가 |
| 추가 Resource | 거의 필요 없음 | 일시적으로 필요 |
| 배포 중 처리 용량 | 감소할 수 있음 | 비교적 유지 가능 |
| 배포 안정성 | 상대적으로 낮음 | 상대적으로 높음 |
| Rollback 속도 | 이전 버전을 다시 배포 | 기존 버전이 남아 있을 수 있음 |
| 적합한 환경 | 소규모, Resource 제한 환경 | Traffic이 많고 안정성이 중요한 환경 |

- 어떤 방식을 사용할지는 Traffic Pattern, Service 상황, Update 시간에 따라 결정한다.

#### 주제 20: Rolling Deployment의 장단점

##### 장점
- Blue/Green보다 동시에 유지하는 Resource가 적어 Infra 비용을 줄일 수 있다.
- V2 비율을 조금씩 늘리므로 변경 영향을 점진적으로 전달한다.
- 일부 V2에 문제가 발생해도 초기에는 영향받는 Instance 범위가 제한된다.

##### 단점
- Instance가 많으면 전체 교체에 시간이 오래 걸린다.
- 배포 중 V1과 V2가 동시에 요청을 처리한다.
- Client가 V2 기능을 기대했는데 V1이 응답하는 Version 호환 문제가 생길 수 있다.

```text
/api/v1/users/me
/api/v2/users/me
```

- V2가 많이 배포된 뒤 Rollback하면 제거된 V1을 다시 순차적으로 만들어야 하므로 Blue/Green보다 복구가 느릴 수 있다.

#### 주제 21: Blue/Green과 Rolling 비교

| 비교 항목 | Blue/Green | Rolling Deployment |
| --- | --- | --- |
| 배포 방식 | 환경 두 개를 준비한 뒤 Traffic 전환 | 기존 Instance를 순차 교체 |
| Traffic 전환 | 보통 한 번에 전환 | 교체 과정에서 자연스럽게 분산 |
| 추가 Resource | 배포 중 상당히 필요 | 설정에 따라 일부만 필요 |
| 배포 속도 | 전환 자체는 빠름 | 전체 완료까지 시간이 걸릴 수 있음 |
| Rollback 속도 | 매우 빠름 | 이전 버전 재배포가 필요할 수 있음 |
| V1과 V2 혼재 | 비교적 분리 가능 | 배포 중 혼재가 일반적 |

#### 주제 22: Rolling 핵심 정리

| 항목 | 핵심 내용 |
| --- | --- |
| Rolling Deployment | 기존 Instance를 일부씩 새 버전으로 교체 |
| 핵심 목표 | 배포 중 일정 수 이상의 Server가 요청 처리 |
| 핵심 흐름 | V1 제외 -> V2 실행 -> Health Check -> V2 등록 -> 다음 V1 교체 |
| In-place | 기존 Server를 하나씩 새 버전으로 교체, 추가 Resource가 적음 |
| Side-by-side | 새 Server를 먼저 추가한 뒤 기존 Server 제거, 용량 유지에 유리 |
| Rollback | 이전 버전을 다시 순차 배포하는 방식이 일반적 |

#### 주제 23: Canary Deployment
- Canary Deployment는 새 버전을 모든 사용자에게 한 번에 공개하지 않고 일부 사용자나 Traffic에 먼저 노출하는 전략이다.
- 실제 운영 환경에서 지표를 확인한 뒤 새 버전의 노출 범위를 점진적으로 확대한다.
- 문제가 생겼을 때 영향을 받는 사용자 범위를 줄이는 것이 목적이다.

#### 주제 24: Canary와 Rolling의 차이
- Rolling은 Infra와 Instance를 어떻게 교체할지에 초점을 둔다.
- Canary는 어떤 사용자 또는 어느 정도의 Traffic에 새 버전을 노출할지에 초점을 둔다.

| 구분 | Rolling Deployment | Canary Deployment |
| --- | --- | --- |
| 핵심 목적 | Server와 Pod를 순차적으로 새 버전으로 교체 | 새 버전 위험을 작은 사용자 집단에서 검증 |
| 기준 | Instance 교체 순서 | Traffic 비율 또는 사용자 Group |
| 새 버전 노출 | 새 Instance가 준비되면 자연스럽게 요청 처리 | 일부 요청만 의도적으로 전달 |
| 배포 판단 | 새 Instance가 정상인지 확인 | Error Rate, Response Time, Business 지표 분석 |
| 대표 질문 | 몇 대씩 교체할 것인가? | 처음 몇 퍼센트에 노출할 것인가? |

#### 주제 25: Canary Traffic 제어
- 단순한 Traffic 비율로 V1 90%, V2 10%처럼 분배할 수 있다.
- 확률 기반 분배에서는 같은 사용자가 요청마다 V1과 V2를 오갈 수 있다.
- Client Version과 Server Version 사이에 호환 조건이 있으면 단순 Traffic 비율만으로는 문제가 생길 수 있다.
- Web Browser는 새 Client 배포가 비교적 쉽지만 설치형 App이나 PC Program은 사용자의 Update 시점을 강제하기 어렵다.

##### 사용자 Group 고정
- 특정 사용자가 계속 같은 Version을 사용하도록 Tracking 기준을 활용할 수 있다.

```text
- Device Type
- OS Version
- Client Version
- 성별 또는 연령대
- User ID를 이용한 Group 분리
```

- 특정 사용자 Group에 서로 다른 Version이나 기능을 제공하는 방식은 A/B Test와도 연결된다.

#### 주제 26: Bake Time
- Bake Time은 Canary Traffic을 유지하면서 새 버전의 실제 운영 지표를 관찰하는 시간이다.
- 일부 Traffic을 V2에 보낸 직후 전체 배포로 넘어가지 않고 정해진 시간 동안 Error Rate, Response Time, Business 지표를 확인한다.
- 예를 들어 10분 동안 지표를 관찰한 뒤 다음 Traffic 확대 여부를 판단할 수 있다.

#### 주제 27: 배포 전략 선택 기준

| 기준 | Blue/Green | Rolling | Canary |
| --- | --- | --- | --- |
| 핵심 목적 | 환경 단위 빠른 전환과 Rollback | Resource를 아끼며 순차 교체 | 사용자 영향 범위를 제한한 검증 |
| Resource 비용 | 높음 | 비교적 낮음 | Traffic 제어 구조에 따라 다름 |
| Rollback | 이전 환경으로 빠른 전환 | 이전 버전 순차 재배포 | 새 버전 Traffic을 줄이거나 차단 |
| Version 혼재 | 전환 전후 분리하기 쉬움 | 배포 중 혼재 | 의도적으로 일부 사용자에게 혼재 |
| 적합한 상황 | 장애 영향이 크고 빠른 복구가 중요 | Instance가 많고 비용을 고려 | 실제 사용자 지표로 위험을 검증 |
