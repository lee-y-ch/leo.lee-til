### 새로 배운 내용

#### 주제 1: Continuous Integration(CI)이란
- CI는 개발자가 작성한 코드를 자동으로 통합하고 테스트하여 코드 품질을 지속적으로 유지하는 개발 프로세스이다.
- 여러 개발자의 변경 사항을 하나의 기준 코드에 자주 통합하고, 통합할 때마다 자동 빌드와 테스트를 수행한다.
- 변경 사항을 개인 브랜치에 오래 쌓아두지 않고 GitHub 같은 공유 코드베이스에 작은 단위로 자주 반영한다.
- 통합 결과가 실패하면 원인이 되는 변경이 작을 때 빠르게 수정한다.

> CI는 팀의 통합 방식과 자동 검증 체계를 함께 의미한다.

#### 주제 2: CI가 필요한 이유
- 여러 개발자가 결제, 주문, 회원, 쿠폰 같은 기능을 오랫동안 각자 개발한 뒤 한꺼번에 합치면 문제가 커진다.
- 각자의 로컬에서는 정상이어도 통합 후에는 같은 파일 수정, DTO 변경, 의존성 충돌, DB Schema 변경 등이 다른 영역에 영향을 줄 수 있다.
- 변경 범위가 크면 언제, 누구의 Commit 때문에, 어떤 문제가 발생했는지 추적하기 어렵다.

##### CI가 없을 때 발생하는 문제
- 개발자가 자신의 로컬 환경에서만 테스트한다.
- 병합 후에야 Compile 또는 Build 실패를 발견한다.
- 테스트 실행을 빠뜨릴 수 있다.
- 배포 직전에 여러 문제를 한꺼번에 발견한다.
- 문제를 만든 Commit과 PR을 추적하기 어렵다.

##### CI가 제공하는 검증
- PR을 만들거나 코드를 Push하면 공통 Runner 환경에서 다음 항목을 자동으로 확인한다.

```text
- Compile이 되는가?
- Test를 통과하는가?
- Code Quality 규칙을 지켰는가?
- Dependency 문제가 없는가?
- Build가 되는가?
- Docker Image가 정상적으로 만들어지는가?
```

| 문제 | CI가 해결하는 방식 |
| --- | --- |
| 개발자가 로컬에서만 테스트 | 공통 Runner 환경에서 자동 검증 |
| 병합 후 Build 실패 발견 | PR 또는 `main` 병합 직후 자동 Build |
| 테스트 실행 누락 | Test 실행을 병합 조건으로 설정 |
| Code Review만으로 오류 확인 | 자동 Test와 Static Analysis를 함께 실행 |
| 오류를 만든 변경 추적이 어려움 | Commit과 PR 단위 실행 로그 제공 |
| 배포 직전에 문제 집중 | 작은 변경 단위로 빠르게 실패 발견 |

#### 주제 3: CI를 구성하는 원칙

##### 1. 하나의 기준 Codebase를 사용한다
- 팀이 신뢰하는 기준 Branch가 필요하다.
- `main`은 항상 동작하고 배포 가능한 상태를 목표로 한다.
- `dev`와 `feature` Branch를 사용한다면 기능 Branch의 변경을 `dev`에 자주 통합하고 검증한 뒤 기준 Branch로 반영한다.

```text
main
└── dev
    ├── feature/login
    ├── feature/payment
    └── feature/coupon
```

##### 2. 변경 사항을 자주 통합한다
- CI에서 Continuous는 코드가 계속해서 통합되어야 한다는 의미이다.
- 개발자가 다른 사람의 코드와 오랫동안 분리된 채 작업하지 않아야 한다.
- 로그인 API 형식 변경, 예외 처리, Dockerfile 개선처럼 작은 변경 단위로 통합한다.
- 인증, 결제, 주문, 쿠폰을 하나의 PR에 넣거나 전역 Refactoring과 기능 추가를 한 PR에 섞는 방식은 피한다.
- 변경 규모가 커지면 Build, Test, Dependency 검증 비용이 커지고 개발자가 CI를 피하게 될 수 있다.

##### 3. 재현 가능한 Build를 만든다
- 개발자 노트북에서는 되지만 CI Runner에서는 실패하는 상황을 줄여야 한다.
- Secret 누락, 비독립적인 Test, 로컬 전용 Dependency, 환경 차이를 제거한다.

| 항목 | 역할 |
| --- | --- |
| `pom.xml`, `build.gradle` | Java Dependency와 Build 설정 |
| `package.json`, `package-lock.json` | Node.js Dependency와 버전 고정 |
| `Dockerfile` | Container 실행 환경 정의 |
| `docker-compose.yml` | 여러 Container 구성 정의 |
| `.github/workflows/*.yml` | GitHub Actions 자동화 정의 |
| Test Code | 기대 동작 정의 |
| `.env.example` | 환경 설정 구조 공유 |

##### 4. Test를 자동으로 실행한다
- CI는 Build 성공만 확인하는 과정이 아니다.
- Build, Test, Dependency 검증, 필요하면 Static Analysis와 Security Check까지 자동으로 실행해야 한다.
- 검증이 수동이면 개발 일정 때문에 통합과 Test가 미뤄질 수 있다.

#### 주제 4: Build와 Test

##### Build
- Build는 Source Code를 실행 가능한 결과물로 만드는 과정이다.
- Java에서는 Code Compile, Dependency Download, JAR 생성 등이 포함된다.

```bash
./gradlew build
```

##### Test
- Test는 기대하는 동작이 실제로 수행되는지 Code로 검증하는 과정이다.
- 회원가입이라면 이메일 형식, 중복 이메일, 비밀번호 암호화, 성공 응답 등을 검증할 수 있다.

```java
@Test
void 중복된_이메일로_회원가입하면_예외가_발생한다() {
    // given
    String email = "test@example.com";
    userRepository.save(User.create(email, "encoded-password"));

    // when & then
    assertThatThrownBy(() -> userService.signUp(email, "password"))
        .isInstanceOf(DuplicateEmailException.class);
}
```

#### 주제 5: Test의 종류와 역할

| 종류 | 확인 대상 | 특징 | CI 적용 우선순위 |
| --- | --- | --- | --- |
| Unit Test | 함수, Class, Service Logic | 빠르고 원인 추적이 쉬움 | 매우 높음 |
| Integration Test | DB, Redis, API, Module 연결 | 실제 환경 문제를 더 잘 발견 | 높음 |
| E2E Test | 사용자의 전체 흐름 | 실제 사용자 경험과 가까움 | 핵심 Scenario에 선택적 적용 |
| Static Analysis | Code 규칙, 잠재 오류 | 실행 전 Code Quality 검사 | 높음 |

| Test의 역할 | 설명 |
| --- | --- |
| 기능 검증 | 현재 기능이 요구사항대로 동작하는지 확인 |
| 회귀 방지 | 새 기능과 Refactoring이 기존 기능을 깨뜨렸는지 확인 |
| 요구사항 문서 | 입력과 예상 결과를 Code로 기록 |
| 변경 안전성 | 수정의 영향 범위를 빠르게 확인 |
| 설계 Feedback | Test하기 어려운 Code에서 과도한 책임과 의존성 발견 |

#### 주제 6: 좋은 Test Code의 원칙

##### 동작을 검증한다
- 단순히 특정 Method가 호출되었는지보다 사용자가 기대하는 결과와 상태 변화를 검증한다.

```java
@Test
void 정상적인_정보로_회원가입하면_회원이_저장된다() {
    // given
    String email = "test@example.com";

    // when
    UserResponse response = userService.signUp(email, "password123!");

    // then
    assertThat(response.email()).isEqualTo(email);
    assertThat(userRepository.existsByEmail(email)).isTrue();
}
```

##### 하나의 중요한 동작만 검증한다
- 회원가입, 로그인, 게시글 작성, 댓글 작성, 로그아웃을 하나의 Test에 넣지 않는다.
- 회원가입 성공, 중복 이메일 실패, 비밀번호 암호화처럼 Test를 중요한 동작별로 나눈다.

##### Test끼리 독립적이어야 한다
- 실행 순서와 상관없이 항상 같은 결과가 나와야 한다.
- 각 Test는 필요한 데이터를 직접 준비하고 다른 Test에 상태를 남기지 않아야 한다.
- 병렬 실행에서도 데이터가 충돌하지 않아야 한다.

#### 주제 7: Given-When-Then
- Given-When-Then은 Test Code를 준비, 실행, 검증으로 나누어 읽기 쉽게 만드는 방식이다.

| 구분 | 의미 | 질문 |
| --- | --- | --- |
| Given | Test 준비 | 어떤 상황인가? |
| When | 대상 실행 | 무엇을 실행했는가? |
| Then | 결과 검증 | 무엇이 일어나야 하는가? |

```java
@Test
void 주문_수량이_0이면_예외가_발생한다() {
    // given
    Long userId = 1L;
    Long productId = 10L;
    int quantity = 0;

    // when & then
    assertThatThrownBy(
        () -> orderService.createOrder(userId, productId, quantity)
    ).isInstanceOf(InvalidOrderQuantityException.class);
}
```

#### 주제 8: Test 대상의 우선순위
- 모든 Code를 같은 수준으로 Test할 수는 없으므로 중요한 기능부터 작성한다.

| 우선순위 | 대상 | 예시 |
| --- | --- | --- |
| 매우 높음 | 핵심 Business Rule | 주문 가능 여부, 결제 금액, 권한 검증 |
| 매우 높음 | 장애 시 피해가 큰 Logic | 중복 결제, 재고 차감, Point 차감 |
| 높음 | 입력 검증과 예외 처리 | 잘못된 요청, 권한 없음, 중복 데이터 |
| 높음 | 복잡한 조건과 계산 | 할인 정책, 등급 정책, 상태 전이 |
| 중간 | 외부 System 연동 | Redis, DB, Message Queue, 외부 API |
| 낮음 | 단순 DTO, Getter, Setter | 단순 데이터 전달 객체 |
| 낮음 | Framework 자동 설정 | Spring Boot 기본 설정, 단순 Configuration |

#### 주제 9: TDD와 Test Coverage
- TDD(Test Driven Development)는 구현 전에 Test를 작성하고, 실패하는 Test를 통과하는 구현을 만든 뒤 Refactoring하는 개발 방법론이다.

[이미지 위치: TDD의 Red, Green, Refactor 흐름]

##### TDD의 장점
- 요구사항을 구현 전에 Test Code로 구체화할 수 있다.
- 작은 Test부터 작성하면서 기능을 작은 단위로 개발하게 된다.

##### TDD 적용 시 주의점
- 개발자가 예상하지 못한 Case는 Test에도 포함되지 않을 수 있다.
- 높은 Coverage가 Business Logic의 완전성을 보장하지 않는다.
- Test 통과 자체가 목적이 되면 실제 동작보다 Test에 맞춘 구현을 만들 수 있다.

##### Test Coverage를 바라보는 기준
- Coverage 숫자를 높이는 것 자체를 목표로 삼지 않는다.
- 장애나 실수를 발견한 기능에는 재발 방지를 위한 Test를 추가한다.
- 앞으로 변경되어도 반드시 동작해야 하는 핵심 기능을 검증한다.
- 좋은 Test는 중요한 Business 동작을 검증하고, 서로 독립적이며, 같은 입력에서 같은 결과를 만든다.

#### 주제 10: PR과 CI의 흐름

[이미지 위치: PR 생성부터 main 통합까지의 CI 흐름]

| 시점 | 목적 |
| --- | --- |

- PR 단계의 CI는 병합 전 Feedback을 제공한다.
- `main` 단계의 CI는 여러 변경이 합쳐진 최종 상태를 다시 확인한다.

#### 주제 11: CI Quality Gate
- Quality Gate는 CI가 성공했다고 판단하는 기준이다.

| 단계 | 필수 여부 | 이유 |
| --- | --- | --- |
| Compile 및 Build 성공 | 필수 | 실행 불가능한 Code의 병합 방지 |
| Unit Test 통과 | 필수 | 핵심 Logic 회귀 방지 |
| Integration Test 통과 | 가능하면 필수 | DB, Redis, 외부 연동 오류 확인 |
| PR Review 승인 | 팀 상황에 따라 | 설계, 가독성, 의도 검토 |
| Static Analysis | 점진적 도입 | Code 규칙과 잠재 문제 탐지 |
| Security Check | 점진적 도입 | 알려진 취약점 탐지 |
| E2E Test | 핵심 기능만 | 느린 Test의 비용 관리 |

#### 주제 12: 신뢰할 수 있는 CI 운영

##### 빠르고 신뢰할 수 있어야 한다
- CI 결과가 30분씩 걸리면 실패 발견이 늦어지고 그 위에 다른 Commit이 쌓인다.
- 개발자는 느린 CI를 무시하거나 우회할 수 있다.
- 속도와 검증 범위의 균형을 위해 실행 시점을 나눈다.

| 구분 | 실행 시점 | 예시 |
| --- | --- | --- |
| 빠른 검사 | 모든 PR Push | Compile, Unit Test, Format Check |
| 중간 검사 | PR 생성 또는 병합 | Integration Test, Docker Image Build |
| 느린 검사 | `main` 병합 후 또는 야간 | 전체 E2E, 부하 Test, Security Scan |

##### 깨진 Test를 방치하지 않는다
- 데이터 존재를 가정하거나 현재 시간, 외부 API, 병렬 실행 순서에 의존하면 같은 Code에서도 결과가 달라지는 Flaky Test가 된다.
- 깨진 Test를 방치하면 Quality Gate에서 제외하게 되고 CI의 신뢰가 무너진다.

##### Secret과 권한을 최소화한다
- CI Runner는 저장소 Code를 실행하는 외부 환경일 수 있다.
- SSH Key, AWS 권한, 운영 Secret을 필요 이상으로 제공하면 계정이나 Workflow가 탈취되었을 때 피해가 커진다.
- Workflow마다 필요한 최소 권한만 부여한다.

#### 주제 13: CI에 대한 오해
- Test가 존재한다고 자동으로 CI가 되는 것은 아니다.
- CI에는 공유 Codebase, 자주 통합하는 팀 규칙, 자동 Build, 자동 Test가 함께 필요하다.
- CI를 통과해도 모든 Bug가 사라지는 것은 아니다.
- Test는 개발자가 정의한 기대와 예상 가능한 실패를 검증한다.
- CI의 목적은 오류를 완전히 없애는 것이 아니라 운영 배포 전에 빠르게 발견하는 것이다.

#### 주제 14: Continuous Deployment(CD)란
- CD는 자동화된 Test를 통과한 Code를 운영 환경까지 자동으로 배포하는 Process이다.
- CI가 “Code가 정상적으로 동작하는가?”를 확인한다면 CD는 “검증된 Code를 Server와 사용자에게 어떻게 안전하게 전달할 것인가?”를 다룬다.
- CI 성공만으로 기능이 사용자에게 제공되는 것은 아니다. 새 Version 준비, 환경 설정, 서비스 교체, 동작 확인, 실패 시 복구가 남아 있다.

[이미지 위치: CI 완료 후 배포 단계로 이어지는 흐름]

```text
운영 Server 접속
-> 새 Version 준비
-> 기존 Service 교체
-> 환경 변수 적용
-> 새 Version 동작 확인
-> 문제 발생 시 이전 Version 복구
```

> CD는 CI 이후 배포와 검증, 실패 시 복구 과정을 자동화한다.

#### 주제 15: 수동 배포의 문제

```bash
ssh ubuntu@server
git pull
docker build -t memo-api .
docker stop memo-api
docker rm memo-api
docker run -d -p 3000:3000 --name memo-api memo-api
```

- 작은 Project에서는 가능하지만 규모가 커지면 사람마다 절차가 달라지고 실수할 가능성이 커진다.

| 문제 | 실제 상황 |
| --- | --- |
| 배포 절차가 사람마다 다름 | 어떤 사람은 Source를 Build하고 다른 사람은 Image만 교체 |
| 운영 Server를 잘못 조작 | 개발 Server 대신 운영 Server에서 Test 명령 실행 |
| Test한 Code와 배포 Code가 다름 | Test 이후 다른 Commit을 Pull하여 배포 |
| 환경 설정 누락 | `.env`, Port, DB 주소, API Key 누락 |
| 배포 이력이 불명확 | 현재 운영 중인 Version을 알기 어려움 |
| 장애 복구가 느림 | 이전 Image와 복구 절차를 다시 찾아야 함 |
| 배포 중 서비스 중단 | 기존 Container 종료 후 새 Container 실행 |

- CD는 배포 절차를 Code로 만들어 누가 실행해도 같은 결과를 얻도록 한다.
- 핵심은 명령 입력 시간을 줄이는 것이 아니라 배포를 예측 가능하고 복구 가능하게 만드는 것이다.

#### 주제 16: CD가 해결하는 문제

| 해결하려는 문제 | CD가 제공하는 방식 |
| --- | --- |
| 반복적인 배포 작업 | 정해진 Pipeline으로 자동 실행 |
| 사람의 실수 | Test 성공 시에만 다음 단계 진행 |
| 배포 Version 추적 | Image Tag, Commit SHA, 배포 이력 관리 |
| 환경별 설정 혼동 | 개발, Staging, 운영 환경 분리 |
| 배포 후 장애 발견 | Health Check, Log, Monitoring |
| 장애 시 복구 지연 | 이전 안정 Version으로 Rollback |
| 동시 배포 충돌 | 배포 순서와 실행 권한 제어 |

| --- | --- | --- |
| CI | Code Quality 검증 | Build, Test, Static Analysis |

#### 주제 18: Artifact
- Artifact는 CI를 통과한 뒤 실제로 배포할 수 있는 결과물이다.

| 환경 | Artifact 예시 |
| --- | --- |
| Spring | JAR |
| Docker | Image |
| React, Vue | `dist/` |

[이미지 위치: CI Runner에서 생성한 Artifact의 저장과 전달]

##### Artifact를 별도로 보관하는 이유
- 운영 Server에서 직접 Build하지 않는다.
- 운영 Server마다 OS, Java Version, Library, 생성 시점이 다를 수 있다.
- CI Runner의 동일한 환경에서 한 번 Build한 결과물을 여러 Server에 배포한다.

```text
Build once, deploy many times
```

- GitHub Actions의 각 Job은 별도 Runner에서 실행되므로 파일이 자동으로 공유되지 않는다.
- JAR, `dist/`, Test Report는 Artifact로 Upload하고 다음 Job에서 Download할 수 있다.
- Docker Image는 Registry에 Push하여 배포 단계에서 같은 Image를 Pull한다.

#### 주제 19: Continuous Delivery와 Continuous Deployment
- CD는 문맥에 따라 Continuous Delivery 또는 Continuous Deployment를 의미한다.
- 차이는 운영 배포 전에 사람이 승인하는지 여부이다.

| 구분 | Continuous Delivery | Continuous Deployment |
| --- | --- | --- |
| 한국어 | 지속적 전달 | 지속적 배포 |
| Test와 Build | 자동 | 자동 |
| Image 생성과 저장 | 자동 | 자동 |
| Staging 배포 | 자동 | 자동 |
| 운영 배포 | 승인 후 실행 | 자동 실행 |
| 핵심 가치 | 안정성과 통제 | 속도와 자동화 |
| 적합한 환경 | 금융, 공공, 승인 절차가 필요한 조직 | 빠른 배포와 Feedback이 중요한 Service |

##### Continuous Delivery

```text
Test 성공
-> Image 생성
-> Staging 배포
-> 담당자 승인
-> 운영 배포
```

##### Continuous Deployment

```text
Test 성공
-> Image 생성
-> 운영 Server 배포
-> Health Check
-> 성공하면 운영 지속
-> 실패하면 Rollback
```

#### 주제 20: Health Check와 Rollback
- Container Process가 실행 중이어도 내부 Application은 오류 상태일 수 있다.
- Backend에는 Service의 실제 상태를 확인할 Health Check API가 필요하다.
- 새 Version 배포 후 Health Check가 실패하면 이전 안정 Version으로 되돌린다.

```bash
docker pull my-api:new-version
docker run -d --name my-api-new my-api:new-version

if ! curl --fail http://localhost:8080/health; then
  # 새 Version 중단 후 이전 안정 Version 재실행
  ./rollback.sh
fi
```

#### 주제 21: GitHub Actions란
- GitHub Actions는 GitHub Repository의 Event를 기준으로 Build, Test, 배포 Workflow를 자동 실행하는 CI/CD Platform이다.
- EC2와 ECS 같은 VM 또는 Container 기반 배포에서 사용할 수 있다.
- Kubernetes 환경에서는 Jenkins나 Argo CD 같은 도구도 함께 고려할 수 있다.

```text
GitHub Push 또는 PR
-> Dependency 설치
-> Test
-> Build
-> Docker Image 생성
-> Docker Hub 또는 ECR Push
-> EC2 또는 ECS 배포
-> 배포 결과 확인
```

| 구분 | CI에서 하는 일 | CD에서 하는 일 | GitHub Actions 구현 |
| --- | --- | --- | --- |
| 목적 | Code가 정상인지 검증 | 검증된 Code 배포 | YAML Workflow 작성 |
| 대표 작업 | Test, Lint, Build | Image Push, EC2/ECS 배포 | Job과 Step 구성 |
| 실행 시점 | PR 생성, Push | `main` 병합, Tag Push | `on:` Event 설정 |
| 실패 시 | PR 병합 차단 | 배포 중단 또는 Rollback | Job 실패 처리 |

#### 주제 22: GitHub Actions의 핵심 구성

[이미지 위치: Event, Workflow, Job, Step, Action, Runner 관계]

| 구성 요소 | 설명 | 예시 |
| --- | --- | --- |
| Event | Workflow를 시작하는 GitHub Event | `push`, `pull_request`, `workflow_dispatch` |
| Workflow | 자동화 전체 흐름을 정의한 YAML | `.github/workflows/ci.yml` |
| Job | 독립적으로 실행되는 작업 단위 | `test`, `build`, `deploy` |
| Step | Job 안에서 순서대로 실행되는 단계 | Checkout, Dependency 설치, Test |
| Action | 재사용 가능한 자동화 Code | `actions/checkout`, `actions/setup-java` |
| Runner | Job이 실제로 실행되는 컴퓨터 | `ubuntu-latest`, Self-hosted Runner |

#### 주제 23: Event와 Workflow

##### Event
- Event는 어떤 일이 발생했을 때 Workflow를 시작할지 정의한다.

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [dev]
```

| Event | 사용 사례 |
| --- | --- |
| `push` | `main` 병합 후 배포 |
| `pull_request` | PR 생성 시 Test, Lint, Build |
| `workflow_dispatch` | GitHub 화면에서 수동 실행 |
| `schedule` | 정기 Security Check와 Batch |
| `release` | Release 생성 시 Package 배포 |
| `issues` | Issue 생성 시 Slack 또는 Discord 알림 |

- PR 검증, Test 배포, 운영 배포 Workflow를 목적별로 분리할 수 있다.

##### Workflow
- Workflow는 GitHub Actions가 수행할 전체 자동화 절차이다.
- Repository의 `.github/workflows` 아래에 YAML 파일로 작성한다.

```text
my-project/
├── src/
├── package.json
└── .github/
    └── workflows/
        ├── ci.yml
        └── cd.yml
```

- Workflow를 Code로 관리하면 변경 이력을 남기고 누구나 같은 절차를 실행할 수 있다.

#### 주제 24: Runner
- Runner는 Job이 실제로 실행되는 환경이다.

```yaml
runs-on: ubuntu-latest
```

- GitHub-hosted Runner는 GitHub가 제공하는 새 가상 머신에서 Job을 실행한다.
- Job마다 별도 환경을 사용하므로 이전 Job의 Code, Dependency, 생성 파일이 다음 Job에 자동으로 전달되지 않는다.
- Dependency는 Cache를 사용하고 결과물은 Artifact로 전달한다.
- GitHub-hosted Runner는 사용자의 EC2 내부에서 실행되는 것이 아니다.

##### Private Subnet에 접근하는 방법
- 외부 Runner가 SSH로 접근하도록 Network를 열 수 있지만 Port와 IP, Credential 관리가 필요하다.
- Private Network 안의 EC2에 Self-hosted Runner를 설치할 수 있다.
- AWS CodeDeploy 같은 배포 도구를 중간에 사용할 수 있다.
- 어떤 방법이든 Secret과 Network 권한을 최소화해야 한다.

#### 주제 25: Job과 Step

##### Job
- Job은 Workflow 안의 독립 작업 단위이다.
- Job들은 기본적으로 병렬 실행할 수 있으며 각각 별도 Runner를 사용한다.
- `needs`로 실행 순서를 지정한다.
- 선행 Job이 실패하면 후속 Job은 기본적으로 실행되지 않는다.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh
```

- Checkout, Dependency 설치, Test, Build를 각각 별도 Job으로 지나치게 잘게 나누면 Runner가 달라져 파일 공유 설정이 복잡해진다.

##### Step
- Step은 한 Job 안에서 순서대로 실행되는 단계이다.

```yaml
steps:
  - name: Checkout repository
    uses: actions/checkout@v6

  - name: Install dependencies
    run: npm ci

  - name: Run tests
    run: npm test
```

#### 주제 26: Action
- Action은 반복되는 기능을 재사용할 수 있도록 만든 자동화 Code이다.
- GitHub 공식 Action뿐 아니라 외부에서 만든 Action도 사용할 수 있으므로 출처와 권한을 확인해야 한다.

| Action | 역할 |
| --- | --- |
| `actions/checkout` | Repository Code를 Runner로 내려받음 |
| `actions/setup-node` | Node.js 설치와 설정 |
| `actions/setup-java` | Java 설치와 설정 |
| `actions/cache` | Dependency Cache 저장과 복구 |
| `docker/login-action` | Docker Hub 또는 Registry Login |
| `docker/build-push-action` | Docker Image Build와 Push |
| `actions/upload-artifact` | Build 결과물 Upload |
| `actions/download-artifact` | 다른 Job의 Build 결과물 Download |

#### 주제 27: GitHub Actions CI 예시

[이미지 위치: GitHub Actions Workflow 실행 흐름]

```yaml
name: Backend CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: backend-ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - name: Checkout repository
        uses: actions/checkout@v6

      - name: Set up JDK 21
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
          cache: maven

      - name: Run Maven verification
        run: ./mvnw -B verify
```

#### 주제 28: Cache와 Artifact

| 구분 | Cache | Artifact |
| --- | --- | --- |
| 목적 | 실행 속도 향상 | 결과물 전달과 보관 |
| 대표 대상 | npm, Gradle, Maven Dependency | JAR, `dist/`, Test Report |
| 다음 Job 전달 | 가능하지만 주목적이 아님 | 가능 |

```yaml
- name: Upload build result

    name: frontend-build
    path: dist/
```

```yaml
- name: Download build result
  uses: actions/download-artifact@v4
  with:
    name: frontend-build
```

```yaml
- uses: actions/setup-node@v4

    node-version: 22
```

#### 주제 30: CI/CD 핵심 정리

| 개념 | 핵심 |
| --- | --- |
| CI | 변경 사항을 자주 통합하고 Build와 Test를 자동 수행하는 개발 방식 |
| Test Code | 핵심 기능이 요구사항을 만족하는지 검증하는 Code |
| Test Coverage | Test가 실행한 Code 범위를 나타내는 지표이며 품질 자체를 보장하지 않음 |
| TDD | Test를 먼저 작성하고 구현과 Refactoring을 진행하는 개발 방법론 |
| Given-When-Then | Test를 준비, 실행, 검증으로 구조화하는 방식 |
| CD | CI 결과물을 정해진 규칙으로 배포하고 검증하며 필요하면 Rollback하는 Process |
| Artifact | CI에서 생성한 배포 가능한 JAR, Image, `dist/` 등의 결과물 |
| GitHub Actions | GitHub Event를 기반으로 CI/CD를 실행하는 Platform |
| Workflow | CI/CD 자동화 흐름을 정의한 YAML 파일 |
| Runner | Job이 실제로 실행되는 GitHub-hosted 또는 Self-hosted 환경 |
| Job | Workflow 내부의 독립 실행 단위 |
| Step | Job 안에서 순차 실행되는 단계 |
| Action | 재사용 가능한 자동화 Code |
| Health Check | 배포된 Service가 실제로 정상 동작하는지 확인 |
| Rollback | 장애가 발생한 새 Version을 이전 안정 Version으로 복구 |
